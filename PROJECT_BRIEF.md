# Project Brief

Source of truth for the `ai-sandbox` project. Machine-read fields live in the YAML frontmatter above; prose below is for humans. Generated and confirmed via the project-builder agent against the existing repo state on 2026-05-10.

## Overview

- **name:** ai-sandbox
- **problem:** Claude Code's permission prompts interrupt autonomous workflows, but running Claude with `--dangerously-skip-permissions` directly on the host is unsafe — it has unrestricted access to the user's files, network, credentials, and shell. There is no out-of-the-box way to get a fully autonomous Claude that is also confined.
- **users:**
  - Solo developers and tinkerers who want a long-running autonomous Claude on their own machine without it touching the host.
  - Open-source contributors and operators in the Claude Code community who prefer a one-command setup over rolling their own devcontainer.
  - Linux operators who want a one-command setup over rolling their own devcontainer. **The project is Linux-only (UC-27)** — the operator scripts are POSIX bash; the prior PowerShell mirrors were removed.
- **value_proposition:** Zero-prompt autonomous Claude in a disposable Linux (glibc/Debian) container, persisted across detach/reattach via `tmux`, set up with a single guided wizard, and protected against secret leaks by `gitleaks` running at two layers (host pre-commit and container-wide). The container is the trust boundary, so `--dangerously-skip-permissions` is acceptable. Differentiates on **Simpler**, **More autonomous**, and **Safer** versus running Claude on the host or building a bespoke devcontainer.
- **maturity_target:** MVP — usable by early adopters in the wider community; the maintainer accepts issues and PRs but does not promise SLAs.
- **in_scope:**
  - A self-contained Docker image (Debian/glibc `node:20-bookworm-slim` base + Node + Claude Code + tmux + gitleaks + gh + git + ssh).
  - A guided `setup.sh` wizard that handles SSH key, image build, optional `gh` login, Claude `/login`, the dev-tools capability selection (UC-27), and start.
  - `attach.sh` thin wrapper around `tmux attach -t main` for detach/reattach.
  - `clean.sh` destructive reset path with explicit confirmation.
  - Two-layer gitleaks secret-scan protection (host pre-commit and container-wide git hook).
- **non_goals:**
  - Not a multi-user platform or shared service.
  - Not a cloud or SaaS deployment of Claude.
  - Not a packaged Claude IDE, editor extension, or GUI.
  - Not a hardened security product — the trust boundary is "a Linux (glibc/Debian) container under the user's Docker daemon," not a VM or microVM.
  - Not a CI/CD orchestrator for Claude.
- **success_criteria:**
  - A new user can clone the repo, run `setup.sh` once, and end up with a fully autonomous Claude running locally.
  - After initial setup, attaching to or detaching from Claude is a single command and never loses session state.
  - Any commit Claude makes (in the host repo or in any cloned project inside the container) is scanned by gitleaks before it lands.
  - Audience: wider community (public, MIT-licensed); contributions welcome but not required.

## Technologies

The project now spans three co-equal stacks: the original shell + Docker container layer that hosts Claude, the host-resident **Java/Spring Boot management server** introduced by UC03 (`use-cases/03-mtls-java-management-server.md`), and the **Android client** introduced by UC04 (`use-cases/04-android-client.md`). All three ship from the same repo. The container side and the Java server are released together; the Android client is released on its own tag stream.

- **constraints:**
  - Must run on a Linux host via Docker — no cloud, no SaaS. **UC-27: the project is Linux-only.** The operator scripts are POSIX bash; macOS and Windows/WSL2 may work but are not a supported target.
  - Operator-facing scripts are **POSIX bash only** — UC-27 removed the PowerShell (`.ps1`) mirrors and the parity requirement.
  - Container must be self-contained: no host tooling required beyond Docker, a shell, and (optionally) `pre-commit` for contributors of this repo.
  - The Java management server requires **host OpenJDK 21+** at install time on Linux hosts that run the service. The project ships a **fat jar**, not a bundled JRE; the operator is responsible for installing a JDK via their package manager. Windows and macOS hosts can run the container stack without a JDK; the systemd service itself is Linux-only.
  - The Android client targets **`minSdk = 29`** (Android 10) with the latest stable `compileSdk` and `targetSdk` at build time. It is built from the same Gradle multi-project as the server (`./gradlew :android:…`) and distributed as a signed APK + AAB through a separate `android-vX.Y.Z` tag stream — never bundled into the server release zip.
- **runtimes:**
  - Host: Docker (any version supporting Compose v2) + a POSIX shell (bash). Linux hosts that run the management server additionally need OpenJDK 21+ on the host (no JVM inside the container).
  - Container: **Debian (glibc) — `node:20-bookworm-slim` base for every session (UC-27; was Alpine/musl pre-UC-27).** The single glibc base lets opt-in toolchains (notably the Android emulator's QEMU) run without a build-time libc flip.
  - In-container processes: Node.js (from the `node:20-bookworm-slim` base) hosting `@anthropic-ai/claude-code`; `tmux` keeping the Claude session alive across detach/reattach. `rtk` (Rust Token Killer) sits on the PATH as a passive CLI proxy invoked by Claude's Bash hook to compress command output before it reaches the LLM — no daemon process.
  - JVM (host): a single long-running JVM 21 process under `systemd` running the Spring Boot server jar; a short-lived JVM invocation when the operator runs the `aisandboxctl` companion jar for PKI / client-mint / revoke / list / **invite** operations.
  - Android: Android 10+ (`minSdk = 29`) on phone and tablet (`≥600 dp` width triggers split-pane). One signed APK + AAB per `android-vX.Y.Z` release.
- **languages:**
  - Bash — operator scripts (`setup.sh`, `spawn.sh`, `attach.sh`, `clean.sh`), the dev-tools selector (`devtools-select.sh`, `devtools-ui.sh`) and capability manifests (`devtools.d/`), `entrypoint.sh`, the in-container capability helpers (`container-bin/aisandbox-{dind,java,android,emulator}`), and system-wide git hooks. **No PowerShell (UC-27 — Linux-only).**
  - Dockerfile — `SandboxDockerfile` that builds the `ai-context:latest` image (single glibc/Debian base).
  - **Java 21 LTS** — Spring Boot management server and the `aisandboxctl` companion CLI; both live under `ai-sandbox/server/` and build with the same Gradle multi-module project.
  - **Kotlin (latest stable at build time)** — the Android client under `ai-sandbox/android/`, written entirely in Kotlin with Jetpack Compose. No Java sources in the Android module.
- **frameworks:**
  - **Spring Boot** (latest stable at implementation time) for the management server — `spring-boot-starter-web`, `spring-boot-starter-security`, `spring-boot-starter-actuator`, `spring-boot-starter-validation`, and `spring-boot-starter-websocket`. No other web framework.
  - **Jetpack Compose** (Compose BOM at the latest stable at build time) for the Android client's entire UI layer. **Material 3 Expressive baseline**, dark theme only, mono-warm accent default per the Claude Design handoff bundle (see Android subsection below). No XML layouts.
- **key Java libraries (prose only — no frontmatter field):**
  - **springdoc-openapi** — runtime generation of the OpenAPI 3.x spec served at `/v1/openapi.yaml` and dumped to `server/openapi.yaml` at build time; CI fails on drift.
  - **Bouncy Castle** (or JDK-native equivalents) — PEM parsing and PKCS#12 emission for `aisandboxctl client mint` and for on-redemption cert minting in the UC04 `POST /v1/enrollment` endpoint.
  - **Picocli** (or Spring Boot's CLI runner) — argument parsing for the `aisandboxctl` companion jar; choice deferred to the dev-team but must match the prevailing convention of the chosen Spring Boot release line.
- **Android subsection (UC04):**
  - **Language + UI:** Kotlin + Jetpack Compose, Material 3 Expressive baseline. Dark theme only — the color token table in UC04 (`use-cases/04-android-client.md` § Theming) is the authoritative palette. Mono-warm accent (`#ece6ec`) is the default; alternate accent swatches are operator-selectable design variations, not runtime-configurable.
  - **Typography:** Roboto Flex (sans, primary UI) + JetBrains Mono (all session IDs, fingerprints, connection metadata, terminal output, and any code-shaped string). System fallbacks `Roboto`, `system-ui`, `ui-monospace`.
  - **Terminal renderer:** Termux's `TerminalView` (Apache 2.0, vendored as a Gradle dependency) wraps the WebSocket binary stream. Handles ANSI / xterm 256-color + true-color, scrollback, and tmux's status line. The Compose layer hosts the `TerminalView` inside an `AndroidView` interop wrapper.
  - **Networking:** TLS 1.3 with mTLS using the Android KeyStore-resident client cert as the sole TLS identity; server cert is **pinned** to the SHA-256 fingerprint received during QR enrollment. REST via OkHttp (or equivalent — final choice is the developer's), WebSocket via the same client with the mandatory subprotocol `ai-sandbox.v1`.
  - **Background work:** a `dataSync` foreground service (Android 14+ aware) keeps the WebSocket alive across lock screen and task switch. No `WorkManager`, no Firebase, no Crashlytics, no analytics SDKs — UC04 AC29 explicitly forbids them.
  - **Design source of truth:** the Claude Design handoff bundle is committed to the repo under `<TARGET_DIR>/design/android-ui/` (see `design/android-ui/README.md` and `design/android-ui/index.html`). The dev-team agents reproduce the visual specification in Compose; they do **not** copy the prototype's React/HTML structure. Screens UC04-1 (QR onboarding) through UC04-7 (cert-revoked dialog) are the canonical screen inventory; the Theming color token table is the canonical palette; the iconography list is the canonical icon set.
- **data_stores:** none. The container side keeps state in three bind mounts (`workspace/`, `secrets/` read-only, `claude-config/`). The Java server keeps trust state on disk under `/etc/ai-sandbox-server/` (allowlist folder of client certs + server cert + config YAML + the new UC04 enrollment-token folder `/var/lib/ai-sandbox-server/enrollment/`) and audit state under `/var/log/ai-sandbox-server/`. The Android client persists only the imported client key in the Android KeyStore and the pinned server fingerprint + URL in app-private storage. **Enrollment-token files are short-lived filesystem state, not a data store.** No relational, document, key-value, or vector store.
- **auth_strategy:**
  - **Container side (unchanged):** Git over SSH using a user-supplied private key copied into `secrets/git-key`; bind-mounted read-only into the container at `/etc/secrets/git-key` and copied to `~/.ssh/git-key` by the entrypoint. Optional `gh` CLI auth via a token in `secrets/gh-token`; entrypoint runs `gh auth login --with-token` on boot if present. Claude Code `/login` performed once in a disposable container during setup; persisted to `claude-config/` (bind-mounted to `~/.claude/` in the container).
  - **Management server (UC03):** mutual TLS against a **folder-of-allowed-client-certs (fingerprint allowlist)** at `/etc/ai-sandbox-server/clients/`. No CA, no IdP, no password. Server cert + private key live under `/etc/ai-sandbox-server/pki/`. Both directories are filesystem-watched and hot-reload without restart. All valid client certs are equal-authority admins for this MVP; identity is logged per call (CN for display, SHA-256 fingerprint for audit).
  - **Android enrollment (UC04):** token-based bootstrap. The operator runs `aisandboxctl client invite <name>` on the server host to generate a 10-min single-use token; the token + server URL + server cert pin are encoded into one QR. The Android app scans the QR, POSTs `{"token": "..."}` to the new `POST /v1/enrollment` endpoint (the **only** mTLS-exempt path on the server), receives a PKCS#12 bundle, imports the key into the Android KeyStore as non-exportable, and uses it as the sole TLS client identity for every subsequent call. Re-scanning a QR replaces the existing identity (one server profile at a time).

  - **GitHub** — git clone/push over SSH, `gh` CLI, `gh` API (`api.github.com` over HTTPS).
  - **Anthropic** — Claude Code authentication and API endpoints (used by `@anthropic-ai/claude-code`).

## Architecture

The architecture is now a three-tier composition: (a) the original container side — one Linux (glibc/Debian) container per Claude session, organised as a separate Docker Compose project `ai-sandbox-N` per UC02 — (b) a single host-resident **Java/Spring Boot management server** introduced by UC03, running as a `systemd` service outside any container, and (c) the **Android client** introduced by UC04, which is a downstream consumer of the server's REST + WebSocket surface (plus the new mTLS-exempt enrollment endpoint). The container tier and the server tier are deliverables of the same repo and the same release pipeline; the Android module is a deliverable of the same repo but its own release pipeline.

- **platforms:**
  - Desktop / CLI on the operator's host (**Linux** — UC-27 made the operator scripts bash-only; macOS / Windows-WSL2 may work but are not a supported target) — the container side as before.
  - **Host-resident systemd service** on Linux for the Java management server. Exposes a single TLS port (default **12410**, bound to all interfaces by default) carrying both an HTTP/2 REST API (`/v1/*`) and a WebSocket endpoint (`wss://host:12410/v1/sessions/{n}/stream`, subprotocol `ai-sandbox.v1`).
  - **Android (phone + tablet)** for the UC04 client. Sideloaded signed APK; no Play Store distribution today. Tablet split-pane at `≥600 dp`; phone is single-pane.
  - Nothing is published to a web or browser-extension surface in this repo — those clients are deferred to a later use case and will consume the same REST + WebSocket surface.
- **service_shape:**
  - **Container tier:** single-container monolith *per Compose project*. Each `ai-sandbox-N` runs one Compose service (`claude-sandbox`) from one glibc/Debian image (`ai-context:latest`). UC02 turned the historical singleton into a fleet, but each member is still a monolith inside its boundary.
  - **Host tier:** a single Spring Boot fat-jar process — the management server — plus the short-lived `aisandboxctl` fat-jar for PKI/admin tasks (including the new UC04 `client invite` subcommand). The server is a sibling to the containers, not embedded in any of them.
  - **Android tier:** a single-process Compose app. No services-talking-to-services within the app; the foreground `dataSync` service is an Android lifecycle construct, not a separate process.
  - Net shape: one Java server per host + N containers per host + the UC02 host scripts that the server invokes + zero-or-more Android clients per server. No services-talking-to-services pattern on the server side.
- **components:**
  - **Operator scripts (host)** — `setup.sh`, `spawn.sh`, `attach.sh`, `clean.sh` (POSIX bash; **no `.ps1` mirrors — UC-27 made the project Linux-only**). Wizard, multi-session spawn (UC02), tmux attach wrapper, destructive reset. All must support non-interactive flag-only invocation; `spawn.sh` accepts `--label <value>` setting `com.ai-sandbox.label` on the container (UC02 ACs 21–22, hard preconditions for UC03). **UC-27 — "Select the development tools you want to install" step.** `setup.sh` Step 6 (and `./setup.sh --reconfigure`) runs a **pure-shell raw-mode cursor checkbox selector** (`devtools-ui.sh`, driven from `devtools-select.sh`): one capability per line prefixed `[X]`/`[ ]`, arrow keys + mouse-wheel to move, Space to toggle, Enter to commit, q/Esc to cancel — no `whiptail`/`dialog` dependency, so the `.deb` TTY auto-onboard path works. Capabilities are **auto-discovered, sourced shell manifests** at `devtools.d/<id>/manifest.sh` (each declares `ID`, a version-bearing `LABEL`, `DEPENDS_ON`, optional `WARNING`, `APPLY_AT`, `ARCH`, plus `devtool_spawn_env` + `devtool_provision` hooks); adding a capability is dropping a directory. The catalog ships exactly three: **DinD** (rootless Docker-in-Docker), **Java 21** (Temurin JDK), and **Android SDK** (`DEPENDS_ON: [java]`, amd64-only; shown disabled on other arches). Selecting a capability auto-selects its transitive deps; deselecting a depended-on capability prompts and cascade-deselects on confirm. Selections persist to `./.ai-sandbox-devtools` (gitignored, `<id>\t<apply_at>` per line, byte-stable catalog order). Toolchains are **provisioned eagerly at spawn** (not baked into the image); new sessions get the current selection, already-running ones are unaffected (recycle to retrofit). The old `.ai-sandbox-toolchains` ledger and the UC-22 Android `[Y/n]` prompt are retired (merged into this selector; no migration).
  - **`docker-compose.dind.yml` + `container-bin/aisandbox-dind` (UC-26)** — the spawn-time and in-container halves of the DinD capability. `spawn.sh` reads `.ai-sandbox-devtools` and, when `dind` is enabled, appends `docker-compose.dind.yml` to `AI_SANDBOX_EXTRA_COMPOSE_FILES` and exports `AI_SANDBOX_DEVTOOL_DIND=1`. The override adds `/dev/fuse` passthrough, `apparmor:unconfined` + `seccomp:unconfined` (rootless dockerd requires both), and re-publishes the env var into the container. Inside the container, `entrypoint.sh` runs `aisandbox-dind install` + `start` when the env var is set: a one-time fetch of the static rootless-Docker tarball from `download.docker.com` into `/workspace/environment-utilities/dind/` (cached afterward), then `dockerd-rootless.sh` in the background bound to `/run/user/<uid>/docker.sock`. The helper carries `install / start / stop / doctor / selftest` subcommands; `selftest` is the load-bearing AC-9 fixture (alpine compose-up → `tmux -V` exec → compose-down). The client attaches over the **same mTLS `wss://host:12410/v1/sessions/0/stream` WebSocket** as any Claude session — the only difference is the bridge runs a bare local `tmux attach` instead of `docker compose exec`. The host tmux persists across detach/disconnect/app-restart (existence derives from `tmux has-session`, re-listed on every enumeration) and is destroyed **only** when the client removes the row (`DELETE /v1/sessions/0` → `tmux kill-session`). **Security posture:** this host shell is a deliberate, accepted **crossing of the container trust boundary** that is the project's core value proposition — it grants an enrolled client a shell on the host, not inside a sandbox container. It is an operator convenience, gated by `ai-sandbox.server.server-ssh.enabled` (default `true`); set it `false` to suppress the feature (the row is never listed and the create endpoint no-ops). It rides the existing mTLS-pinned transport, so reachability is still bounded by client-cert enrollment — no additional network attack surface beyond the already-authenticated WebSocket channel.

- **data_flow_narrative:**
  - **Local operator flow (unchanged):** operator runs a host script → `docker compose -p ai-sandbox-N` boots `claude-sandbox` from `ai-context:latest` → entrypoint hydrates auth and starts `tmux main` → Claude runs inside `/workspace` (host's `./workspace/` by default per UC02) and reaches out to GitHub/Anthropic → operator attaches via `docker compose exec`.
  - **Dev-tools selection flow (UC-27):** operator runs `./setup.sh` (Step 6) or `./setup.sh --reconfigure` → the raw-mode cursor selector (`devtools-ui.sh`) reads the pre-existing `./.ai-sandbox-devtools`, renders the auto-discovered manifest catalog with the inline trust-boundary `WARNING` shown at the moment of selection, resolves dependencies, and writes the updated ledger back (byte-stable catalog order). On the next `./spawn.sh`, `lib.sh`'s generic `inject_devtool_spawn_env` reads the ledger, sources each enabled capability's manifest, runs its `devtool_spawn_env` hook (exports per-capability env + layers the matching compose override — `docker-compose.dind.yml` for DinD, `docker-compose.kvm.yml` for Android when `/dev/kvm` is present), and exports `AI_SANDBOX_DEVTOOLS=<ids>` into the container. The new compose project boots; `entrypoint.sh` then runs the **generic capability dispatch loop** — for each enabled id (deps-first) it sources the manifest and runs `devtool_provision` (DinD → `aisandbox-dind install`+`start`; Java → `aisandbox-java install`; Android → `aisandbox-android install`), then loads each capability's `env.sh` into the entrypoint's environment **before** `tmux new-session` so Claude and every non-login `sh -c` child inherit `JAVA_HOME`/`ANDROID_HOME`/`PATH` (the AC#10 PATH fix). A readiness marker is written after tmux is up; `spawn.sh` polls it so attach tolerates the provisioning window. Already-running sessions are not retrofitted — they keep their pre-toggle configuration until recycled.
  - **Remote operator flow (unchanged from UC03):** a remote client (CLI today; Android via UC04) terminates TLS at the Java management server on port 12410, presenting a client cert that must match a file in `/etc/ai-sandbox-server/clients/`. For management calls, the client hits `/v1/sessions`, `/v1/clients`, `/v1/healthz`, etc.; the server validates the request, dispatches Docker-touching operations to the UC02 scripts (`spawn.sh`, `clean.sh`, or the `docker compose ls` enumerate), captures stdout/stderr, and replies as JSON or `application/problem+json`. For terminal sessions, the client upgrades to `wss://.../v1/sessions/{n}/stream` with subprotocol `ai-sandbox.v1`; the server allocates a per-client tmux session inside container N (`tmux new-session -t main`), pipes WebSocket binary frames in/out as raw tty bytes, and translates text frames (`resize`/`mouse`/`error`/`close`) into tmux commands. Multiple concurrent clients can attach to the same container — each gets independent sizing via its own tmux client.
  - **Android enrollment flow (UC04, new):** operator runs `aisandboxctl client invite <name>` on the server host → CLI generates a single-use ≥256-bit token + writes `{token, name, exp}` to `/var/lib/ai-sandbox-server/enrollment/<token-prefix>.json` (mode 0600) + prints a QR encoding `{u, t, exp, pin}` (server URL, token, expiry, server cert SHA-256 fingerprint) → operator shows the QR to the device → Android scans, pins the server cert against `pin`, POSTs `{"token": t}` to `<u>/v1/enrollment` over TLS (no client cert) → server validates the token (exists, not expired, not redeemed), atomically deletes the token file (`Files.deleteIfExists`, single-use), mints an RSA-2048 client cert via BouncyCastle, writes the public cert into `/etc/ai-sandbox-server/clients/` (so `AllowlistWatcher` picks it up), and returns 201 `application/octet-stream` carrying the `<name>.p12` bundle (sentinel passphrase `ai-sandbox-enrollment` per UC14 — not a secret; required because BouncyCastle 1.79 rejects empty char[] during PBKDF2 unwrap) → Android imports the key into the Android KeyStore as non-exportable, destroys the in-memory PKCS#12, and is now authorized for every subsequent mTLS call. Re-scanning a QR replaces the existing identity; the old KeyStore entries are deleted before importing new ones.
  - **Audit / log flow:** every authenticated request and every stream open/close emits one JSON Lines entry to stdout (captured by journald) and, for audit-tagged events (`spawn`, `kill`, `attach-open`, `attach-close`, `client-cert add/remove`, `server-cert rotation`, `healthz-fail`, plus UC04's `enrollment-issued`, `enrollment-redeemed`, `enrollment-rejected`), an additional line to `/var/log/ai-sandbox-server/audit.log` (app-managed daily rotation, 7-day retention).
- **trust_boundaries:**
  - **Container-as-sandbox.** Each container is still a trust boundary. Claude runs as the non-root `claude` user inside the Linux (glibc/Debian) container and can only see the host through its bind mounts. `--dangerously-skip-permissions` remains acceptable because the grant is bounded by Linux user perms + Docker isolation.
  - **`secrets/` is read-only.** The shared `:ro` bind mount means even an autonomous Claude cannot rewrite the SSH key or `gh` token in place — though it can read them, and via SSH it has the same authority over remote git as the operator.
  - **gitleaks at two layers.** Host pre-commit (this repo's contributors) and container-wide system hook (every commit Claude makes inside any container). Both pinned to gitleaks 8.21.0 and must move together.
  - **Java management server is a host-level network attack surface.** Port 12410 is bound to **all interfaces** (`0.0.0.0` and `::`) by default. mTLS against the folder-of-allowed-client-certs is the **sole** authentication gate for every endpoint **except** `POST /v1/enrollment`; no plaintext fallback, no anonymous TLS elsewhere, no opt-out. TLS 1.3 only, explicit cipher allowlist. A misconfigured host firewall could expose the port to a hostile network; the README and `docs/THREAT_MODEL.md` both call this out and recommend host-level firewalling regardless.
  - **`POST /v1/enrollment` widens the trust boundary (UC04).** This endpoint is the **only** mTLS-exempt path on the server. It exists because mTLS clients have to bootstrap their cert somehow, and a single-frame QR is the chosen bootstrap channel. The mitigations are layered: (a) **single-use tokens** with **≥256 bits of entropy** (no brute-force window); (b) **10-min default expiry** (configurable down); (c) **per-IP rate limit** (1 redemption per 60 s by default); (d) **64 KiB / 256-byte body cap** (returns 413 over); (e) **on-redemption cert minting** (an unredeemed/expired token leaves no cert behind, so the allowlist never bloats from issued-but-unused invites); (f) **token file mode 0600** in a 0700 directory owned by `ai-sandbox-server`; (g) **TLS still required** even though mTLS is not, so the token never crosses the wire in cleartext. The flag is explicit: this is a deliberate trust-boundary widening accepted as a UC04 design tradeoff, captured in `docs/THREAT_MODEL.md` (UC04 AC36). A future revision may move enrollment behind a separate operator-only mTLS-gated bootstrapping channel, but that adds operator burden today.
  - **`docker` group is a privilege boundary.** The server runs as `ai-sandbox-server`, a non-root user in the `docker` group. Anyone with code execution inside the server process can typically escape to host root via `/var/run/docker.sock`. mTLS (and on the enrollment path, the rate-limited single-use-token gate) are the only layers between the network and that capability; the Java code must keep every unauthenticated path closed except the one well-defined enrollment endpoint. `/v1/healthz` is mTLS-gated for exactly this reason.
  - **Server private key at rest = plain PEM 0600.** Stored at `/etc/ai-sandbox-server/pki/`, owned by `ai-sandbox-server`. Mode 0600 is the protection. `docs/THREAT_MODEL.md` flags this for future review (passphrase-protected key + EnvironmentFile passphrase as the planned upgrade path).
  - **Android KeyStore as the device-side trust anchor (UC04).** The imported client private key is stored in the Android KeyStore, hardware-backed when the device supports it, and marked non-exportable. The original PKCS#12 transport bundle is discarded immediately after import and never written to durable storage on the client. The pinned server fingerprint + URL live in app-private storage; loss of the device = revoke that cert on the server (`aisandboxctl client revoke <name>`).
  - **Per-client tmux isolation.** The WebSocket endpoint runs `tmux new-session -t main` per stream, so client window sizes and mouse state are independent. The underlying `main` session is still shared — concurrent clients see the same Claude conversation — and that is intentional. Revoking a cert tears down its in-flight WebSocket within ≤ 1s of the allowlist watch reload.
  - **No inbound network surface on the container tier.** Compose projects publish no ports; containers are reachable only via `docker compose exec` (from the operator at the host console or from the Java server via the UC02 scripts).
  - **Bind-mount dirs are not project source.** `workspace/`, `secrets/`, and `claude-config/` are runtime state owned by the operator/Claude — they are excluded from `paths.production` so the dev-team never edits them.
  - **RTK as a CLI proxy on the PATH, not a new trust boundary.** `rtk` is a passive binary at `/usr/local/bin/rtk` invoked by Claude's Bash hook. It runs in-process as the `claude` user; it does not add inbound surface or change isolation properties. The supply-chain note for `rtk-ai/rtk` GitHub Releases (build-time fetch, rolling-latest, no checksum) is the relevant risk.
  - **Rootless Docker-in-Docker (UC-26) — deliberate, opt-in widening of the per-session boundary.** When the operator selects the `dind` devtool in the setup wizard, spawned sessions layer `docker-compose.dind.yml` on top of the base compose: `/dev/fuse` is passed in (fuse-overlayfs needs it), `apparmor:unconfined` and `seccomp:unconfined` are set on the session container (rootless dockerd's nested mounts + namespaces collide with the default profiles otherwise), and `entrypoint.sh` starts a rootless `dockerd-rootless.sh` inside the session bound to `/run/user/<uid>/docker.sock`. The host docker socket is **never** mounted in — `--volume /var/run/docker.sock` is absent — so the **host** trust boundary is unchanged. The **per-session** boundary, though, is intentionally widened: code in a DinD-enabled session can now launch and inspect containers via its own rootless daemon, and the relaxed AppArmor/seccomp profiles give it slightly more room to maneuver than the default session has. The wizard surfaces this tradeoff inline at the moment of selection (UC-26 AC#3), README documents it (AC#10), and disabled / never-selected sessions are byte-identical to today's behaviour (AC#6). The capability is delivered as an in-session rootless daemon only — UC-26 deliberately does **not** deliver host-daemon visibility from inside the session, and there is no opt-in flag for that today.
- **multi_tenancy:** still **not applicable**. There is one operator, one host, one fleet of containers, one Java server. The Java server supports **multiple authenticated clients concurrently** — but they are all the same operator coming in from different devices (laptop + mobile + a second laptop). All valid client certs are equal-authority admins in this MVP; the server does not partition state per client. UC04's "one server profile at a time" rule applies at the **Android-device** level (one cert per device, one server URL stored at a time), not at the server level.

### Android-client subsection (UC04)

- **Module location:** `<TARGET_DIR>/android/` — a new Gradle subproject rooted at the existing top-level Gradle build, sharing the wrapper with `:server`.
- **Trust boundary:** the Android app consumes exactly one UC03 server, identified by URL + pinned server cert fingerprint baked into the QR. It has **one** mTLS identity (the cert imported during enrollment) and no other egress: no analytics, no telemetry, no third-party SDK, no Firebase, no Crashlytics (UC04 AC29). Outbound traffic is only to the configured server's port 12410.
- **REST consumption:** the standard UC03 endpoints — `GET /v1/sessions` (returning the per-session `status` field, value set `running | starting | provisioning | stopped | terminating`; the UC-27 `provisioning` value marks a container that is up but still installing its spawn-time toolchains, surfaced in the app as the amber "installing…" pill, and the UC-28 `terminating` value marks a session whose teardown is in progress — delete confirmed / in-flight — surfaced as the red "terminating" pill), `POST /v1/sessions`, `DELETE /v1/sessions/{n}`, `GET /v1/clients`, `GET /v1/healthz` — all over mTLS with the KeyStore-resident client cert and the pinned server cert.
- **WebSocket consumption:** `wss://<host>:12410/v1/sessions/{n}/stream` with mandatory subprotocol `ai-sandbox.v1`. Binary frames are raw tty bytes piped into the Termux `TerminalView`; text frames are JSON control (`resize`/`mouse`/`error`/`close`) per `server/STREAM_PROTOCOL.md`. Mouse gestures (drag-to-resize-pane, long-press-as-right-click, two-finger-drag-as-wheel) and rotation/keyboard resize events emit `resize` and `mouse` frames within 200 ms of the trigger.
- **Design source of truth:** the Claude Design handoff bundle, committed under `<TARGET_DIR>/design/android-ui/` (see `design/android-ui/README.md` and `design/android-ui/index.html` — referenced, not re-rendered in this brief). The Compose implementation reproduces the visual specification (Theming token table, screen inventory UC04-1 through UC04-7, component family, iconography) — it does **not** copy the prototype's React/HTML structure.
- **`POST /v1/enrollment` — the only mTLS-exempt path:** the bootstrapping endpoint that lets an Android device acquire its first mTLS identity. Trust-boundary-widening flag = **explicit and deliberate**. Mitigations recapped: single-use cryptographic tokens (≥256 bits, hex-encoded), 10-minute default expiry, per-IP rate limit (1/60 s default, configurable, returns 429 `enrollment_rate_limited`), 256-byte payload cap (returns 413 `payload_too_large` over), on-redemption cert minting (no cert ever pre-exists on disk for an unredeemed token), token-file mode 0600 in a 0700 directory owned by `ai-sandbox-server`, and TLS still required even though mTLS is not. Re-keying an existing client is **explicitly not** a use case for this endpoint — revocation flow is delete-from-allowlist + new `client invite` + re-scan on the device. `docs/THREAT_MODEL.md` carries a new section documenting this widening (UC04 AC36).
- **QR-token bootstrap (high level):** operator runs `aisandboxctl client invite <name>` on the server host → CLI emits a single QR encoding `{u, t, exp, pin}` (≈200 bytes, well within a v3 QR's capacity) → operator points the Android camera at the QR → app pins the server cert against `pin`, POSTs `{"token": t}` to `<u>/v1/enrollment` → server validates + atomically deletes the token + mints + writes-to-allowlist + returns the PKCS#12 bundle in the response body → app imports the key into the Android KeyStore (non-exportable, hardware-backed when supported), destroys the in-memory bundle, and transitions to the sessions list. Re-scanning replaces the existing identity in one prompt; one server profile at a time.

- `paths.api_boundary`: `["server/src/main/java/**/api/**"]` — recorded as a hint for the dev-team. The exact final package convention (`api/`, `controller/`, or `web/`) is the developer's call during `/develop`; the dev-team may refine this glob once the package layout is settled. The Android module has no analogous `api/` boundary today — it is a single-app artifact with no public Java/Kotlin API surface.

Quality bar now spans three stacks: the original shell + Docker container layer (unchanged, still no formal harness — operator-aware behavior is the contract), the Java/Spring Boot server layer introduced by UC03 (real tests, lint, and CI), and the Android client introduced by UC04 (its own lint, JVM tests, and a separate CI workflow, but explicitly **no instrumented tests in CI** as a deliberate cost tradeoff).

The Spring Boot ecosystem aligns on google-java-format in modern setups; this also matches the `profile-java-server-architecture` opinion baseline. The dev-team may not deviate without an explicit brief amendment.

A future revision may add a ktlint or detekt plugin if machine-enforced formatting is wanted.

  - Bash: none configured today (shellcheck/shfmt remain reasonable future additions).
  - Dockerfile: none configured today (hadolint remains a reasonable future addition).

Autoformat with `./gradlew :server:spotlessApply`; CI-enforced with `./gradlew :server:spotlessCheck` (the `server-ci.yml` workflow fails the PR on violations). Spotless is the single source of truth for Java formatting — no IDE-specific config takes precedence.

(A ktlint or detekt plugin remains a reasonable future addition if machine-enforced Kotlin formatting is wanted.)

- **testing:**
  - **levels:** `unit`, `integration`. Unit tests cover pure Java logic on the server (request/response mapping, allowlist parsing, problem-json shaping, control-frame JSON, enrollment-token validation/expiry/single-use semantics) and pure Kotlin logic on the Android side (state-holder / ViewModel logic, WebSocket frame parsing, retry/backoff math, KeyStore-import wrappers around fake `java.security` providers). Integration tests cover the full server boot + TLS + REST + WebSocket + `POST /v1/enrollment` surface against disposable certs and a real Docker daemon via Testcontainers. **No instrumented (`androidTest`) tests run in CI** — see CI section below.

No bats/Pester on the shell side.

Coverage tooling (Jacoco for Java, Kover for Kotlin) may be added later if the operator wants a gate; the dev-team should not add it unilaterally without a brief revision.
  - **CI:** `.github/workflows/server-ci.yml` runs `./gradlew :server:spotlessCheck :server:test` on every PR touching `server/**` and on every merge to `main`. Failures block merge. **`.github/workflows/android-ci.yml`** (new in UC04) runs `./gradlew :android:lint :android:test :android:assembleDebug :android:bundleDebug` on every PR touching `android/**` and on every merge to `main`. Failures block merge. The Android CI **does NOT run instrumented tests** (`:android:connectedAndroidTest`, `:android:connectedDebugAndroidTest`) — Compose UI tests require a device or emulator, GitHub Actions emulator setup is slow + flaky + a significant cost driver, and UC04 is sideload-only-for-two-users (developer + partner). The trade-off is explicit: in exchange for fast PRs and zero emulator cost, instrumented tests are operator-run on a connected device pre-release. The shell/Dockerfile side has no CI today.
- **security:**
  - **Secret scanning — host layer.** `.pre-commit-config.yaml` invokes gitleaks v8.21.0 via the [pre-commit](https://pre-commit.com/) framework before commits land in this repo. Contributors install with `pip install pre-commit && pre-commit install`.
  - **Secret scanning — container layer.** `SandboxDockerfile` installs gitleaks 8.21.0 and configures a system-wide git pre-commit hook (`git config --system core.hooksPath /etc/git-hooks`) that scans every commit Claude makes in any cloned project inside the container. To allowlist a finding, drop a `.gitleaks.toml` in the affected repo's root; to bypass for a single commit, `git commit --no-verify` (used sparingly).
  - **Pinning discipline.** Both gitleaks layers are pinned to the same version; bumping requires updating `.pre-commit-config.yaml` and the `GITLEAKS_VERSION` build arg in `SandboxDockerfile` together.
  - **Container hygiene.** Non-root `claude` user inside the image; no published ports in `docker-compose.yml`; `secrets/` bind mount is `:ro`.
  - **Management-server authentication = mTLS only (except enrollment).** UC03's Java server (host, systemd) terminates a single TLS port (12410) and is gated by mutual TLS against a folder-of-allowed-client-certs at `/etc/ai-sandbox-server/clients/`. TLS 1.3 only; explicit cipher allowlist; no plaintext fallback. UC04 introduces a single mTLS-exempt path (`POST /v1/enrollment`) gated by single-use tokens + per-IP rate limit + body cap (see Architecture § "trust_boundaries"). All valid certs are equal-authority admins for MVP; identity = CN (displayed) + SHA-256 fingerprint (audited). Revocation = delete from allowlist; in-flight connections torn down on the next watch reload (≤ 1s).
  - **At-rest server key.** Plain PEM 0600 at `/etc/ai-sandbox-server/pki/`, owned by `ai-sandbox-server`. Mode 0600 is the protection. Flagged for future review (passphrase-protected key + EnvironmentFile passphrase as the planned upgrade path) — see `docs/THREAT_MODEL.md`.
  - **Enrollment-token store (UC04).** Single-use tokens live as `<token-prefix>.json` files at mode 0600 inside `/var/lib/ai-sandbox-server/enrollment/` (mode 0700, owned by `ai-sandbox-server`). Tokens carry ≥256 bits of entropy (hex-encoded). Lifetime: 10 min default, configurable via `--ttl`. Redemption is atomically followed by `Files.deleteIfExists` (POSIX-atomic) inside a `synchronized` block on the enrollment service, so two concurrent redemptions of the same token cannot both succeed.
  - **Android KeyStore (UC04).** Client private key imported into the Android KeyStore as non-exportable, hardware-backed when the device supports it. The in-memory PKCS#12 transport bundle is destroyed immediately after import; nothing is ever written to app-external storage. Server cert SHA-256 pin + server URL persist in app-private storage. Loss of the device → operator revokes via `aisandboxctl client revoke <name>` + issues a new `client invite` + re-scan on the replacement device.
  - **Android distribution security (UC04).** Release APK + AAB are signed with a v2/v3-scheme key whose passphrase comes from a GitHub Actions secret (`ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_PASSWORD`) and whose keystore is provided to the workflow as a base64-encoded secret (`ANDROID_KEYSTORE_BASE64`) or fetched from `~/.gradle/keystore.jks` on a self-hosted runner. **Signing-key backup discipline is mandatory** — losing the key means the partner's already-installed APK can never be updated (Android refuses APKs signed by a different key); the operator README and `docs/THREAT_MODEL.md` must document the recovery path (re-key + new install on every device).
  - **Audit log.** `/var/log/ai-sandbox-server/audit.log` (JSON Lines, app-managed daily rotation, 7-day retention, no size cap) captures: spawn, kill, attach-open, attach-close, client-cert add, client-cert remove, server-cert rotation, healthz-fail, plus UC04's `enrollment-issued` (on `client invite`), `enrollment-redeemed` (on successful `POST /v1/enrollment`), and `enrollment-rejected` (on token-invalid / token-expired / token-redeemed / rate-limited / payload-too-large). Same lines also flow to journald with an `audit=true` field. No secret material is ever logged (no private keys, no full PEM bodies, no passwords, no PKCS#12 bodies, no full enrollment tokens — only token-prefix for correlation).
  - **Threat-model document.** **`docs/THREAT_MODEL.md`** is a committed deliverable, produced by UC03's `/develop` run and **extended by UC04's `/develop` run** with a new section covering the enrollment trust boundary (single mTLS-exempt path, single-use token semantics, rate limiting, the operator's responsibility to keep `/var/lib/ai-sandbox-server/enrollment/` tight, the explicit non-goal of using the endpoint for re-keying existing clients, and the deliberate decision to widen the trust surface to bootstrap mTLS rather than to require a separate operator-only bootstrapping channel). The original container-tier risks (SSH key reachable by Claude, outbound network to GitHub/Anthropic, shared host kernel) remain documented informally in the README; this brief does not commit to expanding the threat model to cover them at this time.
  - **No dependency scanner today.** No `npm audit` / `pip-audit` / Trivy / Snyk wired up on the container side. **Note:** Spring Boot is a large dependency surface (UC03 explicitly accepts this risk); transitives expand the CVE-watch footprint. The Android side adds another large surface (AGP, Compose BOM, Termux `TerminalView`); same accepted risk. The CI workflows building on every PR are the only automatic feedback channel today — Dependabot / Renovate / Snyk are reasonable future additions but not committed.
  - **No SAST today.**
  - **Docker-group privilege boundary.** The `ai-sandbox-server` user is a member of the `docker` group; anyone with code execution inside the server process can typically escape to host root via `/var/run/docker.sock`. mTLS (and on the enrollment path, the rate-limited single-use-token gate) are the only authentication layers; the Java code must keep every unauthenticated path closed except the one well-defined enrollment endpoint. Accepted risk, documented in `docs/THREAT_MODEL.md`.
- **accessibility_target:** not applicable to the CLI surfaces (operator scripts, `aisandboxctl`) and the mTLS REST/WebSocket API — they have no UI. The Swagger UI shipped at `/v1/swagger-ui` is for API discovery only and is mTLS-gated; not a user-facing product surface. **The Android client (UC04) does not set a committed accessibility target either** — it is a sideload-for-two-users tool, not a public product; Compose's defaults (TalkBack content descriptions on every interactive composable, system text-scale honored, system dark/light is N/A because dark is forced) are the floor and the dev-team should not regress them, but no formal WCAG level is in scope. Note for future revision: if the Android client ever moves to Play distribution, Google's policies (and a real a11y target) become binding.

Image build time, `attach` latency, REST p95, WebSocket throughput, stream open-time, and Android startup latency are all operator-perceived but no formal budget is set. ## Profiles

This project opts into the following profile skills. Per `CLAUDE.md`'s precedence rules, the brief always wins; active profiles apply where the brief is silent; model defaults are the final fallback.

- **`profile-java-server-architecture`** — opinionated Java server conventions: Gradle (latest stable), Spring Boot (latest stable), Java (latest LTS, here pinned to 21); repositories return DTOs (never JPA entities); internal DTOs never cross the API boundary (the controller layer has its own request/response DTOs); strict Controller/Job → Facade → Service → Repository call chain with **transactions owned by the facade**. The dev-team must follow this layering when implementing the management server under `server/src/main/java/**`. The repositories-return-DTOs rule applies even though there is no data store today — if the dev-team introduces persistent state during implementation, it must comply.
  - **Active exception (UC06 § AC25)** — **install-time CLI commands** under `server/src/main/java/com/aisandbox/server/cli/**` are exempt from the Controller/Facade/Service/Repository layering. Picocli subcommands like `pki init` and `secrets seed` are thin shells that run root checks, do file I/O, and shell out to container tools (`docker`, `ssh-keygen`, `gh`, `claude`). Forcing them through a four-layer DI graph adds Spring weight without buying any of the layering's safety properties (no transactions, no repositories, no API boundary). Step helpers under `cli/secrets/` (`SshKeyStep`, `GhTokenStep`, `ClaudePreInitStep`, …) keep the per-step logic testable via injected `ProcessRunner` / `ConsoleIO` seams, but they are not Services in the profile's sense and don't need to be. Server *runtime* code (`api/`, `service/`, `facade/`, `sessions/`, `enrollment/`) remains fully bound by the profile.
- **`profile-java-call-graph-tool`** — provisions the [java-class-call-scanning](https://github.com/HaroldHormaechea/java-class-call-scanning) bytecode call-graph analyzer for the dev-team. The `develop` skill's Step 3b downloads the latest release jar to a per-user cache and writes an MCP server entry to `<TARGET_DIR>/.mcp.json`; agents use the nine query operations (`find-callers`, `find-callees`, `methods-in-class`, `methods-at-line`, `find-field-readers`, `find-field-writers`, `impact-of-diff`, `tests-for-diff`, `refresh-index`) either through MCP tools or against the cached jar.

## Deployment

Deployment now spans three co-located targets that share a repo and a single Gradle wrapper but split into two release pipelines: the **container tier** + the **Java management server tier** ride `server-vX.Y.Z` tags as before (the server-tier additions from UC04 — `POST /v1/enrollment` and `aisandboxctl client invite` — roll out by cutting a new `server-vX.Y.Z` release), and the **Android client tier** (UC04) ships on its own `android-vX.Y.Z` tag stream as a signed APK + AAB attached to a GitHub Release. The shell/Dockerfile side remains clone-and-build.

### Production

- **hosting:** the operator's own host machine (Linux for the full feature set; macOS and Windows can still run the container tier but **not** the systemd-managed Java service). No cloud, no PaaS, no managed runtime. The "production environment" is whatever Docker daemon the operator has installed, plus — on Linux — a host OpenJDK 21+ runtime and `systemd`. A dedicated non-root system user **`ai-sandbox-server`** (member of the `docker` group) owns the Java service process. The Android client runs on the operator's personal device(s) — sideload-only today (no Play Store distribution).
- **cloud:** none.
- **iac:**
  - **Container tier:** `docker-compose.yml` + `SandboxDockerfile` are the entire infrastructure surface for the per-session containers. No Terraform, no Pulumi, no CDK. **Image versioning (UC-38):** the runtime tag stays `ai-context:latest`, but each build stamps the **server package version** onto the image as the OCI label `com.ai-sandbox.image-version` (`SandboxDockerfile`'s `ARG IMAGE_VERSION`, defaulting to `dev`; the build passes `docker compose build --build-arg IMAGE_VERSION=<version>`). Staleness is read from that **label** (via `docker image inspect`), never the tag. `aisandboxctl onboard --rebuild-image` forces an image-only rebuild on demand, and a `.deb` **upgrade** rebuilds the image synchronously in `postinst` when the installed label differs from the new package's version (guarded so it never fails/hangs the install). Fresh installs keep the lazy build-on-first-use behaviour.
  - **Java server tier:** a `systemd` unit file (`ai-sandbox-server.service`) is shipped alongside the server fat jar. Hardening directives include `NoNewPrivileges=true`, `ProtectSystem=strict`, `ProtectHome=true`, `PrivateTmp=true`, `RestrictAddressFamilies=AF_INET AF_INET6 AF_UNIX`, `Restart=on-failure`, `RestartSec=5s`, `StartLimitBurst=5`, `StartLimitIntervalSec=60s`, `WantedBy=multi-user.target` (UC03 §3). A sample `config.yaml` (server-side YAML at `/etc/ai-sandbox-server/config.yaml`) is shipped beside the unit file. No higher-level IaC tool.
  - **Android client tier:** none. The "infrastructure" is the operator's device; install is a manual sideload of the signed APK.
- **ci_cd: GitHub Actions.** Four workflows live in `.github/workflows/`:
  - **`server-ci.yml`** — runs on every PR touching `server/**` and on every merge to `main`. Executes `./gradlew :server:spotlessCheck :server:test` (which exercises unit + Testcontainers integration tests, UC03 §45–46). Failures block merge.
  - **`server-release.yml`** — triggered by version tags matching `server-vX.Y.Z` (UC03 §47). Builds the server fat jar, builds the `aisandboxctl` fat jar (including the new UC04 `client invite` subcommand), regenerates the springdoc OAS (which now includes `POST /v1/enrollment`), and emits **a single release zip** containing: the two jars, `server/openapi.yaml`, the systemd unit file, the sample `config.yaml`, and a release README. Modelled after the `java-class-call-scanning` project's release flow; no intermediate artifacts are published (no per-module jars, no plugin Maven repository). **UC04's server-side additions (`POST /v1/enrollment` + `aisandboxctl client invite`) ride this same pipeline** — the operator MUST cut a new `server-vX.Y.Z` release as part of UC04's roll-out, separately from any `android-vX.Y.Z` release, so the device-side flow has a live server to enroll against.
  - **`android-ci.yml`** (UC04) — runs on every PR touching `android/**` and on every merge to `main`. Executes `./gradlew :android:lint :android:test :android:assembleDebug :android:bundleDebug`. The debug assemble + bundle steps are included on PR to catch packaging breakage early, but the artifacts are not attached anywhere (the release workflow re-builds and signs the release variants separately). **No instrumented tests** — emulator cost + flakiness on GitHub Actions is the explicit trade-off; the developer + partner run smoke tests on real devices pre-tag. Failures block merge.
  - **`android-release.yml`** (UC04) — triggered by version tags matching `android-vX.Y.Z`. **Modelled on `server-release.yml`.** Builds `:android:assembleRelease` + `:android:bundleRelease` with the production signing config (keystore + key passwords sourced from GitHub Actions secrets — see "secrets" below), attaches the signed APK + AAB to the GitHub Release for that tag, and includes a release notes scaffold. Does **not** publish to Play Internal Testing today (deferred — see "distribution" below). Cutting a release is `git tag android-vX.Y.Z && git push --tags`, independent of any server tag.
- **distribution:**
  - **Container tier (unchanged):** source on GitHub at `https://github.com/HaroldHormaechea/ai-sandbox`. Operators clone, run `./setup.sh` (Linux), and get a local container. The image (`ai-context:latest`) is built locally on each operator's host — not published to any registry.
  - **Java server tier (unchanged):** **tag-driven release zip** published as a GitHub Release asset by `server-release.yml`. The operator downloads the zip from the GitHub Releases page, unpacks it, installs the jars/unit/config to their target paths, and starts the service via `systemctl enable --now ai-sandbox-server`. Clone-and-build via `./gradlew :server:bootJar` still works for contributors. UC04's server-side changes (`POST /v1/enrollment` + `aisandboxctl client invite`) ship in this same zip; rolling them out is a normal `server-vX.Y.Z` release.

Sideload-for-two is the deliberate v0.1 choice given UC04 AC29's strict "no telemetry / no SDK that phones home" rule and the absence of a public-product use case.
- **environments:** a single `local` environment per operator. There is no dev/staging/prod split — there is no shared deployment target. The Java server runs in the same single environment as the containers. The Android client targets the same operator's single server profile (one URL + one pinned fingerprint stored on the device at a time).
- **secrets:**
  - **Container tier (unchanged):** host-side `secrets/` folder (gitignored, `.gitkeep` placeholder), bind-mounted read-only into each container at `/etc/secrets`. Holds `git-key` (SSH private key) and optional `gh-token`. The operator places these via the setup wizard (`setup.sh` step 1 for SSH; step 3 for `gh auth login` writing to `gh-token`). No external secrets manager — the host filesystem with `0600` perms is the entire policy.
  - **Java server tier (UC03 + UC04 + UC06):** all material lives under `/etc/ai-sandbox-server/`:
    - `pki/server.crt` + `pki/server.key` — server cert and **plain PEM private key at mode 0600**, owned by `ai-sandbox-server`. `docs/THREAT_MODEL.md` flags the at-rest key for future review (passphrase-protected key + EnvironmentFile as the planned upgrade path).
    - `clients/<name>.crt` — one file per allowed client cert; folder at mode 0750. This **is** the trust anchor for mTLS; no CA. Filesystem-watched for hot reload; revocation = delete the file.
    - `enrollment/<token-prefix>.json` (UC04) — single-use enrollment tokens (≥256-bit entropy, hex-encoded), each `{token, name, exp}` at mode 0600 inside the `enrollment/` folder (mode 0700, owned by `ai-sandbox-server`). Lifetime: 10-min default. Redemption atomically deletes the file; expiry is checked on read.
    - `secrets/git-key` + `secrets/gitconfig` + (optional) `secrets/gh-token` (**UC06**) — container-tier credentials bind-mounted RO into every spawned session at `/etc/secrets/`. Captured by `aisandboxctl secrets seed`, which walks the operator through four steps (SSH key → git identity → gh PAT → Claude pre-init), each driven by CLI flags so the same command runs unassisted under Ansible / cloud-init (`--no-gh` / `--no-claude-preinit` opt out of optional steps). The SSH key is **decrypted at install time** (passphrase stripped via `ssh-keygen -p`) so the container can use it non-interactively; the operator's host key is never modified. All three files at mode 0600, owned `ai-sandbox-server`.
    - `templates/claude-config/` (**UC06**) — snapshot of `~/.claude/` captured during a one-off interactive OAuth session, RO bind-mounted into every spawned session at `/etc/claude-template/`. `entrypoint.sh` copies it into `~/.claude/` exactly once per session (gated by `~/.claude/.seeded`) so new sessions inherit logged-in Claude state. Operators can override per-session with `claude /login` inside the running container; respawns lose the override. Folder mode 0750, owned `ai-sandbox-server`. Empty / absent template (deployments using `--no-claude-preinit`) makes the seeding `cp` a no-op.
    - **Refresh path** — `aisandboxctl secrets seed --force` re-runs all four steps and overwrites every output. There is no per-credential refresh shortcut: expiring `gh` tokens, rotated SSH keys, and re-authenticated Claude sessions all go through the same `--force` re-run. Already-running sessions don't pick up new templates (the `.seeded` marker holds); operators must kill + respawn affected sessions.
    - `config.yaml` — server config at mode 0644 (port, paths, caps, timeouts, plus UC04's enrollment-rate-limit + token-TTL settings).
    - All artifact types are generated/managed by the `aisandboxctl` companion jar (`pki init`, **`secrets seed`** (UC06), `client mint`, `client revoke`, `client list`, `client invite`). No external secrets manager.
  - **Android client tier (UC04, new):**
    - **On-device:** the imported client private key lives in the **Android KeyStore**, hardware-backed when supported, non-exportable. The pinned server fingerprint + URL persist in app-private storage. The PKCS#12 transport bundle is destroyed after import; nothing else is persisted.
    - **CI signing config:** the release signing keystore (`~/.gradle/keystore.jks` on the operator's machine; mirrored as `ANDROID_KEYSTORE_BASE64` GitHub Actions secret) plus two passphrase secrets (`ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_PASSWORD`) feed `:android:bundleRelease` and `:android:assembleRelease` in `android-release.yml`. Debug builds use the standard Android debug keystore (no secrets needed). **Signing-key backup discipline is mandatory and operator-owned** — losing the key means Android will refuse every future update on every installed device, forcing a full uninstall + new install with a different signing identity. The operator must keep an offline backup (e.g. an encrypted USB drive) of the original `keystore.jks` and the password material; the README and `docs/THREAT_MODEL.md` both call this out as the highest-impact distribution risk for the Android tier.
- **observability:**
  - **Container tier (unchanged):** `docker compose logs claude-sandbox` is the only window into container behavior. No metrics, no tracing, no aggregation.
  - **Java server tier (unchanged from UC03; UC04 audit events added):** operational logs as **JSON Lines on stdout**, captured by journald via the systemd unit. Audit-tagged events additionally written to `/var/log/ai-sandbox-server/audit.log` (JSON Lines, app-managed daily rotation, 7-day retention, no size cap), now including `enrollment-issued` / `enrollment-redeemed` / `enrollment-rejected`. No metrics endpoint in MVP, no tracing, no APM. `/v1/healthz` is mTLS-gated like every other endpoint.
  - **Android client tier (UC04):** local-only logging; no remote sink; no analytics; no Crashlytics. The operator uses `adb logcat` for diagnostics on a connected device.
- **dr:** none — state remains the operator's responsibility:
  - `workspace/*` (cloned project work, per UC02 shared-by-default), `workspace-<N>/` (per-N isolated overlay if used), `claude-config/` (Claude `/login` state) — backed up by the operator's host backup strategy.
  - `secrets/` — operator-supplied SSH key + optional `gh-token`; the operator maintains the source of truth.
  - **PKI material** under `/etc/ai-sandbox-server/pki/` and the client allowlist under `/etc/ai-sandbox-server/clients/` — the operator backs these up (or accepts that a loss means rotating via `aisandboxctl pki init` + reissuing client bundles via `aisandboxctl client mint` or `client invite`).
  - **Enrollment-token store** under `/var/lib/ai-sandbox-server/enrollment/` — ephemeral by design; no backup needed (tokens expire in 10 min and are single-use).
  - **Android signing key** (`keystore.jks` + passwords) — operator-owned offline backup is **mandatory**; losing it forces a re-key + new install on every device.
  - The container images, jars, and systemd unit are all rebuildable from a git tag, so no DR plan beyond "preserve the operator's host-side state, the source repo, and the Android signing key" is required.

### Development

- **environment:** four relevant audiences:
  - **End-user / operator (container tier):** the container *is* the dev environment for whatever Claude is working on. The host needs only Docker + a shell.
  - **Contributor to this repo — shell/Dockerfile side:** edit `.sh` / `devtools.d/` manifests / `container-bin/` helpers / `SandboxDockerfile` / `entrypoint.sh` natively on the host; validate with `docker compose build` and a fresh `setup.sh` run. Install `pre-commit` (`pip install pre-commit && pre-commit install`) so the host gitleaks scan fires before every commit.
  - **Contributor to this repo — Java server side:** edit under `server/` natively; install OpenJDK 21+ via the host package manager. Iterate with:
    - `./gradlew :server:test` — unit + integration tests. **Requires a working Docker daemon on the contributor host** because Testcontainers spins up real containers during integration tests.
    - `./gradlew :server:spotlessApply` — autoformat; `./gradlew :server:spotlessCheck` — verify (same command CI runs).
    - `./gradlew :server:bootJar` — build the server fat jar.
    - Local end-to-end run: generate dev PKI with `aisandboxctl pki init` against a scratch directory, mint a dev client cert with `aisandboxctl client mint dev` (or use `aisandboxctl client invite dev` to test the UC04 path end-to-end), then `java -jar server/build/libs/server-*.jar --spring.config.location=file:./config.yaml` pointed at the scratch PKI + clients dirs.
  - **Contributor to this repo — Android client side (UC04):** edit under `android/` natively; install the Android SDK (command-line tools + platform-tools + an SDK platform matching the current `compileSdk`) via Android Studio or `sdkmanager`. JDK 21 from the server-side install is the same JDK Gradle uses for the Android build. Iterate with:
    - `./gradlew :android:test` — JVM unit tests.
    - `./gradlew :android:lint` — Android lint (AGP); Kotlin formatting is via Android Studio / the IDE (no ktlint plugin configured).
    - `./gradlew :android:lint` — Android lint.
    - `./gradlew :android:assembleDebug` — produces a debug-signed APK installable on a developer device via `adb install`.
    - `./gradlew :android:connectedAndroidTest` — runs the Compose UI / instrumented tests on a connected device or emulator. **Not run in CI**; the developer is expected to run this locally before tagging a release.
- **containerization:**
  - Container tier: required and central — the per-session product **is** a container; there is no non-containerized mode for the Claude side.
  - Java server tier: **not** containerized. The Java server runs as a host-resident JVM process under systemd, deliberately outside any container, so it can drive Docker via the UC02 host scripts and watch host filesystem paths (`/etc/ai-sandbox-server/`) directly. Running it in a container would re-introduce the very abstraction it must escape.
  - Android client tier (UC04): **not** containerized — the build runs on the contributor's host JDK + Android SDK, and the artifact runs on a real Android device.
- **hot_reload:**
  - Container tier: not applicable. The container runtime is `tmux` running Claude in a while-loop; iterating on the image itself requires `docker compose down && docker compose build && docker compose up -d` (or just `./clean.sh` then `./setup.sh`).
  - Java server tier: Spring Boot DevTools is permitted in the contributor inner loop (re-runs on classpath changes) but is **off by default for the production fat jar** and never enabled in the systemd-deployed binary. UC03 explicitly hot-reloads only TLS materials and the client allowlist via filesystem watches; everything else is restart-only. UC04 adds no new hot-reload paths.
  - Android client tier (UC04): **Compose Live Edit / Live Literals** are available in Android Studio for the inner loop but are not a deployment construct — they only apply when running a debug build from the IDE. No production hot reload (Android does not have one).
- **seed_data:**
  - Container tier: none. Operator-supplied (`secrets/git-key`, optional `secrets/gh-token`, the project that gets cloned into `/workspace`).
  - Java server tier: none. Trust state is the operator's PKI material; there is no data store to seed. UC04's enrollment-token store is also ephemeral and not seeded.
  - Android client tier (UC04): none. Initial state is "no server profile, no client identity"; the QR enrollment flow is the first-run experience.
- **migrations:** not applicable. None of the three tiers has a data store or schema.
