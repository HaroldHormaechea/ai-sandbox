# Use Case 36: Android terminal — conversational keyboard (word input + autocompletion), not char-by-char, without dropping commands

## Summary
On the terminal screen the on-screen keyboard is stuck in **char-by-char ("single key") mode**: there is no word prediction, no suggestion strip, and no autocompletion, which makes typing prose to a conversational agent (e.g. talking to Claude in the session) tedious. The cause is explicit: `AiSandboxTerminalViewClient.shouldEnforceCharBasedInput()` returns a hardcoded `true` (`android/src/main/kotlin/com/aisandbox/android/ui/components/TerminalSurface.kt:85`). The vendored `TerminalView.onCreateInputConnection` (`terminal-view/src/main/java/com/termux/view/TerminalView.java:307-339`) branches on that flag: when `true` it sets `InputType.TYPE_TEXT_VARIATION_VISIBLE_PASSWORD | TYPE_TEXT_FLAG_NO_SUGGESTIONS` (suppresses suggestions/autocorrect → the current behavior); when `false` it uses `InputType.TYPE_NULL`. Neither path gives a normal word-prediction + autocomplete experience: `NO_SUGGESTIONS` disables it outright, and `TYPE_NULL` makes most IMEs fall back to dumb key events with no composing/suggestions either. The user wants the keyboard to behave like a **normal text field — word input, prediction, and autocompletion — so they can converse naturally**, while the terminal must **still deliver every command intact ("not drop commands")**: committed/autocompleted/autocorrected text must reach the PTY in full and in order, and control input (Ctrl/Esc/arrows/Tab/Enter/Backspace via the `ModifierBar`) must keep working. This is the well-known terminal-vs-IME tension (termux deliberately disabled suggestions because composing-text + PTY echo can duplicate or drop characters), so the UC must solve conversational input **without** corrupting the byte stream.

## Acceptance Criteria

1. When typing into the terminal, the OS keyboard shows its normal **word prediction + suggestion strip and autocompletion** (the conversational experience), instead of the current char-based / no-suggestions mode.
2. **No dropped or reordered input.** Any committed text — a plain word, an accepted suggestion, or an autocorrected word — is delivered to the PTY in full and in the order typed. A representative command (e.g. `ls -la /tmp` then Enter) arrives at the remote shell exactly as composed and executes correctly; rapid typing does not lose characters.
3. **Composing text is reconciled with PTY echo** so the user does not see duplicated or ghost characters: while a word is being composed locally, the final committed bytes are sent once on commit (space/punctuation/suggestion tap/Enter), and the terminal's rendering (driven by server echo) stays correct. No visual double-typing.
4. **Autocorrect must not silently change a command.** Either autocorrect is constrained so it cannot mangle CLI tokens (paths, flags, `cd`, `git`, etc.), or the design makes corrections only apply to clearly word-like input — the user’s typed command must never be transformed into a different command without their action. (Resolve how aggressive correction is; "not drop commands" includes "not corrupt commands".)
5. **Control input still works** unchanged: the `ModifierBar` Ctrl/Alt/Esc/arrow/Tab keys still emit the correct control sequences, Enter sends CR (`\r`), and Backspace deletes one char on the PTY — verified to coexist with the new word-based InputConnection (`TerminalView.java` `commitText`/`setComposingText`/`deleteSurroundingText`/`sendKeyEvent` paths).
6. **Shell-side Tab completion remains usable** via the Tab modifier (it sends `\t` to the PTY) — distinct from IME autocomplete; both coexist.
7. If the two modes genuinely cannot be unified for all workflows, provide a **toggle** (a Settings option and/or a ModifierBar affordance) between "Conversational" (words + autocomplete, the new default the user asked for) and "Raw/char" (today's behavior, best for heavy CLI control), persisted across sessions — but the conversational mode must satisfy AC#1-6 on its own, not merely fall back to raw.
8. No regression to UC-21 (terminal), UC-23 (IME insets / keyboard occlusion), or UC-24/UC-33 (rendering): the keyboard change must not reintroduce input occlusion or break the agent-switcher/terminal rendering. Covered by the Compose/instrumented tests under `:android:connectedDebugAndroidTest` plus a focused test of the InputConnection byte delivery.

## Potential Pitfalls & Open Questions
- **Echo duplication (the core hazard).** A PTY echoes typed characters back; if the IME also keeps a local composing region, the user can see each character twice or see stale composition. Termux chose `NO_SUGGESTIONS`/`TYPE_NULL` precisely to avoid this. The fix must define how composing text is committed to the PTY and how local composition is cleared so server echo is the single source of truth — likely committing on word boundaries and calling `finishComposingText()` aggressively.
- **Dropped bytes under composing.** Some IMEs send `setComposingText` then `commitText`; a naive InputConnection that only forwards key events (the `TYPE_NULL` path) drops the composed word entirely. The implementation must forward `commitText` content to the PTY, not rely on `sendKeyEvent` alone.
- **Autocorrect corrupting commands.** Gboard/Samsung may "correct" `grep` → `Greg`, capitalize the first letter of a line, or insert smart quotes (`"` → `“`) that the shell mis-parses. This directly violates "not drop commands". Consider disabling autocorrect while keeping prediction, or scoping correction. Resolve explicitly.
- **Keyboard fragmentation.** The vendored code already notes Samsung-stock and Gboard quirks with `TYPE_NULL` and `shouldEnforceCharBasedInput`. The new mode must be validated on at least Gboard (emulator default); document behavior on others rather than assuming uniformity.
- **Newlines & multi-line.** `IME_FLAG_NO_FULLSCREEN` is set and `IME_ACTION_NONE` is avoided so Enter inserts a newline; ensure Enter still maps to sending CR to the PTY (run the command) rather than inserting a literal newline into a composing buffer.
- **Where the flag lives.** `shouldEnforceCharBasedInput()` is a single boolean on the client; a real toggle needs state plumbed from a setting/VM into `AiSandboxTerminalViewClient`, and `TerminalView` must be told to recreate its InputConnection (`restartInput`) when the mode changes mid-session.
- **Verification.** Emulator instrumented tests can drive the InputConnection (commitText/composing) and assert PTY bytes; live "feel" (suggestions actually appearing) is best confirmed on the booted emulator with Gboard via the `android-testing`/`android-emulator-setup` skills.
