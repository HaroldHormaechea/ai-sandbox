# Use Case 13: Android client adopts BouncyCastle for PKCS#12 enrollment-cert import

## Summary

The Android client cannot import freshly-minted enrollment PKCS#12 bundles from `server-v0.0.12` because the server emits PKCS#12 v3 / PBES2 (PBKDF2 + AES — the modern JDK 21 default for `KeyStore.getInstance("PKCS12")` since Java 14+) and Android's stock PKCS12 provider (Conscrypt + Android's stripped-down `"BC"` provider) does not register a `SecretKeyFactory` under the bare PBKDF2 OID `1.2.840.113549.1.5.12`. Empirical proof on potato-server + phone on 2026-05-21 after the v0.0.12 deploy and a fresh QR: `import_failed Cannot import client cert: exception unwrapping private key - java.security.NoSuchAlgorithmException: 1.2.840.113549.1.5.12 SecretKeyFactory not available`. The fix is Android-side only: add the real BouncyCastle (`org.bouncycastle:bcprov-jdk18on`) as a JCE provider registered under a distinct project-specific name (`BC-ai-sandbox-client`) so the stock `"BC"` provider is left untouched, and route ONLY the PKCS#12 unwrap through it explicitly. Server stays on modern PBES2 (the deliberately-strong format) — no regression to legacy SHA1+3DES. Conscrypt remains the TLS provider for hardware acceleration. Tradeoff accepted: APK size delta (~3-5 MB) + BC CVE-tracking burden, in exchange for preserving PBKDF2-HMAC-SHA256 + AES-256 end-to-end. Ships paired with UC-12 as `server-v0.0.13` + `android-v0.3.0` (minor bump because BC is a new dependency that changes the JCE-provider surface).

## Acceptance Criteria

1. **Phone imports successfully.** The Android client imports a v0.0.12+ PBES2 PKCS#12 emitted by the actual server code path; the post-import success path runs (cert usable for subsequent mTLS requests; no `import_failed` toast/screen).

2. **Real-context import test.** A new Android test (instrumented or JVM-side with proper KeyStore wiring) imports a real server-emitted PBES2 PKCS#12 fixture (generated by the server's actual `KeyStore.getInstance("PKCS12")` code path — generated by a test helper that runs the same minting logic, NOT a hand-rolled fixture) and asserts: (a) import succeeds; (b) extracted private key byte-equals the source key; (c) extracted X.509 cert byte-equals the source cert.

3. **BC provider registered under `BC-ai-sandbox-client`.** The real BouncyCastle is registered under the distinct provider name `BC-ai-sandbox-client` so it does not collide with Android's stock `"BC"` provider (which other system or library code may expect to behave as the stripped-down stock version). PKCS12 KeyStore lookup explicitly targets it: `KeyStore.getInstance("PKCS12", "BC-ai-sandbox-client")`. The integration choice is documented in a code comment and in the PR body.

4. **Conscrypt unaffected.** A test asserts that Conscrypt is still the registered TLS provider after BC is added (e.g., asserts the provider for `SSLContext.getInstance("TLS")` is unchanged). The TLS handshake and the UC-09 / UC-10 SPKI cert-pinning code path continue to work without regression.

5. **SPKI pinning regression test passes.** UC-09 and UC-10 Android tests stay green; the BC provider does not interfere with the pinning code path (the analyst confirms no shared crypto-provider state during proposal review).

6. **Call sites updated.** `android/src/main/kotlin/com/aisandbox/android/net/EnrollmentClient.kt` and any other PKCS#12 import site in the Android module pass the BC provider name explicitly. A negative test (lint rule, ArchUnit equivalent, or grep-based assertion in CI) ensures no enrollment-path code still calls `KeyStore.getInstance("PKCS12")` without an explicit second-argument provider name.

7. **BC dependency pinned.** `android/build.gradle.kts` adds `org.bouncycastle:bcprov-jdk18on:<version>` with a fixed version (NOT a version range, NOT `latest.release`). PR body records: the chosen version, a one-line note on the CVE check performed at pin time (e.g. "no open CVEs in this version as of 2026-05-21 per nvd.nist.gov"), and the renewal cadence intent.

8. **Server unchanged.** `git diff main...HEAD` shows no production-code changes under `server/` — the server's PKCS#12 emission stays on modern PBES2 PBKDF2 + AES.

9. **CI green.** `:android:test`, `:android:lint`, `:android:assembleRelease`, `:android:bundleRelease`, `:server:test`, `:server:spotlessCheck`, `release-install-smoke` (including UC-11's systemd-driven enrollment-write leg now passing through UC-12's routing fix — this UC depends on UC-12 being in the same release), `android-ci` all pass.

10. **Release.** Ships paired with UC-12 as `server-v0.0.13` AND `android-v0.3.0` (minor bump because BC is a new dependency and the JCE-provider surface changes). Release notes call out: the new Android BC dependency, the unchanged server crypto, and the explicit reasoning ("server stays on modern PBKDF2-AES; Android gets the real BC because Conscrypt's stock provider doesn't recognize the bare PBKDF2 OID; alternative was server-side regression to SHA1+3DES, which was rejected for crypto-strength reasons").

11. **Test-first cascade.** QA writes the failing import test (AC2) against current Android `main` BEFORE the developer adds BC. Pre-fix failure pattern (`NoSuchAlgorithmException: 1.2.840.113549.1.5.12`) captured in the test summary; developer's change flips it green.

12. **Documentation.** `android/README.md` (or the Android-side doc surface, per the brief's `## Documentation` section if it names one) records: the BC dependency presence, the `BC-ai-sandbox-client` provider name, and a one-liner on why ONLY the PKCS12 path uses it (i.e. "TLS continues through Conscrypt for hardware acceleration; BC is reserved for the enrollment cert import").

13. **ProGuard / R8 keep-rules.** Whatever Android shrinker rules apply to release builds explicitly keep BC's provider classes so minification doesn't strip them. Verified by an assembleRelease run and a `unzip -l <apk>` (or equivalent) check that BC classes survive in the final APK / AAB.

## Potential Pitfalls & Open Questions

- **Risk** — APK size delta. BC adds roughly 3-5 MB to the Android APK. PROJECT_BRIEF.md has no formal APK size budget, so the analyst confirms with the user in the proposal whether the delta is acceptable. If not, fallback considerations (split APKs per ABI, BC-light artifact, server-side fallback) need to be discussed before implementation.

- **Risk** — Provider-priority footgun. BC's TLS provider could accidentally win for TLS if registered at high priority. Mitigation: register at lowest priority via `Security.addProvider` (which appends), or use `Security.insertProviderAt` at a position that does NOT displace Conscrypt. AC4's Conscrypt assertion is the gate that catches this.

- **Risk** — Stock `"BC"` provider stability. Future Android system updates may change the stock `"BC"` provider's behavior or add PBES2 support natively. Mitigation: AC3's distinct-name strategy (`BC-ai-sandbox-client`) decouples this project from stock-provider changes; AC4's Conscrypt-assertion plus AC5's pinning regression test catch any silent drift.

- **Edge case** — minSdk 29 (Android 10). The BC integration must work on the project's API floor. Verify via an instrumented test on an SDK-29 emulator, or document explicitly in the PR body if CI doesn't run an SDK-29 emulator (acceptable per the brief's mvp maturity target as long as the constraint is recorded).

- **Edge case** — Android 14+ Conscrypt may add PBES2 `SecretKeyFactory` registrations natively in a future Android release. If so, BC becomes redundant on newer SDKs. The integration should NOT block on this — keep BC for the bottom of the supported range and revisit when minSdk rises.

- **Edge case** — ProGuard / R8 stripping. AC13 covers this; analyst confirms the exact `-keep` rule shape (or its R8 equivalent) during proposal review.

- **Edge case** — `assembleRelease` / `bundleRelease` arch coverage. BC is pure-Java (no native code), so multi-arch should be a no-op, but a CI step must confirm the BC classes land in every emitted APK / AAB variant.

- **Risk** — UC-12 dependency order. UC-13's `release-install-smoke` test (AC9) only passes end-to-end if UC-12's WebFlux routing fix is in the same release — otherwise the smoke step would still see HTTP 500 on the enrollment path before the import is even attempted. Develop UC-12 first, OR develop them in parallel branches and merge UC-12 before UC-13. Decision deferred to the analyst at integration time, but the dependency is real and must be flagged in the proposal's risks section.

## Original Description

PKCS#12 / Android crypto compatibility — when the Android client receives a freshly-minted enrollment p12 from `server-v0.0.12` (or any server JVM emitting modern PBES2 PKCS#12), it fails to import with `import_failed Cannot import client cert: exception unwrapping private key - java.security.NoSuchAlgorithmException: 1.2.840.113549.1.5.12 SecretKeyFactory not available`. Empirical evidence from potato-server + Android phone on 2026-05-21 immediately after UC-11's v0.0.12 deploy and after regenerating a fresh QR (so the upstream UC-12 routing bug was not the cause). OID `1.2.840.113549.1.5.12` is PBKDF2. The server emits PKCS#12 v3 / PBES2-encrypted bodies (PBKDF2 + AES, the modern JDK 21 default for `KeyStore.getInstance("PKCS12")` since Java 14+). Android's stock PKCS12 KeyStore implementation (Conscrypt + Android's stripped-down "BC" provider) does NOT register a `SecretKeyFactory` under the bare PBKDF2 OID — providers register under named algorithm strings like `PBKDF2WithHmacSHA256`. So when Android tries to look up the SecretKeyFactory by OID during private-key unwrap, no provider answers and the import fails.

User's chosen fix: option (3) — Android adds the real BouncyCastle (`org.bouncycastle:bcprov-jdk18on`) as a JCE provider and uses it explicitly for the PKCS12 unwrap, instead of the server downgrading to legacy PKCS#12 v1 (SHA1+3DES) or stripping the password. Rationale recorded earlier: this is the most crypto-modern path (server stays on PBES2 PBKDF2-HMAC-SHA256 + AES-256), avoids FIPS-deprecated 3DES, and aligns with the project's "as secure as possible" target. Tradeoff accepted: app gets a multi-MB BC dependency and the team takes on BC CVE tracking; the integration must register the real BC under a distinct name (not Android's stripped-down "BC" provider) and route ONLY the PKCS12 unwrap through it (not TLS — Conscrypt stays the TLS provider for hardware acceleration).

Known footguns the analyst MUST address:
1. Android already ships a stripped-down provider named "BC" — you cannot just `Security.addProvider(new BouncyCastleProvider())` and assume it wins. Either register it under a distinct provider name or call `Security.removeProvider("BC")` BEFORE adding the real one. Either way, the PKCS12 KeyStore lookup must explicitly target the real BC, not the stock provider.
2. TLS must NOT be routed through BC — Conscrypt provides hardware-accelerated AES/AEAD on Android and any regression there would be a perf hit. The BC provider must be added at a position that doesn't displace Conscrypt as the TLS provider.
3. PKCS12 unwrap call sites in `EnrollmentClient.kt` (and anywhere else cert imports happen) must be updated to pass the BC provider explicitly: `KeyStore.getInstance("PKCS12", "BC-fips-or-whatever-name-we-registered")`.
4. Conscrypt version compatibility — check that adding BC at a lower priority doesn't break Conscrypt's TLS handshake or cert validation path.
5. Coexistence with the existing SPKI pinning (UC-09 / UC-10) — the cert-pinning code path must continue to work; this UC touches the import path, not the pinning path, but the analyst confirms no shared crypto-provider state.

Test gap to close: an Android instrumented test (or JUnit test with the Android KeyStore mock) that imports a real server-emitted PBES2 PKCS#12 (test fixture generated by the same server-side code path) and asserts: (a) import succeeds; (b) the resulting private key is the one the server minted (byte-compare against the test fixture); (c) Conscrypt is still the registered TLS provider after BC is added (i.e., the integration did not displace Conscrypt by accident).

Server side: NO changes. The server's `KeyStore.getInstance("PKCS12")` output stays on modern PBES2 PBKDF2 + AES; this is the deliberately-strong format.

Ships paired with UC-12 as `server-v0.0.13` AND a new Android tag (`android-v0.2.1` or whatever the convention dictates). The Android side is the actual fix; the server tag is bundled for release distribution efficiency.

Cross-cutting:
- Release notes call out the new BC dependency on the Android side and the unchanged server crypto.
- `android/build.gradle.kts` adds the BC dependency.
- Existing UC-04 / UC-09 / UC-10 Android tests should continue to pass.

## Clarifications

- Q: How should the real BouncyCastle be registered on Android (to avoid colliding with the stock `BC` provider)?
  A: Register under a distinct project-specific provider name `BC-ai-sandbox-client`. The stock `"BC"` provider is left untouched so anything else on the device that expects the stripped-down stock behavior continues to work. PKCS12 KeyStore lookup uses `KeyStore.getInstance("PKCS12", "BC-ai-sandbox-client")`.
- Q: What Android tag should accompany the `server-v0.0.13` release?
  A: `android-v0.3.0` — minor bump because BC is a new dependency and the JCE-provider surface changes; more conservative semver than a patch bump given the new attack surface.
