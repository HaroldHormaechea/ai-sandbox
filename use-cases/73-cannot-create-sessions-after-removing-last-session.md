# Use Case 73: Bugfix — cannot create sessions after spawning then removing the only/last session

## Summary
Starting from zero sessions, the user creates a session (reported as "the ssh session" — i.e. the SERVER SSH SESSION host-shell row added in UC-62, reserved id `0`), then removes it, and afterwards can **no longer create any new session** — neither another server-ssh row nor a normal Docker session. A read-only code investigation could **not** reproduce this statically: every shared prerequisite that session creation depends on (the `tmux` socket and its parent `sessions/` dir, the `.ai-sandbox-counter`, per-session Docker compose projects/networks, and server-side spawn state) was verified to survive last-session removal — the tmux case was confirmed live (killing the only session leaves the parent dir intact and a subsequent `new-session` transparently recreates the server over the stale socket). Because the root cause is not yet pinned, this use case is **repro-first**: the dev-team must reproduce the failure against a live server with logs before scoping a fix, then fix the actual prerequisite that is destroyed-and-not-restored. The likely blast radius is the recent server-ssh lifecycle work (UC-62 create/remove via `HostShellSessionService`, UC-63 fresh-install provisioning, UC-64 `HOME` redirect), and the asymmetry between init-on-first-create and teardown-on-last-remove.

## Acceptance Criteria
1. **Reproduce first.** The team reproduces the failure on a live server and captures concrete evidence before changing code: the failing `POST /v1/sessions` (and/or `POST /v1/sessions/server-ssh`) HTTP status + response body, the relevant `audit.log` and `journalctl -u ai-sandbox-server` lines, `docker compose ls -a` output, and the contents/permissions/ownership of `/var/lib/ai-sandbox-server/sessions/` (counter file, any stale `server-ssh.sock`) immediately after the failure. The captured evidence is recorded in the PR.
2. If the bug reproduces, the **exact prerequisite** that last-session removal destroys (and that creation needs) is identified at `file:line`, and the fix restores symmetry — either stop destroying it on remove, or (re)provision it on next create — without breaking the UC-62 contract that the server-ssh `tmux` is destroyed only on explicit Remove.
3. After the fix, the full cycle works repeatedly: from zero sessions → create server-ssh → remove → create server-ssh again → succeeds; and from zero sessions → create server-ssh → remove → create a **normal Docker session** → succeeds. Verified at least twice in a row to rule out a one-shot.
4. No regression to the reserved-id guards: `n==0` (server-ssh) still intercepted in `SessionFacade` and never routed through `clean.sh`; `ScriptExecutorService.clean()` still refuses `n < 0`.
5. If, after a genuine live reproduction attempt, the failure **cannot** be reproduced, the team does not invent a speculative fix: it documents the negative result (what was tried, what the logs showed) and escalates so the maintainer can capture a real-world repro. Hardening that is clearly safe and on the suspected path (e.g. idempotent re-provisioning of the `sessions/` dir/socket on create) may still be applied with justification.
6. QA verifies on a live server (the existing server-test / DinD path), not solely by unit tests, because the suspected mechanisms are filesystem/tmux/Docker-runtime behaviours that mocked executors do not exercise.

## Potential Pitfalls & Open Questions
- **Could not reproduce from code** — Treat every "obvious" fix as a hypothesis until the live repro confirms it. The investigation already ruled out (live, for tmux) the most plausible mechanism, so a fix landed without a repro is likely wrong.
- **Risk** — Do NOT "fix" by having `HostShellSessionService.kill()` `rm` the socket or the `sessions/` directory: that dir is shared with the Docker-session host-state root and the counter; deleting it would itself break spawning. The fix direction is restore/keep, not delete.
- **Edge case** — The symptom "can no longer create sessions" may actually be a **504 spawn timeout** (`spawn-timeout-seconds`/`spawn-timeout`) from a slow first `compose build`/`up`, not a hard prerequisite loss. The repro must distinguish a hard error from a slow-spawn timeout (check status code + timing).
- **Edge case** — Operator's local `tmux` version may treat a stale socket left by `kill-session` of the only session differently than this host's; capture the operator's tmux version in the repro.
- **Assumption** — "the ssh session" = the UC-62 SERVER SSH SESSION (host-shell, reserved id 0), not a Docker session. Confirm during repro; if the user meant the first Docker session instead, re-scope to the Docker spawn/clean asymmetry.
- **Key files to start from** — `server/.../sessions/service/HostShellSessionService.java` (`ensureCreated`/`kill`), `server/.../sessions/facade/SessionFacade.java` (`createServerSsh`, `deleteSession` reserved-id interception), `server/.../sessions/service/ScriptExecutorService.java` (`clean` guard), `spawn.sh`, `clean.sh`, `lib.sh` (counter + lockdir), `server/debian/postinst` (sessions/ dir ownership/mode).
