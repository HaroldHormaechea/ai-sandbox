# Use Case 84: Hamburger menu + in-app server self-update

## Summary
On the Android sessions-list screen, replace the two separate top-bar icon buttons (the Terminal "Start SSH session" action from UC-62 and the Settings gear) with a single **hamburger / overflow menu** exposing **"Start SSH session"** and **"Settings"** — same behaviors, one entry point. In the **Settings** screen, add a **"Look for server updates"** action that calls a new mTLS-secured endpoint (e.g. `GET /v1/server/update/check`) which queries the GitHub Releases API for the newest `server-v*` release and compares it to the server's own running version (read from the jar manifest `Implementation-Version`, baked from the gradle `ai_sandbox_server_version`). If newer, the UI shows an **"Update to version X"** button and a **"Changelog"** link that opens that release's GitHub page in an external browser. Tapping update shows an **in-app confirmation dialog**; on confirm it calls a second mTLS-secured endpoint (e.g. `POST /v1/server/update/apply`). The install is performed by a **separate root-owned `ai-sandbox-updater` systemd unit** (oneshot, path/trigger-activated). This updater is the **single privileged action the server can cause, and it accepts no parameters whatsoever**: the non-root server merely emits a bare, payload-free trigger (e.g. touching a fixed trigger path or pinging a fixed socket — no version, no path, no arguments). The root updater **self-determines the target** (the latest `server-v*` GitHub release), downloads + verifies + installs the `.deb`, and restarts `ai-sandbox-server` — entirely from its own trusted logic, never from server-supplied input. Because there are no parameters to inject, the server (even if compromised) can at most request "update to the latest published release", nothing else; **parameter injection is therefore an explicit adversarial QA verification gate**. Because the updater is its own unit, it survives the server restart. The apply endpoint returns promptly; the Android client shows an "updating…" state, tolerates the disconnect, polls `/v1/healthz`, and reports the new running version once back.

## Acceptance Criteria
1. On the sessions-list screen, the Terminal and Settings top-bar icons are replaced by a single hamburger/overflow icon button; opening it shows exactly two items: "Start SSH session" and "Settings".
2. "Start SSH session" from the menu triggers the identical existing behavior (`POST /v1/sessions/server-ssh` → open terminal); "Settings" navigates to the Settings screen. No regression to either action's behavior; existing test tags are preserved or migrated with updated tests.
3. The Settings screen shows a new "Look for server updates" action in its own section, with an explicit trigger control (not auto-run on screen open).
4. Triggering the check calls a new mTLS-secured endpoint that returns: the server's current version, the latest `server-v*` version, an `updateAvailable` boolean, the release HTML URL (changelog), and the matching `.deb` asset download URL.
5. The server reads its own running version at runtime from the jar manifest `Implementation-Version` (populated from `ai_sandbox_server_version` at build time); version comparison uses semantic-version ordering, so an equal or older remote yields `updateAvailable=false`.
6. When `updateAvailable=false`, the UI shows an "up to date" state with no update button. When `true`, it shows an "Update to version X" button and a "Changelog" link that opens the release's GitHub page in an external browser.
7. Tapping "Update to version X" shows an in-app confirmation dialog warning that the server will install vX and restart (the app will disconnect briefly). Only on explicit confirm does the client call the apply endpoint.
8. The apply flow installs the `.deb` and restarts `ai-sandbox-server` via a **separate root-owned `ai-sandbox-updater` systemd unit**, decoupled from the server process so the restart does not kill the in-progress install. The non-root server only emits a bare, payload-free trigger; it never runs `dpkg`/`apt`/`systemctl` directly and never passes any data to the updater.
9. The apply endpoint responds promptly (acknowledging the update was kicked off) without blocking until the restart severs the connection. The client surfaces "updating…", tolerates the disconnect, polls `/v1/healthz`, and on recovery reports the now-running version (ideally confirming it equals the target).
10. Both new endpoints enforce mTLS exactly as other `/v1/**` endpoints do (only `POST /v1/enrollment` exempt); unauthenticated/non-enrolled callers are rejected with the standard `401 mtls_required`.
11. The updater script/unit is the **single privileged executable the server can cause to run**, and it **takes no parameters**: it derives its target itself (latest `server-v*`), downloads + verifies the `.deb` directly from the trusted public GitHub release, then installs and restarts. The server passes it nothing — no version, no path, no flags, no env-borne arguments — so a compromised server cannot direct it to install an arbitrary package or run arbitrary commands as root. No other privileged path (sudo entry, setuid binary, root-runnable script) is exposed to the server.
12. **Adversarial injection gate (must be a real test, not a claim):** QA actively attempts to smuggle attacker-controlled parameters into the privileged path and proves they are never consumed as arguments. At minimum, exercise: (a) crafted content written into the trigger file/socket payload, (b) a malicious trigger filename, (c) injected/poisoned environment variables, and (d) shell-metacharacter payloads — and assert the updater ignores all of them, still acting only on its own derived latest-release target (or refusing). The test fails if any injected input alters the package installed, the command run, or the version targeted.
13. **No GitHub credentials required.** Neither the check endpoint nor the updater uses any GitHub token, `gh auth`, PAT, or other credential — both the release lookup and the `.deb` download run fully unauthenticated against the public repo. No credential is read from secrets, config, or env, and none is provisioned as a dependency. (A test asserts the credential-free paths work and that no auth header/token is attached.)
14. Failure paths are handled and surfaced to the UI without taking the service down: GitHub unreachable/rate-limited, no newer release, no matching `_amd64.deb` asset (wrong arch), download/verification failure, and install failure each produce a clear error while the server keeps running on its current version.
15. The feature targets the repo's `server-v*` release track only; android releases are ignored.
16. The new `ai-sandbox-updater` units/scripts are packaged into the `.deb` (jdeb), enabled idempotently via maintainer scripts, **and** added to the CI bundle/asset checks; new endpoints/enums appear in regenerated OpenAPI (`:server:generateOpenApiDocs`). Server code follows the Controller → Facade → Service chain (profile-java-server-architecture).

## Potential Pitfalls & Open Questions
- **Risk (root trust boundary)** — The non-root server can cause exactly one privileged action: firing the parameter-free updater (AC-11). Because the updater accepts no input and derives its own target (latest `server-v*`), a compromised server cannot install an arbitrary package or run arbitrary commands as root — it can only request "update to the latest published release". The dev team picks the concrete trigger mechanism (e.g. systemd `.path`/socket activation), keeping it strictly payload-free. AC-12 is the adversarial gate proving injection is impossible.
- **Edge case (packaging reach)** — A new required server unit/script must land in the `.deb` (jdeb task), the operator zip, **and** the CI bundle list, or CI/release breaks; `:server:test` alone won't catch it. New units must be enabled idempotently in postinst and cleaned up in prerm/postrm as appropriate.
- **Edge case (path/trigger activation)** — A systemd `.path` unit (or socket activation) watching a server-writable staging dir must have correct ownership/permissions so the non-root server can write the trigger but cannot tamper with the updater unit or its script.
- **Edge case (arch)** — Release ships `..._amd64.deb`; on a non-amd64 host there is no matching asset, so the check/apply must fail cleanly rather than install a wrong-arch package.
- **Constraint (no credentials)** — Repo is public, and the feature must require **no GitHub credentials at all** (AC-13): both the release lookup and the `.deb` download are unauthenticated. Unauthenticated GitHub API rate limits (~60/hr per IP) are acceptable for a user-initiated check; if a check is rate-limited it surfaces as a clear error (AC-14) rather than falling back to a token.
- **Assumption (test environment)** — Real install + systemd restart can't run in unit tests; QA verifies the orchestration logic (version compare, endpoint contracts, trigger writing, error handling) with the actual package/restart path validated via the release functional gate or manual host check.

## Clarifications
- Q: How should the privileged install + self-restart be authorized (the java service isn't root; the restart kills the request-handling process)?
  A: A separate root-owned updater systemd unit does the download/install/restart; the server only stages the artifact/intent and triggers it (path/socket-activated). Clean privilege separation.
- Q: How should the server learn its own running version at runtime for the comparison?
  A: Bake the gradle version into the jar manifest `Implementation-Version` and read it at runtime.
- Q: How much confirmation/safety before the destructive apply (install + restart)?
  A: Require an in-app confirmation dialog, then show an updating state, poll `/v1/healthz`, and report the new version when back online.
- Q: What should the "Changelog" link do?
  A: Open the release's GitHub HTML page (with its auto-generated notes) in an external browser.
- Q: How tightly should the privileged updater be constrained?
  A: The updater must be the ONLY thing the server can execute that requires privileges, and it must accept NO parameters. The server emits a bare, payload-free trigger; the updater self-determines the latest `server-v*` target. Parameter injection must be an explicit adversarial test-verification gate (crafted trigger content/filename, poisoned env, shell metacharacters — all proven inert).
- Q: May the feature use GitHub credentials (token/PAT/gh auth) for the lookup or download?
  A: No. The repo is public; both the release check and the `.deb` download must run with no GitHub credentials at all — none read from secrets/config/env, none provisioned.
