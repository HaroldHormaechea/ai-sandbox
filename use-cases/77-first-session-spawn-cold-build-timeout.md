# Use Case 77: Bugfix — first session spawn times out on the cold `docker compose build` (>60s `spawn-timeout`)

## Summary
Creating the **first** Docker session after a fresh install can fail with a hard `500 internal_error` because `POST /v1/sessions` runs `spawn.sh` (which does `docker compose build` + `up` for the heavy sandbox image) as a subprocess bounded by `ai-sandbox.server.spawn-timeout-seconds: 60` (`server/src/main/resources/application.yaml`). The cold first build of the sandbox image legitimately takes **longer than 60s**, so `ProcessExecutor` aborts a spawn that would have succeeded, throwing `IOException`/`TimeoutException("exec timeout: …/spawn.sh")` → `500 internal_error`. Once the image layer cache is warm the same spawn returns in well under a second. This surfaces to the user as **"I can no longer create sessions"** — and is the most likely real-world cause behind the UC-73 report (the in-process server-ssh session creates instantly, but the first *real* Docker session afterwards trips this timeout). This was confirmed by a live reproduction during UC-73 investigation: a fresh server's first `POST /v1/sessions` returned `500 @63s` with `exec timeout: …/spawn.sh` in `journalctl`, then `201` in ~0.4s once cached — the failure is **independent of removing the server-ssh session**. The fix is to stop a slow-but-progressing first build from being read as a hard failure: pre-build/warm the sandbox image so the first interactive spawn doesn't build, and/or decouple the image build from the per-request spawn timeout (and document/raise the timeout). The approach is for analysis to decide; this use case fixes the cold-start failure without weakening the legitimate stuck-spawn guard.

## Acceptance Criteria
1. On a fresh server (cold image cache, sandbox image not yet built), creating the first Docker session no longer fails with a `500` timeout caused solely by the cold `docker compose build` exceeding `spawn-timeout-seconds`. The first session either succeeds, or the build is performed/triggered ahead of the interactive spawn so the spawn request itself is fast.
2. The legitimate purpose of `spawn-timeout-seconds` (bounding a genuinely stuck `spawn.sh`) is preserved — the fix does not simply disable the timeout or make it unbounded. If the timeout value is raised or made configurable, the new behavior is documented and a sane upper bound remains.
3. The slow first-build path is distinguishable from a real spawn failure in logs/telemetry: a long cold build is not logged/returned identically to a hard `spawn_failed`, so operators can tell "warming up" from "broken".
4. Subsequent spawns (warm cache) are unaffected and remain fast; the change adds no latency to the common warm-spawn path.
5. If the chosen approach pre-builds/warms the sandbox image (e.g. at install/onboarding, on server start, or lazily on first readiness), it is idempotent, does not block unrelated server startup paths, and degrades gracefully when the image is already present.
6. A regression test covers the timeout/cold-build interaction at the appropriate level (e.g. the spawn-timeout config binding + the build/spawn decoupling logic), and existing spawn tests stay green.
7. QA verifies on a live server with a **cold** image cache that the first Docker session creation no longer hard-fails on the build timeout, and that a warm-cache spawn still returns quickly. Honest disclosure if a fully-cold environment cannot be reproduced in-sandbox.

## Potential Pitfalls & Open Questions
- **Scope boundary vs UC-73** — UC-73 (prerequisite-loss after removing the server-ssh session) was *not* reproducible and is blocked; this UC is the separately-confirmed, real cold-build timeout. Do not re-introduce a speculative server-ssh/`kill()` change here — this is purely the spawn/build-timeout path.
- **Environment-specific amplifier (out of primary scope)** — the live repro host also exported `AI_SANDBOX_DEVTOOLS` as an env var inherited by the JVM, which forced `spawn.sh` into a long in-container provisioning wait (cold Android SDK, minutes). A real operator's systemd unit sets neither that env var nor an unbuilt image, so the **dominant operator-facing cause is the cold `compose build`**. If the team also wants to harden the devtools-provisioning wait, scope it explicitly; don't let it mask the primary fix.
- **Don't weaken the stuck-spawn guard** — raising `spawn-timeout-seconds` alone is the crude option; it leaves real hangs waiting longer. Prefer decoupling the heavy build from the request-bound spawn (pre-build / async readiness) so the per-request timeout can stay tight.
- **Edge case** — pre-building at install/startup must not break offline installs, must be idempotent, and must not race a concurrent first interactive spawn (don't build the same image twice).
- **Edge case** — the client UX: if the first spawn legitimately takes time to build, the app should not read it as the destructive "re-scan QR / hard failure" path (UC-52/61). Surfacing a "preparing image" state is preferable to a `500`.
- **Key files** — `server/src/main/resources/application.yaml` (`spawn-timeout-seconds`), `server/sample-config.yaml`, the spawn facade/service + `ProcessExecutor` that runs `spawn.sh`, `spawn.sh` itself (build vs up), and the install/onboarding/startup path if pre-build is chosen (`setup.sh` / server bootstrap).
