# Use Case 52: Transient connection failure misrouted to the destructive "re-scan a fresh invite QR" TLS-identity screen (no retry, no auto-recovery)

## Summary
A transient connectivity failure — the management server briefly down, a server restart, a WiFi/network blip, a dropped WebSocket — routes the Android app to the full-screen **`ServerIdentityChangedScreen`** with the copy "Couldn't reach the server securely / The TLS handshake with the server failed for a reason other than pin or hostname mismatch … re-scan a fresh invite QR if the problem persists", offering only **Quit** / **Scan new QR**. There is no **Retry**/**Reconnect**, and the app does **not** auto-recover when the server comes back — the user is stranded on an identity-error screen and pushed toward re-enrolling (destructive: scanning a new QR re-keys the device) for what is actually a momentary network hiccup.

Reproduced live against the emulator: with the conversation/session screen open, stopping the server makes the next request fail and the app jumps to this screen; restarting the server does not dismiss it; only `back` (escaping the pushed route) or Quit/Scan-new-QR get out.

Root cause: `TlsFailureTranslation.translate()` maps **`is IOException -> NetworkEvent.HandshakeError`** as a catch-all. Plain connectivity failures — `java.net.ConnectException` (connection refused), `SocketTimeoutException`, `UnknownHostException`, generic socket `IOException` — are all `IOException`s, so they are classified as a TLS handshake failure. The `AiSandboxHttpClient` interceptor emits that `HandshakeError` `NetworkEvent`, and the root composable force-routes to `ServerIdentityChangedScreen`. A genuine connectivity problem is thus indistinguishable, to the UI, from a real TLS/identity compromise.

The fix distinguishes **transient connectivity failures** from **genuine TLS/identity failures**: connectivity failures surface a transient, **retryable "server unreachable / reconnecting"** state (with a Retry action and/or automatic recovery once the server is reachable again), and never push the user to the re-enroll/identity screen; the identity screen (and its "re-scan QR" remediation) is reserved for real pin/hostname/handshake compromises (`SSLHandshakeException`/`SSLPeerUnverifiedException`/`SSLException` and pin-mismatch).

## Acceptance Criteria
1. A `ConnectException` (connection refused), `SocketTimeoutException`, `UnknownHostException`, or other non-TLS socket `IOException` is classified as a **transient connectivity** failure — NOT `HandshakeError` — and does **not** route to `ServerIdentityChangedScreen`.
2. On a transient connectivity failure, the user sees a recoverable state (e.g. an offline/"can't reach server, reconnecting" banner or retryable surface) with a **Retry** affordance; quitting/re-enrolling is not the only option.
3. The app **auto-recovers**: once the server is reachable again, the normal screen returns without the user having to Quit, re-scan a QR, or restart the app (e.g. the next `refresh`/reconnect succeeds and clears the transient state).
4. Genuine TLS/identity failures are unchanged and still route to `ServerIdentityChangedScreen`: SPKI pin mismatch (`SSLHandshakeException` carrying the `SpkiPinningTrustManager` message → `PinMismatch`), hostname/SAN mismatch (`SSLPeerUnverifiedException` → `HostnameMismatch`), and other genuine `SSLException` handshake errors (→ `HandshakeError`).
5. `TlsFailureTranslation.translate(...)` returns a distinct value for transient connectivity failures (a new transient/unreachable variant, or `null` so the caller treats it as a non-identity error) so existing callers that already guard with `translate(...) == null` (`SessionsCoordinator.delete()/lifecycle()`, and UC-51's `refresh()/spawn()`) treat connectivity failures as ordinary recoverable errors rather than identity events.
6. The `AiSandboxHttpClient` interceptor no longer emits the full-screen identity `NetworkEvent` for plain connectivity failures (it emits the transient signal or none, letting the call site surface a recoverable error).
7. No regression to UC-04/UC-10 TLS routing, UC-32 events-feed reconnect/back-off, or the cert-revoked (4401) path.
8. Unit tests pin the classification: each of `ConnectException`/`SocketTimeoutException`/`UnknownHostException`/generic `IOException` → transient (not identity); each genuine TLS case (pin mismatch, SAN mismatch, other `SSLException`) → its existing identity variant.

## Potential Pitfalls & Open Questions
- **Exception taxonomy** — Distinguish by class precisely: `SSLException` (and subclasses `SSLHandshakeException`/`SSLPeerUnverifiedException`) = TLS; `ConnectException`/`SocketTimeoutException`/`UnknownHostException`/`EOFException`/plain `IOException` = connectivity. A `SocketException: Connection reset` can occur mid-TLS; decide its bucket deliberately (lean "transient/retry" unless it carries a TLS cause) and pin it with a test.
- **Don't weaken security** — A real pin or hostname mismatch must STILL hit the identity screen. The change must only re-bucket clearly-connectivity exceptions; when in doubt about a TLS-adjacent exception, keep it on the identity path rather than silently retrying against a possibly-compromised endpoint.
- **Auto-recovery surface** — Decide where the transient state lives (sessions list already has UC-32 reconnect + REST fallback; the conversation/terminal stream has its own `ReconnectController`). Prefer reusing existing reconnect/refresh machinery to clear the transient banner on success rather than adding a parallel recovery path.
- **Interplay with UC-51** — UC-51 prevents the uncaught crash; this UC fixes the misclassification/misroute. They are complementary: after both, a server-down on the sessions list neither crashes (UC-51) nor shows the identity screen (this UC) — it shows a retryable "server unreachable" state that clears on recovery.
- **Escapability today** — Currently `back` escapes the pushed identity route to the previous screen, but the underlying request still fails and there's no retry; the fix must give a real recovery path, not rely on the back-stack accident.

## Clarifications
- Q: Is it reproducible and persistent? A: Yes — server down → identity screen; server back up → screen stays (no auto-recovery); only Quit/Scan-new-QR (or a back-press accident) escape.
- Q: What's the misclassification? A: `is IOException -> HandshakeError` in `TlsFailureTranslation`; a plain connection-refused is treated as a TLS handshake failure and routed to the re-enroll screen.
- Q: Should genuine TLS failures still show the identity screen? A: Yes — pin mismatch, SAN/hostname mismatch, and real handshake errors must keep their current identity-screen routing unchanged.
- Q: Desired behavior for transient drops? A: A retryable "server unreachable / reconnecting" state that auto-recovers when the server returns — never the destructive re-scan-QR dead-end.
- Q: Scope vs UC-51? A: UC-51 stops the crash in `SessionsCoordinator.refresh()/spawn()`; this UC fixes the classification + routing + recovery for transient connectivity failures across the net layer (`TlsFailureTranslation`, `AiSandboxHttpClient`, the identity-screen routing).
