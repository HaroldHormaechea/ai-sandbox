# Use Case 75: Bugfix — answering via the "Other" free-text field hangs the conversation (thinking spinner never resolves)

## Summary
When Claude raises an AskUserQuestion in a session, the Android client shows the radio options plus an **"Other"** free-text field. Selecting a canned option works, but typing a custom answer into the "Other" field and sending can leave the conversation **stuck on the thinking/working spinner** — the answer is not committed and Claude stays blocked on the same prompt, so no transcript frame arrives to flip `WORKING`→`IDLE`. The spinner is *correctly* reflecting "no forward progress"; the real defect is that the free-text answer is not delivered safely. The investigation pinned a concrete, provable cause for the **multi-line** case: the "Other" field allows newlines (`QuestionSheet.kt` `singleLine = false`, `maxLines = 3`), the newline survives transport (`ConversationClient.jsonEscape`), and the server injects the answer text **raw** via `InputInjectionService.selectQuestionAnswer` → `sendLiteral(n, target, freeText)` with no newline handling — unlike `injectComposer`, which splits on `\n` and uses `C-j` (LF-without-submit) between lines. Per the code's own comments, a bare `Enter`/newline on the "Type something" row **commits/declines the ask**, so an embedded newline commits partial/empty text or declines → blocked prompt → stuck spinner. There is also a recovery gap: nothing flips the spinner back to IDLE when a `pending-clear` arrives without a resolving frame. This bugfix makes the answer free-text path newline-safe, hardens the client input, and adds a spinner safety-net so a failed/declined answer can never hang the UI forever.

## Acceptance Criteria
1. Sending a single-line custom answer via the "Other" field reliably commits the AskUserQuestion and Claude proceeds (spinner resolves to the next turn), matching the behaviour of selecting a canned option.
2. Sending a **multi-line** custom answer (text containing newlines) via the "Other" field no longer prematurely commits/declines: the server injects it newline-safely, mirroring `injectComposer` (split on `\n`, `C-j` between lines, final submit once), so the full text reaches the prompt and the ask is committed exactly once.
3. The server-side fix lives in `InputInjectionService.selectQuestionAnswer` for **both** the single-select free-text branch and the multiSelect free-text branch (and the batch path), replacing the raw `sendLiteral(n, target, freeText)` with the newline-safe walk (ideally a shared helper extracted from `injectComposer`). Blank/whitespace-only interior lines are handled exactly as `injectComposer` handles them (no stray submit on an empty segment).
4. Client-side defensive normalization: the "Other" field no longer sends a raw newline that could commit prematurely (normalize/strip newlines before send, or constrain the field), without otherwise regressing the UC-57 option/Other index mapping.
5. Spinner safety-net: when a pending sheet is cleared (`pending-clear`) or an answer otherwise fails to produce a forward frame, the conversation does not remain pinned on `WORKING` indefinitely — it recovers to a usable state. Prefer event-driven recovery (`pending-clear` → resolvable) over a blind timer; any timeout is conservative to avoid flipping to IDLE while a slow-but-valid answer is still processing.
6. New unit tests cover a newline-containing "Other" answer for single-select, multiSelect, and batch in `InputInjectionServiceTest.java` (the only existing `\n`/`C-j` test today is for the composer path), and the option/Other index mapping (UC-57) stays green.
7. QA verifies **live on the emulator** against a real AskUserQuestion (single-line and multi-line "Other"), since the "Other" commit keystroke dance is live-TUI-version-specific and the unit tests use a mocked tmux executor that pins keystroke sequences, not real TUI outcomes.

## Potential Pitfalls & Open Questions
- **Risk** — The commit sequence is pinned to a specific Claude TUI version (comments reference a concrete version); green unit tests are necessary but not sufficient. Verify live, consistent with prior fragility around pane-stepping / AskUserQuestion working-idle detection.
- **Edge case** — A blank or whitespace-only interior line must be skipped for content but still advance with `C-j` (as `injectComposer` does); a naive `split("\n")` that emits an `Enter` on an empty segment will decline the ask.
- **Edge case** — `maxLines = 3` is intentional multi-line UX. Decide between preserving multi-line (delivered via `C-j`) vs forcing `singleLine = true`; AC2 assumes multi-line is preserved end-to-end. Don't silently drop user newlines.
- **Risk** — The spinner safety-net must not mask a genuinely-delivered slow answer by flipping to IDLE too early; bias toward `pending-clear`-driven recovery and a generous timeout if any.
- **Assumption** — Root cause is "answer not delivered" (premature commit/decline), not "spinner stuck despite delivery"; confirmed for the multi-line case from code. A single-line repro that still hangs points to a live-TUI commit fragility to be confirmed on the emulator.
- **Key files** — `server/.../stream/service/InputInjectionService.java` (`selectQuestionAnswer` vs `injectComposer`), `server/.../stream/handler/SessionConversationHandler.java` (`deriveAnswerSpec`), `android/.../ui/components/QuestionSheet.kt` (Other field), `android/.../conversation/ConversationController.kt` (`submitAnswer`/`submitAnswerBatch`, `pending-clear` handling), `android/.../net/ConversationClient.kt` (`jsonEscape`).
