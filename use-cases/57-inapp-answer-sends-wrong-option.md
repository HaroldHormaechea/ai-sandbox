# Use Case 57: In-app AskUserQuestion answer sends the wrong option (first-visible instead of the selected one)

## Summary
When the user answers an interactive `AskUserQuestion` prompt **in-app** (the conversation view's `QuestionSheet`), the answer delivered back to the running Claude Code session does not always correspond to the option the user actually selected — it appears to send the **first visible option** rather than the chosen one. The symptom was reported from a live session: the user selected the second option but the session received the first. It does not reproduce on every prompt (in at least one observed instance the correct, non-first option was received), which points to a conditional mismapping — most likely an off-by-one or an order mismatch introduced when the displayed option order differs from the order used to build the answer frame, when an injected/"Recommended" or "Other" entry shifts indices, or when the selected-index state is not actually bound through to the submitted `selections`. The defect lives in the selection → submit mapping that produces the `answer` / `answer-batch` frame (and the keystroke `deriveAnswerSpec` injection on the server). The fix must guarantee that the option the user selected is exactly the option round-tripped to the session, for single-select, multi-select, and the free-text "Other" case, regardless of option ordering or any prepended/recommended entry. This is expected to be primarily an Android-client change in the `QuestionSheet` selection-state → answer-frame path, with possible server-side `deriveAnswerSpec` verification.

## Acceptance Criteria
1. Submitting an in-app answer to a **single-select** `AskUserQuestion` sends the option the user actually selected — the submitted `selections` reference that option, not the first/visible-top option — verified end-to-end (the value injected into the session matches the user's pick).
2. The selection → submitted-frame mapping is correct **regardless of option ordering** and is **not** thrown off by a prepended, "Recommended", or otherwise reordered/injected entry (no off-by-one between displayed index and submitted index).
3. **Multi-select** answers submit exactly the set the user checked — no more, no fewer — with each checked option correctly identified.
4. The **"Other" / free-text** option round-trips its typed text and is not silently collapsed to a default/first option.
5. Both the **transcript-derived** `question` path and the **pane-derived** `pending-question` path (UC-50 / UC-55) submit the user's actual selection; if either path is mismapping, it is fixed.
6. An automated test asserts that for a prompt with N options, selecting a non-first option (e.g. index 1 of 3, and the last index) produces an `answer` / `answer-batch` frame whose `selections` correspond to that option — covering single-select, multi-select, and "Other" — so the off-by-one/first-option regression is guarded.
7. No regression to the existing UC-40 / UC-50 / UC-55 question rendering and submit flows (plan-approval variant included), and their tests still pass.
8. CI gates pass: `:android:test` and `:android:lint`; and if any server code changes, `:server:test` and `:server:spotlessCheck`.

## Potential Pitfalls & Open Questions
- **Ambiguity** — The bug did not reproduce on every prompt in the reporting session (one prompt delivered the correct second option). The analyst/QA must isolate the exact triggering condition — likely a specific option layout (an injected "Recommended"/"Other" entry, a particular option count, or a reordered display) — and build a reliable repro before the developer changes the mapping.
- **Risk** — Two plausible root causes to distinguish: (a) the selected-index state is not bound through to the answer spec and defaults to the head (index 0 / first option); or (b) the displayed option order differs from the model order used to build `selections` (a sort/reorder or a prepended recommended entry), so "first visible" ≠ model index 0. The fix differs per cause; pin it with a test.
- **Edge case** — Single-select, multi-select, and plan-approval variants may each maintain their own selection state — verify all three rather than fixing only the single-select path.
- **Assumption** — "Sends the first option visible" indicates a UI-order vs. model-order mismatch or an unbound selection defaulting to the head; the corrected selection must flow through the same `deriveAnswerSpec` / `answer`-frame mechanism (no parallel divergent path) so the version-pinned injection stays intact.
- **Relationship** — Overlaps UC-55, which already calls for verifying the answer-send path; this UC narrows specifically to **selection → submitted-option correctness**. UC-55 has an open (pending) worktree — coordinate so the selection-correctness fix lands once and is not duplicated or reverted by the broader UC-55 work.

## Clarifications
- A: Go straight to implementation — handled autonomously (PR may be merged by Claude and a release generated). (The interactive clarification loop was skipped at the user's request, and deliberately so since the in-app answer path is the very feature under suspicion.)
- **Primary repro lead (live, two data points on the SAME question — strong signal).** The reporting session asked one `AskUserQuestion` with options sent in this order: index 0 = "Define a use case first", index 1 = "Go straight to implementation". The user **saw the options, tapped "Define a use case first"** (their words: "I had selected to generate a use case"), but the session **received "Go straight to implementation"** (index 1). The user also described it as "I answered the second and you received the first" and explicitly hypothesised **"maybe the ordering is wrong?"**. Taken together: the user's tapped option and the option delivered to the session do not match, and the mismatch tracks option *position*, not content. With only two options this presents as a swap.
- **Resulting root-cause hypothesis for the analyst (verify, don't assume).** The app appears to render the option list in a **different order than it was sent** (reversed, or shifted by an injected "Other"/"Recommended" entry), while building the answer/`answer-batch` frame from the **displayed position index applied to the original (differently-ordered) option array** — so tapping displayed-position *k* sends back `originalOptions[k]`, which is not the option shown at position *k*. Concretely, the analyst should: (1) find where `QuestionSheet` (and the pane-derived UC-50/UC-55 path) builds the option list for display vs. where it computes the `questionIndex`/`selections` for the submitted frame; (2) check for any `reversed()`/`sortedBy`/prepend/`asReversed()`/map-iteration-order or "Recommended"-promotion that reorders display without reindexing the answer; (3) confirm whether the `AskUserQuestion`-injected "Other" entry is prepended/appended and whether it shifts the index used for the submitted selection. Build the deterministic repro from this (e.g. a 3-option prompt where display order ≠ sent order) before changing the mapping.
- Note: The open items in *Potential Pitfalls & Open Questions* were left for the dev-team to resolve against the code and a live emulator repro. Given the lead above, the display-order vs. submit-index mismatch (Pitfall **Risk** option (b)) is now the leading hypothesis over the unbound-default-to-first option (a) — but the analyst must still confirm which against the source.
