# Use Case 46: Server-row context menu with Docker-lifecycle actions

## Summary
Each row in the mobile app's main sessions list (`SessionRow` in `android/src/main/kotlin/com/aisandbox/android/ui/screens/SessionsScreen.kt`) currently supports tap (open conversation), long-press (open tmux terminal), and a swipe-left gesture that reveals a destructive delete with confirmation (UC-20 / UC-28). This use case adds a **context menu** to each row exposing the full container lifecycle: **remove, stop, start, pause, unpause** — modeled on Docker's lifecycle states. The existing slide-to-remove gesture is kept; "remove" in the menu is an equivalent path to the same teardown flow. Critically, the server today exposes only spawn (`POST /v1/sessions`) and delete (`DELETE /v1/sessions/{n}`) — there are **no** stop/start/pause/unpause endpoints and no `docker pause|unpause|stop|start` controls in the session scripts. So this use case spans both client (the menu UI, action wiring, and per-row state/transition handling) and server (new lifecycle REST endpoints that drive the corresponding Docker operations on the session's container). Each action must be offered only when valid for the row's current state, optimistic/disabled-while-pending UI must prevent double-fire, and the enumerated `state` reported by `GET /v1/sessions` must grow to represent paused/stopped sessions so the `StatusPill` reflects them.

## Acceptance Criteria
1. Each session row exposes a context menu (e.g. via an overflow affordance and/or long-press alternative) listing the lifecycle actions: **Remove, Stop, Start, Pause, Unpause**.
2. The existing swipe-left / slide-to-remove gesture and its confirmation dialog continue to work unchanged; "Remove" in the menu triggers the same confirmed teardown path (not a second, unconfirmed delete).
3. Menu actions are shown/enabled only when valid for the row's current state (Docker-lifecycle semantics): e.g. **Start** only when stopped, **Stop** only when running, **Pause** only when running/unpaused, **Unpause** only when paused. Invalid actions are hidden or disabled, not silently no-ops.
4. The server exposes REST endpoints that perform the corresponding Docker operation on the session container for stop, start, pause, and unpause; each returns a clear success/failure status and is idempotent or safely rejects an out-of-state request.
5. `GET /v1/sessions` (the `SessionSummary.state` field) reports the new lifecycle states (at minimum a `paused` and a `stopped` state distinguishable from `running`/`terminating`), and `StatusPill` renders each with an appropriate visual treatment.
6. While a lifecycle action is in flight, the row reflects a transitional/pending state and the triggering control is disabled so the action cannot be double-fired; the row reconciles to the authoritative state on the next status update (UC-32 live push).
7. A failed lifecycle action surfaces a visible error to the user and leaves the row in its prior (or server-reported) state — never a stuck fake state.
8. Server lifecycle operations are concurrency-safe per session (consistent with the existing per-N mutex used for delete) so overlapping requests on the same session cannot corrupt state.

## Potential Pitfalls & Open Questions
- **Missing input** — No server endpoints or Docker controls for stop/start/pause/unpause exist today; this is net-new server work, not just a client menu. Scope must include the server side or the feature is non-functional.
- **Edge case** — Docker `pause` (SIGSTOP via cgroup freezer) suspends all processes including tmux and Claude; a paused session will drop/stall any live conversation or terminal stream (UC-32 push, UC-37 conversation). Reconnect/teardown behavior on a paused container needs definition so the app doesn't crash or hang on a frozen session.
- **Edge case** — `docker stop` of a session container vs. the app's `clean.sh` teardown: "stop" must preserve the container/volume so "start" can resume it, whereas "remove" tears down. The distinction between stop (resumable) and remove (destroyed) must be explicit in the server scripts.
- **Risk** — State model expansion: the current `state` enum (`running`/`starting`/`provisioning`/`terminating`/`stopped`) must be extended (e.g. `paused`, possibly `stopping`/`pausing`) consistently across server enumeration, client `SessionSummary`, and `StatusPill`, or rows will fall through to the unknown/fallback rendering.
- **Ambiguity** — Whether "Stop" should also stop a paused container (i.e. allowed from paused state) — Docker permits `stop` on a paused container; the AC3 state matrix should be confirmed against desired UX.
- **Ambiguity** — Surface for the menu: a Material dropdown from an overflow icon vs. repurposing long-press (which today opens the tmux terminal). Long-press is already taken, so a dedicated affordance is assumed; this should be confirmed so the terminal shortcut isn't lost.
- **Risk** — Starting a previously stopped session must re-establish whatever the session needs (network, mounts, tmux) — a bare `docker start` may not restore the full session contract that `spawn.sh` sets up. Resume fidelity needs verification.

## Original Description
Add functionality so in the mobile app, the rows that show each server in the main list have a context menu with options to remove (keep the slide to remove also), stop, start, pause, un pause. These follow the docker lifecycle states.
