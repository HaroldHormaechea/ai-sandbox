# Use Case 94: Fix session-spawn failure from root-owned per-session bind sources

## Summary
On the install-mode management server, spawning a session fails because per-session bind-mount sources under the host state root (`/var/lib/ai-sandbox-server/sessions/`) are owned `root:root` and unusable by the session container, which runs as `997:0` (uid `ai-sandbox-server`, gid `0`) via `AI_SANDBOX_RUN_AS_USER`. Any bind source that does not exist when `docker compose up` runs is auto-created `root:root` by the Docker daemon; `spawn.sh`'s `mkdir -p` is a no-op on an existing directory so it never repairs ownership, and the debris survives `apt purge`+reinstall because `/var/lib` is not dpkg-tracked. This manifests two ways: (1) the DinD override (`docker-compose.dind.yml`) binds `secrets/dind/subuid|subgid` as *files* onto `/etc/subuid|/etc/subgid`, but they are auto-created as root *directories* → fatal `error mounting ".../secrets/dind/subuid" to rootfs at "/etc/subuid": not a directory`; (2) `claude-config`/`workspace` auto-created `root:root` → the entrypoint dies on `Permission denied` writing `/home/claude/.claude` and the container exits 1. A contributing cause is that `ScriptExecutorService.composeEnv()` never exports `AI_SANDBOX_DIND_SUBUID_HOST_PATH`/`_SUBGID`, so they fall back to the state-root default instead of the server-owned secrets dir the design intends. The fix wires the dind paths to the server-owned `/etc/ai-sandbox-server/secrets/dind/`, guarantees every bind source is a correctly-typed, service-user-owned path before compose, and repairs stale root-owned debris from root-privileged installer paths.

## Acceptance Criteria
1. Starting from the broken precondition (root-owned `claude-config`/`workspace`, and `secrets/dind/subuid` as a root-owned directory), a spawn **succeeds**: the container reaches a healthy/ready state, `/etc/subuid` and `/etc/subgid` mount as files, and uid `997` can write `/home/claude/.claude`.
2. `ScriptExecutorService.composeEnv()` exports `AI_SANDBOX_DIND_SUBUID_HOST_PATH` and `AI_SANDBOX_DIND_SUBGID_HOST_PATH` pointing at the server-owned secrets dir (`/etc/ai-sandbox-server/secrets/dind/{subuid,subgid}`); onboarding / `secrets seed` ensures that directory exists owned by the service user; the files carry both `claude:100000:65536` and `sandbox:165536:65536`.
3. `aisb_subuid_ensure_line` (`devtools.d/lib/server-install.sh`) self-heals a path that exists but is not a regular file — it removes and recreates it as an empty regular file rather than failing — and is covered by a unit test.
4. All per-session bind sources (`workspace`, `claude-config`, `claude-projects-<N>`, dind `subuid`/`subgid`) are created and owned by the service user **before** `docker compose up` (prevention path in `spawn.sh` / server wiring); the service-user identity is derived, never hardcoded to `997`.
5. Pre-existing root-owned or wrongly-typed state-root debris is repaired by **both** the deb `postinst` and `aisandboxctl onboard` (root-privileged), narrowly scoped to the known per-session bind-source names under the state root (never a blanket chown of arbitrary data); the repair survives `apt purge`+reinstall.
6. **MANDATORY QA gate (non-negotiable):** the failure is reproduced *before* the fix (the exact `not a directory` mount error and/or the `Permission denied` entrypoint failure are shown) **and** success is reproduced *after* the fix from that same broken starting state (spawn succeeds, container healthy). Both before-and-after reproductions are required acceptance evidence; a fix without them does not pass QA. QA authors the exact reproduction commands; because there is no passwordless sudo on this host, the orchestrator (root session) relays the `sudo` steps to the user to run and captures the output as evidence.
7. No regression: a non-DinD spawn and a fresh-state spawn (no pre-existing broken state) remain byte-compatible with current behavior.

## Potential Pitfalls & Open Questions
- **Risk** — the `postinst` / onboarding repair must be narrowly scoped to ai-sandbox-server's own per-session bind-source names under the state root; it must never blanket-`chown` arbitrary or unrelated data.
- **Assumption** — the service-user uid/gid is derived (e.g. from the secrets-dir owner, as `ScriptExecutorService` already does for `AI_SANDBOX_RUN_AS_USER`, or from the systemd `User=`), never hardcoded to `997`.
- **Note (resolved)** — `spawn.sh` runs as the non-root service user, so it can only *prevent* new breakage (create correctly-owned sources in dirs it owns). *Repairing* already-broken root-owned state requires root and therefore lives in the deb `postinst` and `aisandboxctl onboard`.
- **Note (resolved)** — release: after the PR is merged, a `server-v*` release is cut via the `release` skill (separate from this fix's PR).

## Original Description
Spawning sessions fails on the install-mode management server. Root cause is one systemic defect: per-session bind-mount sources under the host state root (/var/lib/ai-sandbox-server/sessions/) that do not exist when `docker compose up` runs are auto-created root:root by the Docker daemon, so the session container — which runs as 997:0 (uid=ai-sandbox-server, gid=0) via AI_SANDBOX_RUN_AS_USER — cannot use them. spawn.sh's `mkdir -p` is a no-op on an already-existing root-owned dir, so it never repairs ownership. Because /var/lib is not dpkg-tracked, these root-owned dirs survive `apt purge` + reinstall (proven by a leftover claude-projects-55 dir from a pre-reinstall counter value) — which is why uninstall/reinstall did not fix it.

Observed symptoms:
1. DinD: docker-compose.dind.yml bind-mounts secrets/dind/subuid + subgid as FILES onto /etc/subuid|/etc/subgid. They get auto-created as root DIRECTORIES → fatal `error mounting ".../secrets/dind/subuid" to rootfs at "/etc/subuid": not a directory: Are you trying to mount a directory onto a file?`. The spawn-time guard `_aisb_dind_ensure_subid_files` (devtools.d/dind/manifest.sh) is meant to pre-create them, but `aisb_subuid_ensure_line` (devtools.d/lib/server-install.sh:37) cannot write into a root-owned parent (Permission denied) and cannot heal a directory (`: > dir` → "Is a directory"); both failures are swallowed by the guard's `|| true`.
2. claude-config / workspace auto-created root:root → entrypoint dies with `cp: cannot create '/home/claude/.claude/...': Permission denied` and `touch .seeded: Permission denied` → container Exited(1).

Missing server wiring (contributing cause): ScriptExecutorService.composeEnv() (server/src/main/java/com/aisandbox/server/sessions/service/ScriptExecutorService.java) never exports AI_SANDBOX_DIND_SUBUID_HOST_PATH / AI_SANDBOX_DIND_SUBGID_HOST_PATH, although docker-compose.dind.yml's `${AI_SANDBOX_DIND_SUBUID_HOST_PATH:-./secrets/dind/subuid}` default AND the dind manifest comments both say the management server is supposed to override them to point at its server-owned secrets dir. So they fall back to ./secrets/dind/ under the state root, which docker auto-creates root:root.

Validated unblock (proves fix direction; already applied to the live host): `sudo chown -R ai-sandbox-server:ai-sandbox-server /var/lib/ai-sandbox-server/sessions` plus ensuring secrets/dind/{subuid,subgid} are FILES containing the lines `claude:100000:65536` and `sandbox:165536:65536` → container stays Up, uid 997 can write /home/claude/.claude, subuid mount succeeds.

Reproduction command (runs spawn exactly as the server does; needs sudo to run as the ai-sandbox-server user):
`sudo -u ai-sandbox-server env AI_SANDBOX_COMPOSE_FILE=/opt/ai-sandbox-server/host/docker-compose.yml AI_SANDBOX_HOST_STATE_ROOT=/var/lib/ai-sandbox-server/sessions AI_SANDBOX_SECRETS_HOST_PATH=/etc/ai-sandbox-server/secrets AI_SANDBOX_CLAUDE_TEMPLATE_HOST_PATH=/etc/ai-sandbox-server/templates/claude-config AI_SANDBOX_RUN_AS_USER=997:0 bash /opt/ai-sandbox-server/host/spawn.sh --non-interactive --shared-workspace --shared-claude-config`

Notes: The server only logs `outcome:fail` + exitCode; the real stderr is returned to the client via SpawnFailedException, so server-side reproduction must capture spawn.sh stderr directly. The local POC jar can be hot-swapped (build the server jar, swap into /opt/ai-sandbox-server/lib/) to test server-side changes before cutting a release. Releases are cut by pushing a server-vX.Y.Z tag.

## Clarifications
- Q: Where should the DinD subuid/subgid files canonically live (and which path should the server wire via AI_SANDBOX_DIND_SUBUID_HOST_PATH)?
  A: Server-owned `/etc/ai-sandbox-server/secrets/dind/{subuid,subgid}` — the server exports the override paths there; matches the documented design and avoids the state-root root-creation trap.
- Q: Repairing already-broken root-owned state needs root (spawn.sh is non-root). Where should that repair live?
  A: Both the deb `postinst` and `aisandboxctl onboard` (root-privileged) re-own/clean stale state-root bind-source debris, so reinstall self-repairs; `spawn.sh` only prevents new breakage.
- Q: QA's mandatory before/after reproduction needs sudo, which isn't passwordless here. How should QA obtain the evidence?
  A: QA authors the exact before/after repro commands; the orchestrator (root session) surfaces the sudo steps for the user to run and captures the output as acceptance evidence.
- Q: Should the dev-team run end with a cut release, or stop at a merged-ready PR?
  A: Open a PR with the fix + evidence; after the merge is confirmed, cut a `server-v*` release via the release skill.
