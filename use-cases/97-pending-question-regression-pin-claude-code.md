# Use Case 97: Pending `AskUserQuestion` not delivered again (Claude Code drift) — fix the in-view signal, pin the Claude Code version, add a drift guard

## Summary
On the ai-sandbox Android conversation view, a live `AskUserQuestion` (single or multi) again fails to surface **conditionally**: sometimes the screen appears stuck and the question sheet never renders (and no sessions-list `?` indicator appears), so the user must switch to tmux to see/answer it or exit and re-enter the conversation to force it to appear — while other times the question is delivered correctly (a phone push notification fires and tapping it deep-links and renders the sheet). Reproduced live on this session (Claude Code **`2.1.159`**): one `AskUserQuestion` raised while the conversation was in view showed neither the sheet nor a list indicator (visible only in tmux), yet a later question fired a push notification whose deep-link rendered correctly. The failure is therefore **conditional and intermittent across every entry path**: one in-view question showed neither the sheet nor a list indicator (only tmux); a second question fired a push notification whose deep-link rendered the sheet correctly; and a third question fired a push notification whose alert showed, but **tapping the alert AND opening the conversation normally both failed to render the sheet**. Because the alert/detection fires even when nothing renders, the pending-question **detection is not the failure** in that third case — the regression is concentrated in the **sheet render/delivery layer** (`ConversationController.pendingSheet` population and the client render-gating / `readOnly` path), downstream of detection and independent of entry path (in-view, notification deep-link, or normal navigation). The in-view live-delivery path and the sessions-list `?` indicator also fail under some conditions (UC-40/50/93 territory). Leading systemic cause: **Claude Code spec drift** — the sandbox installs `@anthropic-ai/claude-code` unpinned (`latest-at-build`, `SandboxDockerfile:85`), so its TUI/transcript shape can move out from under the pane/transcript scraper, the same failure mode as UC-50 (defeated by `v2.1.169`). The fix is three-pronged: (A) **repro-first**, root-cause and repair the in-view live delivery + list indicator so a pending question renders live in the open conversation and as the `?` indicator, for single/multi and `ExitPlanMode`, with the in-app answer path intact; (B) **pin Claude Code to a gate-verified known-good version** in the image build and updater, replacing `latest-at-build`, so version bumps are a single deliberate change; and (C) **add a drift guard** — a UC-85 functional-gate leg (plus a pinned pane-signal-shape fixture) that asserts pending-question detection/delivery against the live pinned Claude Code, turning a drift-breaking version red *before* release. Must not regress UC-40/50/55/57/69/75/76/85/90/93/96.

## Acceptance Criteria
1. **Repro-first.** Before any fix, reproduce live (live server + Android app/emulator, on the pinned Claude Code) the conditional failure: a pending `AskUserQuestion` (single and multi) raised **while the conversation is in view** renders neither the conversation-view sheet nor the sessions-list `?` indicator while the session blocks (visible only in tmux), and pin down the condition that distinguishes this from the cases that work (e.g. app foregrounded-on-conversation vs. backgrounded / notification-triggered). At the wedge, capture five signals: (i) `aisandbox-conversation-tail --scan-pending` output for the blocked pane; (ii) pane/transcript bytes (does the TUI still expose the affordance the scraper expects; is the assistant turn in the `.jsonl`); (iii) server `ConversationController.pendingSheet` null vs populated; (iv) client `selectedTargetId`/`readOnly`; (v) app/session state (which view is foregrounded, socket connected vs. reconnecting).
2. Root cause is stated explicitly from those signals (in-view live-delivery / re-emit gap vs. render-gating vs. list-indicator field), not assumed — and reconciled with the fact that the push-notification + deep-link path succeeds for the same class of question.
3. After the fix, a pending `AskUserQuestion` renders the sheet **live** in the conversation view with **no action in any other view** while the session is blocked, including when the conversation is already open/foregrounded — single and multi (paged sheet, UC-43), plus the `ExitPlanMode` approval prompt.
4. The sessions-list `?` indicator (UC-49) appears while blocked and clears when answered/cancelled.
5. No exit/re-enter or tmux round-trip is required; the warm/in-view conversation path surfaces the question (UC-93 warm-start behavior preserved).
6. The sheet renders reliably across **all** entry paths, since all are currently intermittent: (a) in-view while foregrounded; (b) tapping a UC-69/76 push notification (deep-link); and (c) opening the conversation normally from the sessions list. The push notification itself still fires (detection), and in every case the sheet renders rather than the current state where the alert can fire yet neither the deep-link nor normal navigation shows the question.
7. Answering in-app resolves the question in the live session and the turn proceeds (UC-55/57/75 answer path intact — correct option mapping, no "Other" hang).
8. **Claude Code is pinned** to a specific gate-verified version in `SandboxDockerfile` and `ai-sandbox-updater.sh`, replacing the unpinned `latest-at-build` install; `PROJECT_BRIEF.md` `stack.versions.claude_code` is set to the pinned value. The analyst selects the newest version that passes the UC-85 gate and records why.
9. Upgrading the pin is a **single deliberate change gated by the UC-85 functional gate**; the process is documented (where the version lives, how a bump is proposed and verified) so drift can't silently reach production.
10. **Drift guard:** a UC-85 gate leg (and/or a pinned pane-signal-shape fixture) asserts pending-question detection + in-view delivery (single + multi) against the live pinned Claude Code and turns **red** if a future version breaks the signal — i.e. it would have caught this break.
11. A regression test reproduces the detected root cause at the correct layer (helper/`scanPending` fixture, server re-emit, or client render-gating) — failing before, passing after — without weakening UC-85 invariants.
12. No regression to UC-40/50/55/57/69/75/76/85/90/93/96. CI gates pass: `:server:test` + `:server:spotlessCheck` (server/Node-helper) and `:android:test` + `:android:lint` (client).

## Potential Pitfalls & Open Questions
- **Edge case (conditional failure)** — The bug is *not* uniform: an in-view question failed with no list indicator, but a later question fired a push notification and deep-linked correctly. The whole investigation hinges on isolating the discriminating condition (app foreground/background, socket state, first-vs-later question of a turn, single vs multi). Do not assume "detection is dead" — the push path proves detection can fire.
- **Risk (brittleness)** — The signal scrapes Claude Code's pane/transcript, now broken twice on drift (UC-50, this UC). Prefer the most stable affordance Claude Code exposes and pin its shape with a fixture; the drift guard (AC10) is the safety net.
- **Ambiguity (version ordering)** — This session runs `2.1.159`, *older* than the `2.1.169` the fixes were verified on. The analyst must confirm whether production regressed to an older Claude Code (stale image) or the numbering misleads — this determines the gate-verified pin target (AC8).
- **Assumption** — Affected surface is the **Android conversation view**; the tmux view is unaffected (works there per the user).
- **Risk (bundle size)** — One run carries three thrusts (fix + pin + guard); the challenger should confirm this stays tractable within the 6-round cap or flag a split.
- **Cross-reference (UC-93 re-analysis)** — UC-93 disproved the nav-entry-reuse theory and left two live candidates for the warm-path wedge: (B) a re-emit gap (`ConversationController.attach` no-ops when `connectJob.isActive`), and render-gating (`readOnly = selectedTargetId.startsWith(SUBAGENT_ID_PREFIX)` restored on warm re-entry hides the sheet even when `pendingSheet` is populated). Start the triage from those two, using the AC1 signal capture to choose.
