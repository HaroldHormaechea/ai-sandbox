# Use Case 85: Deterministic, LLM-free functional release gate

## Summary
The mandatory pre-release functional gate (the `release` skill's Phase 1, backed by `android-testing`) today needs an LLM agent to pilot the Compose UI with blind `adb input tap` coordinates against a live Claude session and *eyeball* screenshots — non-deterministic and fragile (the server-v0.0.52 / android-v0.4.16 release was blocked from completing that drive by chronic emulator launcher ANRs). This use case **replaces those LLM-driven checks with a deterministic, instrumented harness** and builds it fully. A **record-once/replay** mechanism captures real Claude protocol frames into committed fixtures and replays them deterministically through the real server (or a thin replayer) to the enrolled device over the real websocket — so an `AskUserQuestion` (and conversation transcript) can be raised on demand with **no live Claude**. **On-device instrumented Compose/Espresso tests** then drive the flows by stable `testTag` (never coordinates) and assert outcomes programmatically: the single-select / multi-select / "Other" free-text question paths (UC-55/75), that the *selected* option is the one actually sent back to the server (UC-57), multi-question→answer-frame mapping (UC-43), and the conversation-view invariants (teammate/subagent bubbles UC-58, anchor-to-bottom UC-78, lazy scroll-up UC-79, uncropped long messages UC-80, long-press copy UC-81). The suite must run **both in GitHub Actions CI** (emulator-in-CI) **and as one deterministic local command** on the KVM spawn, reusing the UC-83 headless QR-from-file enrollment route. Because the driver is on-device, the harness must also tame the emulator instability (launcher/SystemUI ANRs, animations) so it is reliable. Any test-only replay/injection seam added to the server must be absent or unreachable in release builds and must not weaken mTLS.

## Acceptance Criteria
1. A deterministic functional-gate harness exists that runs with **no LLM and no live Claude session**, raising `AskUserQuestion`s and conversation transcripts from **recorded protocol-frame fixtures** committed to the repo.
2. The frame-capture/record path is documented and repeatable: there is a defined way to (re)capture real protocol frames into the fixture format, and a **fixture schema/version check** that fails loudly when a fixture is stale or malformed (drift detection).
3. Recorded frames are replayed through the real server (or a thin replayer) to the enrolled device over the **real websocket/mTLS transport** — not a UI-layer shortcut that bypasses the network stack.
4. The driver is **on-device instrumented Compose/Espresso tests** that interact via stable `testTag`s only (no `adb input tap` coordinates, no screenshot eyeballing); every gated behavior has a programmatic assertion.
5. Assertions cover the answer paths: single-select, multi-select, and **"Other" free-text** (UC-55/75); and **the selected option is the one actually transmitted** to the server (UC-57) — verified by capturing/inspecting the outbound answer frame, not just the UI state.
6. Assertions cover **multi-question** `AskUserQuestion` sheets: each question maps to its own answer frame and the conversation resumes cleanly (UC-43).
7. Assertions cover the conversation-view invariants via instrumented checks: teammate/subagent bubbles render as distinct non-user messages (UC-58), anchor-to-bottom on load (UC-78), lazy scroll-up paging without jump (UC-79), uncropped long messages (UC-80), and long-press copy (UC-81).
8. The harness runs as **a single deterministic local command** on the KVM spawn AND **as a GitHub Actions CI job** (emulator-in-CI), both green on the current `main`; the CI job gates releases/PRs as configured.
9. Enrollment reuses the **UC-83 QR-from-file headless route**; no new enrollment path is introduced.
10. The on-device run is made **reliable against the emulator instability** seen during the server-v0.0.52 release (launcher/SystemUI ANRs, animations) — e.g. via AVD/runtime configuration — so flakiness from that source is eliminated or documented-and-mitigated.
11. Any test-only server replay/injection seam is **not present or not reachable in production/release builds** and does not weaken the mTLS trust boundary; a test asserts this guard.
12. The `release` skill's Phase 1 and the `android-testing` skill are updated to invoke this deterministic harness as the gate, with the prior LLM-driven, coordinate-tap, screenshot-eyeball steps removed (or explicitly demoted to optional), so future releases gate on the harness.
13. The work builds on existing assets (the Compose instrumented suite, `E2eQrFileEnrollmentTest`, UC-83 route) rather than a parallel framework.

## Potential Pitfalls & Open Questions
- **Risk (emulator reliability)** — On-device-only means the gate still depends on a healthy emulator; the chronic Quickstep/SystemUI ANR that blocked the server-v0.0.52 release must be genuinely fixed/mitigated (disable animations, launcher tweaks, boot/AVD config, retry/wait strategy) or the deterministic gate inherits the same flakiness. AC-10 makes this explicit.
- **Risk (CI emulator support)** — GitHub-hosted runners need nested virtualization/KVM for a hardware-accelerated emulator (e.g. `reactivecircus/android-emulator-runner` on a KVM-capable runner). Whether the project's CI runners provide this must be confirmed; a software-rendered fallback may be too slow/flaky.
- **Risk (fixture drift)** — Recorded frames can diverge from the evolving real protocol; AC-2's schema/version check mitigates but a refresh cadence and an occasional real-Claude re-capture are still needed so a green gate stays meaningful.
- **Risk (production safety of a replay seam)** — If replay needs a server-side seam to push frames to the device, it must be debug-only and unreachable in release builds (AC-11).
- **Edge case (outbound-frame capture)** — Asserting "selected option actually sent" (UC-57) requires observing what the device transmits; the harness needs a deterministic way to capture the outbound answer frame (test server hook or instrumented interception).
- **Assumption** — Enrollment determinism from UC-83 is sufficient and reused unchanged.

## Original Description
"Evaluate how to automate the [release] functional tests without using an LLM to run them."

Context the user is reacting to (gathered live during the server-v0.0.52 / android-v0.4.16 release): The project's mandatory pre-release functional gate (the `release` skill Phase 1, backed by the `android-testing` skill) currently REQUIRES an LLM agent to drive it by hand: boot the KVM emulator, build+start a live mTLS management server, enroll the device, then FUNCTIONALLY exercise — against a live server with a real on-device Claude session — (1) a single AskUserQuestion (single-select, multi-select, and "Other" free-text), (2) a multi-question AskUserQuestion sheet, and (3) conversation-view sanity (teammate/subagent bubbles, anchor-to-bottom, lazy scroll-up, uncropped long messages, long-press copy), then pull screenshots and EYEBALL them. Today the agent pilots the Compose UI with blind `adb input tap` coordinates and visually judges screenshots — both non-deterministic. During the server-v0.0.52 release it was BLOCKED: the emulator's Quickstep/SystemUI launcher chronically ANRs, so blind-tap piloting was unreliable and the live single/multi-question drive could not be completed (the release was tagged anyway because UC-84 doesn't touch those paths, but the gate gap is real). The goal of THIS use case is to design/evaluate how to make those functional checks run deterministically as a scripted, CI-runnable harness with NO LLM in the loop — e.g. instrumented Espresso/Compose-UI tests that drive the real flows via testTags (not coordinates) against a real or faithfully-faked server, a deterministic AskUserQuestion injection/trigger mechanism (so a question can be raised on demand without a live Claude), machine-checkable assertions/screenshot-diffing instead of eyeballing, and a way to assert the selected-option-actually-sent (UC-57) and multi-question mapping (UC-43) paths. The existing UC-83 QR-from-file enrollment route already made enrollment deterministic/headless; this extends that determinism to the question/answer + conversation gate.

## Clarifications
- Q: How should the harness deterministically raise an AskUserQuestion (and protocol frames) WITHOUT a live Claude session?
  A: Record-once / replay frames — capture real Claude protocol frames once into committed fixtures, then replay them deterministically through the real server (or a thin replayer).
- Q: What test layer should drive the gated UI behaviors?
  A: On-device instrumented only — Compose/Espresso instrumented tests via testTags on the emulator (exercises the real mTLS/OkHttp + Compose stack end-to-end).
- Q: Where must the deterministic gate be runnable?
  A: Both — a GitHub Actions CI job (emulator-in-CI) AND a single deterministic local command on the KVM spawn.
- Q: What's the deliverable scope for this use case?
  A: Evaluate + implement fully — produce the evaluation AND build the complete deterministic harness (record/replay + instrumented tests + CI wiring), and rewire the release/android-testing skills to use it.
