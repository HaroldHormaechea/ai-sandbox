# Use Case 28: "awaiting termination" feedback state + block re-delete while terminating

## Summary
On the Android sessions list, confirming a delete (the UC-20 swipe-to-dismiss → confirm flow that calls `DELETE /v1/sessions/{n}` → `clean.sh` → `docker compose down`) gives no in-between feedback: the row keeps its prior `running`/`provisioning` pill until the post-delete refresh either drops it or flips it straight to `stopped`, so from the operator's view the session jumps abruptly from "started" to gone/"died." This use case introduces an intermediate **`terminating`** ("awaiting termination") state for a session whose teardown is in progress, surfaced **both** as a first-class server status on `GET /v1/sessions` (new wire token added to `DockerEnumerationService` + `server/openapi.yaml`, alongside `running | starting | provisioning | stopped`) **and** as an immediate client-side optimistic state the moment the user confirms the delete (so feedback appears before the first server refresh lands). While a session is terminating, the app **blocks every new delete attempt** on it — the sessions-list swipe-to-dismiss gesture and the UC-21 terminal-screen hamburger/force-delete all no-op for that session — so the operator cannot re-trigger or stack deletes; other sessions stay fully deletable. The terminating pill is rendered in a distinct destructive-red M3 treatment with an animated/indeterminate indicator (a "spinner-dot"), visually separate from running (green), starting/provisioning (amber), and stopped (gray). The state persists until a refresh resolves it: on success the row is removed and does not reappear; on an explicit delete failure the row exits terminating, reverts to its real server status, and the error is surfaced (preserving UC-20 AC5). The work spans the server (status mapping + OpenAPI spec, kept in sync so `server-ci.yml`'s OAS-drift check passes) and the Android client (`StatusPill`, per-row terminating tracking in `SessionsViewModel`/`SessionsCoordinator`, swipe-gating in `SessionsScreen`, and the UC-21 terminal-screen delete guard). It must stay within the dark-theme M3 Expressive system and must not regress UC-18 tap-to-open or UC-20 swipe/force-delete.

## Acceptance Criteria
1. The server exposes a new session status value `terminating` on `GET /v1/sessions`: a session whose container teardown is in progress is reported as `terminating` rather than `running`/`stopped` or omitted. `server/openapi.yaml` is updated to include `terminating` in the status enum, and `server-ci.yml`'s OpenAPI-drift check passes.
2. On the Android side, confirming a delete immediately puts the targeted row into a visible `terminating` ("awaiting termination") state — a distinct status pill replacing the prior running/provisioning pill — **before** the `DELETE /v1/sessions/{n}` call resolves (client-side optimistic), and the row remains terminating while the server continues to report `terminating`.
3. The session never jumps directly from a running/started pill to removed or `stopped` with no intermediate feedback; the terminating presentation is shown for the duration of the in-flight teardown.
4. While a row is terminating, the sessions-list swipe-to-dismiss delete gesture is disabled for that row and cannot raise a second delete confirmation.
5. Every other delete affordance for that same session — notably the UC-21 terminal-screen hamburger delete and any force-delete path — is likewise blocked / no-ops while the session is terminating.
6. Blocking and the terminating pill are scoped per-session: deleting session A does not block deletes, disable swipe, or change the pill of unrelated sessions B/C, which remain fully deletable.
7. On successful deletion, the terminating row is removed after the post-delete refresh and does not reappear.
8. On an explicit failed delete (non-success HTTP / network / cert-pin error), the row exits terminating, reverts to its actual server-reported status, and the failure is surfaced to the user (UC-20 AC5 preserved) — never a silent no-op.
9. If no explicit error arrives but the server has not yet confirmed removal, the row stays in the terminating state until a subsequent refresh resolves it (the row disappears, or the server stops reporting `terminating`, or an error surfaces) — there is no client-side timeout that forces it out of terminating early.
10. The terminating pill is visually distinct from running (green), starting/provisioning (amber), and stopped (gray): a destructive-red M3 treatment carrying an animated/indeterminate "spinner-dot" and the label `terminating`. Unknown/never-seen status tokens still render gracefully (raw label, neutral treatment).
11. No regression: tapping a non-terminating row still opens the terminal (UC-18); swipe-to-delete + the force toggle still work on non-terminating rows (UC-20).
12. Coverage:
    - Server: a `DockerEnumerationService`/mapping test that a teardown-in-progress session is reported as `terminating`, plus the OpenAPI-spec assertion for the new enum value.
    - Android unit: `SessionsViewModel`/`SessionsCoordinator` terminating-state transitions — enter on confirm, hold while server reports `terminating`, clear on success-removal, revert on explicit failure, per-session isolation.
    - Android instrumented (Compose, runnable via the `android-testing` skill): pill shown after confirm; swipe blocked while terminating; terminal-screen delete blocked while terminating; row removed on success; revert + error surfaced on failure.

## Potential Pitfalls & Open Questions
- **Decision (resolved)** — the state is surfaced **both** server-side (`GET /v1/sessions` reports `terminating`) and client-side (optimistic on confirm). The optimistic flag gives instant feedback (AC2); the server status keeps the pill accurate across refreshes and for any other client. The terminating presentation is the *union* of "client just confirmed a delete for N" and "server reports N as terminating."
- **Risk (server detection mechanism — diagnose first)** — `DELETE /v1/sessions/{n}` is assumed effectively synchronous (`clean.sh` → `docker compose down` runs to completion inside the request thread), so the teardown window a concurrent `GET /v1/sessions` poll can observe is short. Two viable server mechanisms, dev-team's call after diagnosis: (a) **in-flight-delete registry** — the delete handler/facade marks `N` terminating for the duration of `clean.sh`, and `DockerEnumerationService.enumerate()` reports `terminating` for any session in that set (deterministic, independent of Docker timing); and/or (b) **Docker state mapping** — map the transient `removing` (and `exited`-while-project-still-present mid-`down`) `.State.Status` to `terminating` in `mapState` (today it falls through to `stopped`). The registry approach is more reliable because the `removing` window is brief and racy; the analyst should confirm whether `DELETE` is synchronous before choosing.
- **Edge case** — list-refresh races: an `enumerate` completing mid-termination must not resurrect a `running`/`provisioning` pill over an optimistically-terminating row, and the rows are keyed by `n` (cf. UC-20 pitfall). The terminating overlay clears only on (a) the row disappearing from the list, (b) an explicit delete error, or (c) the server reporting a non-`terminating` status that is itself a resolution — never spuriously by an in-flight refresh.
- **Edge case** — deleting a session that is already `stopped` server-side: confirm still shows `terminating` and still blocks re-delete while the (stopped-container) teardown/removal is in flight; resolves the same way (row removed on success).
- **Edge case** — app killed / navigated away mid-termination: on cold resume the client-side optimistic flag is gone; the row reflects whatever the server reports (`terminating` if teardown is still in flight, otherwise removed/`stopped`). This is acceptable — server status is the durable source of truth.
- **Risk (brief drift, do not self-fix)** — `PROJECT_BRIEF.md` documents the status value set as `running | starting | provisioning | stopped` in two prose spots (Technologies "REST consumption" and the Android subsection). Adding `terminating` makes that prose stale. The dev-team MUST NOT edit `PROJECT_BRIEF.md` (it is owned by `revise-brief`); instead flag the drift so a follow-up `/revise-brief` updates the documented value set.
- **Assumption (styling)** — "spinner-dot" means the leading status dot animates (indeterminate) rather than adding a full circular progress spinner, to stay consistent with the existing `StatusPill` dot vocabulary; the destructive-red maps to the M3 `error`/`Warning`-adjacent palette already in the theme. Dev-team may refine within the dark-theme M3 Expressive system; flag if contrast guidance is violated.

## Original Description
> Add feedback in the mobile app when a container is awaiting termination. Introduce a new intermediate state (e.g. "terminating" / "awaiting termination") so the container doesn't jump straight from "started/running" to "died". While in that awaiting-termination state, the app must block new delete attempts — e.g. disable the swipe/slide-to-remove gesture and any delete affordance for that container.

## Clarifications
- Q: Where should the "awaiting termination" state come from — client-side optimistic only, or a server-reported status too?
  A: **Server-reported status too** — add a first-class `terminating` token to `GET /v1/sessions` + `openapi.yaml` (in addition to the client-side optimistic feedback on confirm), so the state is authoritative and any client sees it.
- Q: What label and visual treatment for the terminating pill?
  A: **`terminating`** in a destructive-red treatment with a spinner/indeterminate indicator — signalling an in-progress destructive operation, distinct from green/amber/gray.
- Q: How wide should the "block new delete" guard be?
  A: **All delete paths for that session** — the sessions-list swipe-to-delete AND the UC-21 terminal-screen hamburger/force-delete are blocked for a session that is already terminating; other sessions stay deletable.
- Q: If the server never confirms removal, how should a stuck terminating row behave?
  A: **Stay terminating until a refresh resolves it** — no client-side timeout; the pill clears only when the row is removed, an error surfaces, or the server reports a resolving status.
