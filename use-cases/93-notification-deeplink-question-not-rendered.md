# Use Case 93: Pending question never renders / chat wedges when opening a conversation via the push notification (warm start)

## Summary
On the ai-sandbox **Android client**, tapping a UC-69 pending-question push notification **sometimes opens the conversation but never renders the `AskUserQuestion`, leaving the chat wedged** (no question sheet, composer gated, stale/old content) — while opening the same conversation **from the sessions list works**. Root cause is a navigation-entry-reuse defect on the deep-link path that UC-91 documented but left unfixed in production: the notification deep-link at `android/.../AiSandboxApp.kt:165-167` calls `navigate(Routes.conversationFor(n)) { launchSingleTop = true }` with **no `popUpTo`**, so when a conversation screen is already on top, the single `conversation/{n}` destination **reuses the existing back-stack entry and mutates its arguments in place**. The destination reads the session id non-reactively (`AiSandboxApp.kt:210`), so `ConversationScreen`'s `LaunchedEffect(sessionN) { attach(sessionN) }` (`ConversationScreen.kt:112`) never re-fires, `attach(B)` is never called, no `ConversationController`/WebSocket is established for the target session, the server's per-connection pending-question re-emit (the `aisandbox-conversation-tail` helper re-detects the blocked pane within ~600ms of a fresh connection) is never received, and `pendingSheet` stays `null` so the `QuestionSheet` never shows (`ConversationScreen.kt:210-217`). The sessions-list path uses a plain `navigate(...)` with no `launchSingleTop` (`AiSandboxApp.kt:190`) and always pushes a fresh entry, which re-keys and renders correctly — explaining why "from the list it works well". Cold-start-from-notification also works (a fresh entry is pushed over Sessions). The fix must re-key the deep-link destination on every tap so the target session always re-attaches and its pending question renders, **without re-introducing UC-91's transcript bleed, UC-88's reconnect/socket wedge, or UC-56's conversation→list re-push loop, and while keeping the sessions list under the conversation in the back stack (UC-69 AC4)**.

## Acceptance Criteria
1. **Repro-first.** On the current build, demonstrate *before* any fix that, with `conversation/A` already on top (app foregrounded, or last-on-top when backgrounded), tapping a pending-question notification for session **B** leaves the screen showing A (or B with **no** question sheet) and the chat wedged, while opening B from the sessions list renders B's question correctly. Capture whether `attach(B)` is ever invoked on the deep-link path.
2. After the fix, tapping a pending-question notification for session B **always lands on B's conversation, re-attaches (`attach(B)` is invoked), and renders B's `AskUserQuestion` sheet** (both single-question and multi-question groups), regardless of whether a different conversation, the same conversation, or the sessions list was on top when the notification was tapped.
3. The **same-session** warm case is covered: a notification for the session already on screen surfaces its newly-arrived pending question (no silent `launchSingleTop` no-op that drops the attach / re-render).
4. The deep-link still lands with the **sessions list under the conversation** in the back stack (UC-69 AC4 preserved — no empty back stack); pressing back from the deep-linked conversation returns to the sessions list.
5. **Cold-start** deep-link continues to work (fresh process, notification tap lands on the conversation with the question rendered) — no regression to `PendingQuestionNotificationInstrumentationTest`.
6. No regression to **UC-91** (no session→session transcript bleed or missing agent pills), **UC-88** (no wedged/orphaned-socket reconnect; the re-attach must not leak or accumulate WebSocket connections against the per-fingerprint cap), or **UC-56** (no conversation→sessions re-push / flicker loop from over-eager re-navigation).
7. A **regression test** reproduces the warm deep-link path (conversation-A-on-top → deep-link-to-B) and asserts `attach(B)` is invoked and B's content/question is what renders; it must fail against the pre-fix navigation call and pass after. It extends the UC-91 nav-layer test and/or the UC-69 deep-link instrumentation harness.
8. CI gates pass: **`:android:test` and `:android:lint`**; **`:server:test` + `:server:spotlessCheck` only if any server / Node-helper code is touched** (the expected fix is Android-only, so the server gates should be unnecessary).

## Potential Pitfalls & Open Questions
- **Assumption to confirm on a live/emulator repro.** Confirm that Navigation-Compose's `launchSingleTop` reuses the top `conversation/{n}` entry across *different* `n` (in-place arg mutation) and that `attach(B)` is genuinely never called on the warm deep-link — instrument `attach()` and assert it. Also confirm the same-session warm no-op case (AC3).
- **This is the UC-91 fix that was specified but not shipped.** UC-91 was marked `done` via a server/helper transcript-isolation fix (per-session `~/.claude/projects` in `aisandbox-conversation-tail`), but its own test (`ConversationSessionSwitchNavInstrumentationTest`) prescribes `popUpTo(Routes.ConversationPattern) { inclusive = true }` at `AiSandboxApp.kt:165-167`, and that line still only carries `launchSingleTop = true`. Apply the documented nav fix; do not re-litigate the transcript layer.
- **Don't ship a third incomplete fix** (the UC-91 test's own warning): the regression test must assert the *rendered target session + its question*, not merely navigation success or scroll position.
- **Regression risk vs UC-56.** Adding `popUpTo` / forcing re-navigation must not create a re-push loop on the conversation→sessions transition; scope the change to the deep-link `navigate` only and leave the network-event routing untouched.
- **Regression risk vs UC-88.** Re-attaching must reuse the process-scoped `conversationController(n)` (it already tears down other-N controllers) and must not leak or accumulate sockets; verify the `PendingQuestionService` events feed and the conversation WebSocket don't double-count against the per-fingerprint cap.
- **Open design question.** Decide between `popUpTo(ConversationPattern){ inclusive = true }` (pop + recreate the entry, as the UC-91 test prescribes and already backs) versus making the destination read `n` reactively (observe the back-stack entry's args) so `LaunchedEffect`/`attach` re-fire on arg change. The pop+recreate option is test-backed today; the reactive-read option is more general and would also harden the same-session case (AC3). The analyst should weigh which the developer adopts.
- **Server re-emit timing is fine (verified during triage).** The tail helper re-derives the pending question per connection within ~600ms; the fix is purely about ensuring the client actually opens that connection (`attach`) for the target session — no server change is expected.

## Original Description
In the ai-sandbox project, questions sometimes do not render and the chat gets stuck. It may be when trying to get to the question via the notification that does show up — but it's not certain. Other times, at least from the (sessions) list, it works well.

## Clarifications
- Q: Which client, and what exactly is "stuck"?
  A: The **Android client**; the conversation opens but the `AskUserQuestion` sheet never appears and the composer stays gated (wedged), so the user can't answer or proceed.
- Q: What is the difference between the path that fails and the path that works?
  A: It fails when reaching the conversation via the **push notification deep-link** (UC-69) while a conversation screen is already on top (warm start); it works when opening the conversation from the **sessions list** (and on cold-start-from-notification).
- Note: Triaged root cause is the warm-start navigation-entry reuse (`launchSingleTop = true` with no `popUpTo` at `AiSandboxApp.kt:165-167`) preventing `ConversationScreen` from re-attaching to the target session. This is the nav fix that UC-91's regression test prescribes but production never shipped. Closely related prior art: UC-69 (notification + deep-link), UC-55/57/75/90 (question rendering / answer path), UC-88 (wedged reconnect on navigation), UC-91 (session-switch conversation bleed + the prescribed `popUpTo` fix).

## Re-analysis (2026-06-18) — corrected root cause, what shipped, and the required follow-up

> **The original triaged root cause (above) was DISPROVEN during implementation.** The dev-team (analyst + challenger, with QA's on-device measurement) verified it against the real source and a booted emulator. The nav-entry-reuse theory does not hold; the actual cause is still unconfirmed and needs a live reproduction to pin down. This UC must **not** be considered fixed by the changes that shipped on this branch.

**Why the nav theory is wrong.** On Navigation-Compose **2.9.8**, `navigate(conversationFor(n)) { launchSingleTop = true }` **already re-keys** the destination on a warm deep-link — measured on-device: warm A→B `attachOrder=[1,2]`, same-session A→A `[1,1]`, and the `QuestionSheet` renders in both. So `ConversationScreen`'s `LaunchedEffect(sessionN){ attach(sessionN) }` (`ConversationScreen.kt:112`) **does** re-fire on every warm tap, in both the test harness (verified byte-equivalent to production) and production. The "entry reused → `attach` never fires → wedge" mechanism reproduces nowhere. Consequence: the AC7 "fail-before/pass-after" guard is **unsatisfiable at the navigation layer**.

**What shipped on `feat/uc-93-notification-deeplink-question-not-rendered` (safe groundwork, NOT a fix for the wedge):**
1. `AiSandboxApp.kt` — added `popUpTo(Routes.ConversationPattern){ inclusive = true }` to the warm deep-link `navigate`. Retained purely as **back-stack hygiene** (bounds a warm deep-link to a single `conversation/{n}` entry; keeps Sessions underneath per UC-69 AC4) and **UC-91 parity** — explicitly **not** load-bearing for the attach path (the commit comment says so).
2. Two **positive** instrumented tests (warm deep-link re-attaches and renders single + multi `QuestionSheet`) + a popUpTo parity update to `PendingQuestionNotificationInstrumentationTest.kt`. `:android:test` ✅, `:android:lint` ✅, instrumented classes ✅ on the AVD.
3. Correcting annotations on the pre-existing **UC-91** nav tests (`ConversationSessionSwitchNavInstrumentationTest`), which were false-green w.r.t. this mechanism.

**Two candidate real mechanisms (must be distinguished by a live three-signal capture):**
- **(B) Re-emit gap — currently judged UNLIKELY (no source evidence).** `ConversationController.attach` (~kt:257-259) no-ops when `connectJob.isActive`; `startConnectLoop()` is the only re-emit path. *But* pending-question delivery is a **continuous tmux-pane watcher** (`TranscriptTailService` / `aisandbox-conversation-tail`, UC-50) that streams newly-arising questions over the open socket, and the reconnect loop re-derives on every reconnect — so there is no evidenced "server holds a question but never delivers it while connected" state. A ready contingency fix is designed (client `resync-pending` frame + server re-derive-from-live-pane branch; controller-layer fail-before/pass-after test via the existing `ConversationControllerTest` MockWebServer harness) **but deliberately not built** — building it now would be speculative.
- **(render-gating) — equally plausible, and B would NOT fix it.** `ConversationScreen` suppresses the sheet when `readOnly == true`, where `readOnly = selectedTargetId.startsWith(SUBAGENT_ID_PREFIX)`. `_selectedTargetId` is a process-scoped controller field re-sent on reconnect, so a warm re-entry can **restore a prior subagent selection → the sheet is hidden even when `pendingSheet` is populated.**

**Required next step (do not close UC-93 before this).** Run the `release`/`android-testing` **live functional gate** (live app + live server, single AND multi `AskUserQuestion`), and at the instant of any real wedge capture all three: (1) `controller.pendingSheet` null vs populated; (2) `selectedTargetId` / `readOnly`; (3) whether the live pane actually holds a prompt (server tail). Triage: `pendingSheet==null` + pane-has-prompt → build mechanism **B**; `pendingSheet` populated + `readOnly==true` → fix the `selectedTargetId`/`readOnly` restore (not re-emit); no reproduction → close on the shipped popUpTo hygiene + corrected docs with the gate as AC2 evidence. The intermittent ("sometimes") nature means this needs a real reproduction, which was out of reach for this dev-team run.
