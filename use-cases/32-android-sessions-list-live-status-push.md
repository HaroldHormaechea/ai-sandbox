# Use Case 32: Android sessions list — live status updates via server push (WebSocket/SSE), not REST-poll-on-resume

## Summary
The Android sessions list ("the list of servers") does not auto-update session statuses. A session that transitions on the server — `provisioning → running`, `running → stopped`, or `running → terminating → (gone)` — keeps showing its **stale** state on the list until the user manually leaves and re-enters the screen. This is by construction, not a bug in the rendering: `SessionsViewModel` (`android/src/main/kotlin/com/aisandbox/android/ui/screens/SessionsViewModel.kt`) refreshes only (a) once on `init { refresh() }` and (b) on `Lifecycle.Event.ON_RESUME` (re-fetch when returning from the Terminal screen). There is **no server→client push**: `SessionController` (`server/src/main/java/com/aisandbox/server/api/SessionController.java`) exposes only REST `GET/POST/DELETE /v1/sessions`; there is no SSE (`text/event-stream`), no `@MessageMapping`, and no status notification channel. The only WebSocket in the system is the per-session **terminal stream** (`/v1/sessions/{n}/stream`), which carries PTY bytes + the agent-switcher control frames — it says nothing about other sessions' lifecycle. So while a sandbox finishes installing its toolchains (`provisioning`/"installing…"), or dies, or is torn down from another client, the list silently lies until the next manual refresh. The user wants the list to update itself live, driven by server-pushed notifications (a WebSocket or SSE feed of session-status changes), the same way the terminal already streams over a socket.

## Acceptance Criteria

1. When a session's server-side state changes (`starting`/`provisioning` → `running`, `running` → `stopped`, `running`/`provisioning` → `terminating`, and removal), the open sessions list reflects the new state and the filter-chip counts (`All`/`Running`/`Stopped`) recompute **without** the user leaving and re-entering the screen, within a small bounded latency (target ≤ ~2 s on a healthy connection) of the server observing the change.
2. The update is driven by a **server push** channel (WebSocket or SSE) — not by client-side polling. Spec the channel: endpoint, framing, and the event vocabulary (at minimum: session number, new state, and enough fields to update the existing `SessionSummary` row — `state`, `uptimeSec`, `activeStreams`, `startedAt`). The channel is mTLS-gated exactly like the existing REST + stream endpoints (same client-cert allowlist).
3. New sessions spawned from another client (or from this client's FAB) appear as rows on the list live; sessions deleted/terminated elsewhere disappear (or flip to `terminating` then drop) live — both without a manual refresh.
4. The push feed is reconciled with the UC-28 optimistic-`terminating` store: a server `terminating`/removal event and the client-side optimistic flag converge (no flicker back to `running`, no stuck "awaiting termination" after the server confirms). `SessionsUiState.effectiveState` semantics (UC-28) are preserved.
5. Disconnect resilience: if the push channel drops, the list falls back to the existing REST refresh (entry + `ON_RESUME`) and shows no crash and no stuck spinner; on reconnect it re-syncs to the authoritative server state (a full `GET /v1/sessions` reconcile on (re)subscribe is acceptable and recommended to avoid drift from missed events).
6. Battery / lifecycle correctness: the push subscription is tied to the sessions screen being in the foreground (started/stopped with the screen's lifecycle) so it does not hold a socket open behind the user's back — distinct from the terminal foreground-service socket, which is intentionally long-lived.
7. Tests: server-side test asserts a status-change emits a push event with the correct payload to a subscribed mTLS client; an Android test (`android/src/test/**` or `androidTest`) asserts the list `StateFlow` updates a row's `state` + counts on an inbound push frame without a manual `refresh()` call. No regression to UC-04 / UC-27 / UC-28 sessions-list behavior.

## Potential Pitfalls & Open Questions
- **Where the server learns of state changes.** `provisioning → running` is detected by `spawn.sh`/the readiness poll; `running → stopped` happens when a container exits out-of-band (docker, OOM, host reboot). The push source must observe ALL of these, not only client-initiated transitions, or the feed will be exactly as stale as today for the cases that matter most (a session dying on its own). Decide the watch mechanism (docker events stream vs. periodic server-side reconcile that diffs and pushes) before picking the wire protocol.
- **WebSocket vs. SSE.** SSE is simpler (one-way server→client, auto-reconnect, rides the existing HTTP/2 + mTLS stack) and the list only needs server→client. A WebSocket reuses the existing `ai-sandbox.v1` handshake/interceptor machinery (`SubprotocolHandshakeInterceptor`, `StreamCapsHandshakeInterceptor`) but is heavier than needed. Choose deliberately; the user said "websocket notifications" but SSE may satisfy the intent with less surface — surface the trade-off rather than defaulting silently.
- **mTLS + push channel.** The existing handshake interceptors are written for the terminal stream subprotocol. A new channel must go through the same client-cert allowlist + revocation (4401) path; do not bypass `ActiveStreamRegistry`/revocation, or a revoked client keeps getting pushes.
- **Avoiding a thundering reconcile.** On many simultaneous spawns, push one coalesced update rather than N frames; the client should apply updates idempotently to the existing list keyed by `n` (the list is already sorted by `n`).
- **Don't regress the empty-state.** Without Docker there are no sessions and the list shows the empty-state; the push channel must handle "zero sessions" and a subscribe-before-any-session-exists gracefully.
