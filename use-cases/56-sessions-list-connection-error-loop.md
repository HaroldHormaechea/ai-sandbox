# Use Case 56: Connection-error loop when returning from a conversation to the sessions list

## Summary
On the Android client, navigating **back from a conversation/chat to the main sessions list** drops the user into a *loop* of the connection-error / server-identity screen — the full-screen state that offers only "re-scan a fresh invite QR" / "Quit". Swiping back to reach the list flashes the sessions list for a moment and then the error screen reappears immediately, over and over, so the user can never settle on the list. This is the same destructive re-enroll dead-end that UC-52 reclassified (transient connectivity vs. genuine TLS/identity) and UC-54 replaced with a non-blocking tri-state connectivity dot — but it still manifests, now specifically on the **conversation → sessions-list back-navigation transition**, and as a *tight repeating loop* rather than a single misroute. The likely mechanism is a sticky/replayed network `NetworkEvent` (or an error route that is never cleared) being re-consumed on each recomposition or each sessions-list refresh tick after the back navigation, so the error screen is re-pushed as fast as it is dismissed. The fix must ensure that returning to the sessions list lands on (and stays on) the list: a genuinely unreachable server shows the transient, auto-recovering "server unreachable / reconnecting" state (UC-52/UC-54), never a loop, and the destructive identity/QR screen appears only for a real TLS/identity compromise. This is expected to be an Android-client change in the network-event routing / sessions-list navigation state.

## Acceptance Criteria
1. Navigating back (including swipe-back) from a conversation to the sessions list lands on the sessions list and **stays there** — the connection-error / "re-scan QR / Quit" screen is not auto-pushed, and there is no flicker/loop between the list and the error screen.
2. There is no infinite loop under any condition: once the error/identity screen is dismissed or escaped, it is never automatically re-pushed by a stale/replayed network event or by a routine sessions-list refresh tick.
3. When the server is genuinely **reachable**, returning to the list shows the normal list (with the UC-54 tri-state connectivity indicator in its healthy state) and no error surface at all.
4. When the server is genuinely **unreachable** at the moment of return, the list shows the transient "server unreachable / reconnecting" state (UC-52/UC-54), with a retry/auto-recovery path — not the destructive re-enroll/QR screen, and not a loop. It auto-recovers to the normal list once the server is reachable again.
5. The destructive server-identity / "re-scan a fresh invite QR" screen is reached **only** for a genuine TLS/identity compromise (per UC-52's classification), never as a side effect of the conversation→list back navigation.
6. A regression test reproduces the return-to-list scenario under a transient/failed connectivity condition and asserts the sessions list remains displayed without re-routing into the error/identity screen (i.e. the event is single-shot / the error state is cleared on navigation or successful refresh).
7. No regression to UC-51 (no crash on unreachable server), UC-52 (connectivity-vs-TLS reclassification), UC-54 (tri-state connectivity dot, no blocking banner), or UC-32 (events-feed reconnect/back-off).
8. CI gates pass: `:android:test` and `:android:lint`; and if any server code changes, `:server:test` and `:server:spotlessCheck`.

## Potential Pitfalls & Open Questions
- **Ambiguity** — The exact trigger needs isolation on the emulator: is it (a) a sticky `StateFlow`/replayed `SharedFlow` `NetworkEvent` that every recomposition re-consumes and re-routes from, (b) the back-navigation re-subscribing/re-issuing a request that fails and re-pushes the route, or (c) an error route left on the back stack that re-surfaces after the list briefly shows? The analyst/QA must reproduce and pin the precise cause before the developer changes routing.
- **Risk** — Classic one-shot-event bug: a network/identity event modeled as replayable state (rather than a consumed-once effect) will re-fire on every recomposition, producing exactly this flicker loop. The fix should make the routing event single-shot and/or clear the error state on successful navigation/refresh — without weakening UC-52's genuine-identity routing.
- **Edge case** — "Swipe-back flashes the list then the error returns" implies the re-push happens on the next frame or the next refresh tick; the fix must clear/short-circuit the error condition at the moment of return, not rely on the back-stack accident UC-52 noted.
- **Assumption** — This reproduces under a real connectivity edge (server momentarily unreachable, a dropped WebSocket, or a request failing during the nav transition). If it loops even against a fully healthy server, the root cause is a pure navigation/state bug rather than a connectivity-classification one — the analyst must determine which, as it changes the fix site.
- **Relationship** — Closely tied to UC-51/UC-52/UC-54 in the network-event → screen-routing layer (`TlsFailureTranslation`, `AiSandboxHttpClient` interceptor, `SessionsCoordinator`, and the root composable's identity-screen routing). The fix must not regress genuine TLS/identity routing or the tri-state dot.
