# Use Case 50: Conversation view — pending `AskUserQuestion` (single AND multi) no longer appears while the session blocks (UC-40 regression on current Claude Code)

## Summary
In the Android structured-conversation (non-tmux) view, when the live `claude` session asks via `AskUserQuestion` — whether a single question or a multi-question batch — the question sheet **never appears while the session is blocked awaiting the answer**. The conversation just shows the "Working…" spinner indefinitely; the phone user can neither see nor answer the question and is completely stuck unless they long-press into the tmux view. The question only renders **retroactively**, as a collapsed `❓ question / tool: ✗|✓` bubble, once it has already been answered/declined elsewhere. This is a regression of UC-40 (and UC-43's live multi-question delivery) caused by a change in Claude Code's transcript-write behavior.

Confirmed live against a real backend + Android emulator with Claude Code `v2.1.169`: while the session is blocked on an `AskUserQuestion`, the transcript `.jsonl` **ends with a newline at the user-prompt line** — the assistant turn that carries the `AskUserQuestion` `tool_use` is **not written to the transcript at all**, not even as an unterminated trailing line. UC-40's fix delivered the blocking question by detecting a **complete-but-unterminated `residual` line** (the assistant message written without its trailing newline) and idle-flushing it (`container-bin/aisandbox-conversation-tail` → `idleFlush`). Current Claude Code buffers the entire assistant turn in memory until the answer is produced, so there is **no residual to flush** — `idleFlush` and the transcript-tail path have nothing to relay, and the conversation view shows nothing.

The same blindness is already documented in-code: `aisandbox-conversation-tail`'s `scanPending` carries a "KNOWN LATENT GAP (UC-49)" comment noting that a live awaiting-answer `AskUserQuestion` is not persisted to the transcript while Claude blocks, so transcript-derived detection misses it. UC-49 solved this **only for the sessions-list "?" indicator**, via a **visible tmux-pane capture** (the `conversationName`/turn-state pane signal) rather than the transcript. The conversation view's question *delivery* was never migrated to that pane signal and still relies on the now-defunct transcript residual.

The fix delivers the live, pending question (single and multi) to the conversation view from the **tmux-pane signal** (the same class of signal UC-49 proved works), so the question sheet appears while the session is still blocked and the user can answer it in-app — independent of whether Claude Code writes the assistant turn to the transcript before or after the answer. It must keep working once Claude later writes the resolved turn to the transcript (no duplicate bubble, correct dedupe against UC-37/UC-40 keying).

## Acceptance Criteria
1. When the live session asks an `AskUserQuestion` and blocks awaiting the answer, the question sheet appears in the structured-conversation view with **no user action in any other view**, while the session is still blocked — even when Claude Code writes **nothing** to the transcript for the blocking turn (verified behavior on `claude v2.1.169`).
2. Holds for a **multi-question** batch (`questions[]` length ≥ 2): the paged in-app sheet (UC-43) appears with all questions and the answer-batch resolves them, while blocked.
3. Holds for a **single** question: the sheet appears with its options while blocked.
4. Answering in the structured view resolves the question in the live session and the turn proceeds, with no need to open tmux at any point.
5. When Claude later writes the resolved assistant turn (with the `AskUserQuestion` `tool_use` + `tool_result`) to the transcript, the conversation does **not** double-render the question (no duplicate question bubble / no phantom collapsed `❓ question` in addition to the live sheet) — correct dedupe against the UC-37/UC-40 key scheme.
6. The plan-mode `ExitPlanMode` approval prompt — same "assistant message that then blocks on input, not yet in the transcript" mechanism — is delivered live and answerable in the structured view under the same conditions.
7. No regression to the UC-49 sessions-list "?" indicator, the UC-48 working spinner, or normal-turn streaming (assistant text, tool-use/result, thinking, turn-end, backfill/reconnect dedupe — UC-37 AC3–AC6/AC22). Ordering is preserved and no duplicates are introduced.
8. Subagent/teammate (`isSidechain`) pending questions get the same live delivery as the main pane where the pane signal can resolve them.
9. A regression test reproduces the current-Claude state — a blocked session whose transcript has **no** assistant line for the pending `AskUserQuestion` (transcript ends at the user prompt) — and verifies the question is delivered live from the pane signal, then that the later transcript write does not double-emit it.

## Potential Pitfalls & Open Questions
- **Root signal** — The reliable live signal is the **tmux pane** (the `claude` TUI showing the question/options or the multi-question `☐ <header> … ✔ Submit` tab strip), not the transcript. Reuse/extend the UC-49 pane-capture path rather than inventing a parallel scraper; parsing the TUI is brittle, so prefer the most structured signal Claude Code exposes (e.g. the pane's question affordance) and pin its shape with a recorded fixture.
- **Parsing the options from the pane** — The conversation sheet needs the full structured payload (each question's `header`, `question`, `options[].label/.description`, `multiSelect`). The pane capture may not carry the option descriptions verbatim; determine whether the option text/descriptions can be recovered from the pane, and if not, define the degraded-but-usable rendering (labels at minimum) without blocking delivery.
- **Dedupe across the two delivery paths** — The live pane-delivered question and the later transcript-written `tool_use` must collapse to one rendered item. Reuse `ConversationController`'s key-dedupe; key the pane-delivered question stably (e.g. by `toolUseId` once known, else a deterministic pane-derived key) so the transcript copy reconciles rather than duplicating.
- **Answer injection** — Answering in-app must drive the SAME blocked TUI selection (the existing UC-43/UC-37 injection path); confirm the injected answer maps correctly to the multi-question tab/Submit flow so it doesn't desync the wizard.
- **Open question (verification)** — Confirm on the live image whether any Claude Code flag/transcript mode restores the pre-regression behavior (writing the blocking line without a trailing newline). The live byte-level evidence (transcript ends with `\n` at the user prompt, zero assistant `AskUserQuestion` lines while blocked) makes the pane-signal fix the correct path regardless; do not re-hang the feature on the transcript residual.

## Original Description
Functional check of the chat against a real backend + emulator: a multi-question select was not showing in the latest server and client versions, and further questions — even single ones — did not show further down in the conversation. Reproduced live: the conversation view shows only "Working…" while `claude` blocks on an `AskUserQuestion` (single or multi); the question only appears retroactively as a collapsed bubble after it is answered/declined in tmux. Root-caused to Claude Code no longer writing the blocking assistant turn to the transcript, which defeats UC-40's residual idle-flush; UC-49's tmux-pane signal already detects the pending question for the sessions-list indicator and should drive conversation-view delivery too.

## Clarifications
- Q: Single questions only, or multi too? A: Both — reproduced that single AND multi pending questions fail to render live; this UC covers both (multi via the UC-43 paged sheet).
- Q: Is the question lost or delayed? A: Delayed/never-while-blocked — it appears retroactively (as a collapsed resolved bubble) only after being answered elsewhere, confirming a delivery-path gap, not a dropped line.
- Q: Why did UC-40's fix stop working? A: Claude Code (v2.1.169) no longer writes the blocking assistant+`AskUserQuestion` line to the transcript at all (not even unterminated), so the residual idle-flush has nothing to flush. Verified at the byte level on the live image.
- Q: What signal should the fix use? A: The tmux-pane signal proven by UC-49 (sessions-list "?" indicator), brought to the conversation view's question delivery — not the transcript residual.
- Q: Scope? A: Root-cause live delivery from the pane signal for single + multi questions (and ExitPlanMode), with correct dedupe against the later transcript write and no regression to UC-37/40/43/48/49.
