# Use Case 33: Android terminal — re-zoom on mid-stream subagent spawn (window paints split until a switcher tile is tapped)

## Summary
After UC-24 fixed the "all tmux windows shown" regression by generalizing the single-pane **zoom** (`resize-pane -Z`) to every target, a related regression remains for the **mid-stream** case: when an agent team / subagents spawn **while the operator is already attached** to a target (typically `main`), the terminal paints as a **split** (multiple tmux panes visible) instead of staying zoomed to the selected target. The split only collapses back to a single isolated pane once the operator taps one of the agent-switcher tiles. Root cause is in the timing of the server-side zoom: `TmuxBridgeService` (`server/src/main/java/com/aisandbox/server/stream/service/TmuxBridgeService.java`) applies the generalized zoom **only at bridge/attach time and on a `select-target` control frame** (which re-bridges → re-focuses → re-zooms). On the Android side, `TerminalStreamController` (`android/src/main/kotlin/com/aisandbox/android/terminal/TerminalStreamController.kt`) runs a periodic `enumerate` every `ENUMERATE_INTERVAL_MS` (3 s) that refreshes the **switcher row** (`_targets`) but deliberately does **not** re-select or re-zoom the active target. So when Claude Code splits the current window to host newly-spawned teammates, the new pane appears in the already-bridged, previously-zoomed window and un-splits nothing: the zoom is now stale (tmux exposes the multi-pane layout), and nothing re-asserts it until the operator's manual `selectTarget(...)` triggers a fresh bridge+zoom. The fix is to re-assert the zoom on the **currently-selected** target whenever the pane/target set changes mid-stream (detected by `enumerate`), or to make the server auto-zoom the bridged client's active pane whenever it adds a pane to that window — so the operator never sees the transient split.

## Acceptance Criteria

1. On a live `ai-sandbox-N` session, with the operator attached to `main` and the agent-switcher showing only `main`, when an agent team / subagents spawn mid-stream (Claude Code splits the window / opens swarm panes), the rendered terminal **continues to show a single zoomed pane** for the selected target — the operator never sees the multi-pane split appear, even transiently beyond one render frame.
2. The agent-switcher row still updates within ~one `enumerate` interval (≤ ~3 s) to show one tile per new teammate plus the always-first `main` tile (UC-21 AC#9-12 preserved). I.e. the row gains the new tiles **without** the viewport going split.
3. Tapping a switcher tile still works as before (UC-21 AC#11): it switches the rendered target within ~1 s and re-zooms that target; the previously selected tile loses its highlight.
4. The re-zoom is idempotent and does not toggle: because `resize-pane -Z` is a TOGGLE, re-asserting the zoom on an already-zoomed pane must be guarded (reuse / extend `TmuxBridgeService.zoomNeeded`, which checks `#{window_panes} > 1 && !#{window_zoomed_flag}`) so a mid-stream re-zoom never accidentally un-zooms a correctly-zoomed view.
5. No second client / orchestrator regression (UC-24 pitfall): a mid-stream re-zoom triggered by the Android client must not force-zoom or disturb another client of the same swarm/base session, nor the orchestrator's own windows.
6. Reconnect path preserved: after a WS drop+reconnect mid-team, the controller's existing re-enumerate + re-select-prior-target path (`TerminalStreamController.startConnectLoop`) restores the zoomed selected target, not the split.
7. Verification is grounded in live `tmux` inspection (mirror the UC-24 "Live Verification" expectation): record what `list-panes -a` and `#{window_zoomed_flag}` showed at the moment of subagent spawn before and after the fix, and demonstrate AC#1 end-to-end against the emulator via the `android-testing` skill.

## Potential Pitfalls & Open Questions
- **Whose responsibility — client or server.** Two viable fixes: (a) client re-asserts the selected target (re-send `select-target` for the current id, or a lighter "re-zoom" control frame) when `enumerate` reports the target/pane set changed; (b) server auto-zooms the bridged client's active pane whenever a pane is added to that window (a tmux hook / on the next enumerate the bridge re-checks `zoomNeeded` and re-zooms). Option (b) keeps the zoom policy server-side (where UC-24 already lives) and avoids a client round-trip; option (a) needs no server change. Decide explicitly; do not implement both blindly.
- **Detecting "the pane set changed".** `enumerate` already returns the targets list; the client can diff it against the prior `_targets` to detect a mid-stream change and only then re-assert (avoid re-zooming every 3 s unconditionally, which risks toggling and wastes frames).
- **Toggle hazard.** The single biggest trap (called out in UC-24): `resize-pane -Z` is a toggle. Any new re-zoom code path MUST go through a `zoomNeeded`-style guard, or it will intermittently un-zoom and reintroduce exactly the split this UC removes.
- **First-paint vs. mid-stream are different bugs.** UC-24 fixed the initial-attach paint; this UC is specifically the **mid-stream pane-addition** case. A fix that only re-checks at attach (already shipped) does not cover this — verify the new path fires on pane *addition while connected*.
- **Latency window.** Even with a fix, there is a window between the tmux split happening and the next enumerate/hook firing. AC#1 should define the acceptable bound (one render frame / sub-second) and the implementation should minimize it — a tmux `after-split-window`/`window-pane-changed` hook on the server is tighter than a 3 s client poll.
- **Verification cost.** Reproducing requires a live container where `claude` actually spawns a real agent team (same constraint as UC-21/UC-24); the camera-free enrollment probe alone is insufficient to drive the terminal UI.
