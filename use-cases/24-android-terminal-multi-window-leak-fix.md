# Use Case 24: Android terminal — fix "all tmux windows shown" regression (only the main pane should display + agent switcher to swap targets)

## Summary
On the terminal screen (UC04-3, post UC-21), the user reports that tapping a session does not show what UC-21 promised — a single main-session pane with the `AgentSwitcherBar` on top to switch between main and agent-team members. Instead, "all tmux windows are shown", and the switcher does not visibly narrow the display. The Compose + controller source matches UC-21's intent on inspection (one `TerminalSurface`, one `TerminalView`, switcher self-hides when only `main` is present, `selectTarget` re-targets the WebSocket in place), so the regression is runtime-level, not screen-layout level. Three live hypotheses to validate against an active swarm container: (1) the `main` `BridgeTarget` skips `resize-pane -Z` because `hasPane()` is false, so when Claude Code's main session spans multiple tmux windows the per-client `attach` exposes the user to whichever window tmux had focused (and to the prefix-key window switcher in tmux's status line); (2) `select-pane` / `resize-pane -Z` on the per-client swarm session silently fails after the swarm orchestrator rotates panes, leaving the per-client view on the unzoomed split layout that visually matches "all windows shown"; (3) `SwarmEnumerationService.discoverSwarmSockets` enumerates lingering defunct `claude-swarm-*` sockets, surfacing stale teammates in the switcher row alongside the live ones. The fix is to identify which of the three (or a fourth, discovered live) actually fires today, ship the targeted server-side correction, and — if cause (1) is real — extend the switcher to also surface the main session's tmux windows as switchable tiles, since hiding the window switcher from the Android user when Claude Code's runtime has shifted from "one main window" to "many main windows" is the exact gap they reported.

## Acceptance Criteria

1. On a live `ai-sandbox-N-claude-sandbox-1` with **no** agent team running, opening the terminal shows the main pane filling the rendered viewport, no extra panes visible, no agent-switcher row (per UC-21 AC#12).
2. On the same live container with an active agent team (a Claude Code `--team-name` swarm), opening the terminal still shows **only one terminal surface** at a time — never the unzoomed multi-pane split — with the agent-switcher row rendering one tile per teammate plus the always-first `main` tile (per UC-21 AC#9-12).
3. Tapping a switcher tile actually changes what the surface renders within ~1 s on a healthy WS, and the previously selected tile loses its highlight (per UC-21 AC#11). Mid-stream resize frames follow the switch so the visible PTY matches the rendered cols×rows (UC-21 AC#4).
4. Stale `claude-swarm-*` sockets that no longer host a live tmux server do **not** appear in the switcher row. Discovery is robust to a swarm restart between two `enumerate` calls — the second call must reflect the live socket only.
5. If the live evidence shows cause (1) — Claude Code's main session now has multiple windows — the fix extends discovery to enumerate the main session's windows on the default socket, surfaces them as switcher tiles (labeled with the window index + a friendly title pulled from tmux), and routes selection through the existing `select-target` control frame without breaking AC#9-12 above.
6. The diagnosis is grounded in live container inspection (mirror the UC-21 "Live Verification" section in the resulting commit message / use-case update). Spec interpretation alone is not sufficient — record what `tmux list-sessions / list-windows / list-panes -a` returned on the default and swarm sockets, and what `resize-pane -Z` actually did to the per-client session.
7. No regression: UC-21 AC#1-15 still pass (Compose instrumented tests under `:android:connectedAndroidTest`), `:server:test` is green, and a smoke run against the live emulator using the `android-testing` skill demonstrates AC#2 above end-to-end.

## Potential Pitfalls & Open Questions
- **Upstream churn (Claude Code swarm layout).** UC-21 was written against panes-in-one-window on a `claude-swarm-<pid>` socket. If Claude Code has shifted to windows-each-with-one-pane, `list-panes -a` still enumerates them but the zoom path is a no-op (already a single pane per window) and labeling needs to read window-title metadata instead of pane-title. Resolve with live `tmux` inspection before patching the discovery code.
- **Main-session multi-window.** If the regression is actually that the *main* session has acquired additional tmux windows (e.g. user split with the prefix key, or some onboarding helper opened one), the switcher should arguably also surface those — even though UC-21 framed the switcher as "main + agents only". Decide explicitly whether to expand UC-21's contract or to fold a separate "main window switcher" tile category in.
- **Tmux zoom across socket attach.** `resize-pane -Z` toggles the zoom flag on the targeted pane in the *per-client* session, but the new-session was created with `-t baseSession`, which shares window state with the source. Verify the zoom does not leak to other clients of the same swarm session (an orchestrator's window should not be force-zoomed by an Android attach).
- **Identical-id collisions on socket rotation.** The target id is `swarm:<socket-basename>:<window>.<pane>`. A swarm restart that re-uses (window, pane) on a *different* socket-basename is safe; but if the basename ever repeats across restarts (PID reuse), a stale id could match a live target with different argv metadata. Treat the targets list as authoritative per-frame, not cumulative.
- **Verification cost.** This UC depends on a live container with a real Claude Code agent team to reproduce. The `aisandbox-emulator` helper + `android-testing` skill provide the on-device path; the live container requires a session that has actually had `claude` invoke a swarm. Plan for the verification round to take longer than the typical UC.
