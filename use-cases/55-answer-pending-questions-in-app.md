# Use Case 55: Answer pane-derived pending AskUserQuestion in-app (drop the "answer in tmux" fallback)

## Summary
The Android conversation view already renders an in-app `QuestionSheet` for transcript-derived `question` frames (single-question, multi-question, and plan-approval variants), with working selection controls and a submit action that sends the answer back over the conversation WebSocket. However, **pane-derived `pending-question` frames** — the ones delivered (UC-50) while the session is blocked and the transcript hasn't yet been written — arrive marked `answerable = false`. For those, the sheet renders a read-only "⌨ Answer in tmux to continue" affordance with no submit control, forcing the user to leave the app and answer in the tmux terminal. This use case makes pane-derived pending questions answerable **directly in the app**: the question text and its options are surfaced in the same `QuestionSheet` with working radio/checkbox controls and a submit action, and the user's choice is sent back over the conversation WebSocket (`answer` / `answer-batch` frames) and injected into the session by the server, so the session unblocks without the user ever touching tmux. It also verifies that the answer-send path reliably delivers the response and unblocks the session for this pane-derived path, and fixes it if it does not. Likely an Android-client change, but the server may need to populate the full option set on pending-prompt frames if the client cannot currently render answerable controls from them.

## Acceptance Criteria
1. When a pane-derived `pending-question` carrying a **single** question is delivered while the session is blocked, the conversation view shows the question text, its header, and all selectable options with working radio/checkbox controls **and** a submit/answer control — not the read-only "Answer in tmux to continue" affordance.
2. When a pane-derived `pending-question` carries a **multi-question batch**, each question is shown with its options (paged "X of N" as the transcript-derived path already does), and a single final submit sends all answers.
3. Submitting an answer to a pane-derived pending question sends the correct structured frame over the conversation WebSocket — `answer` for a single question, `answer-batch` for a multi-question batch — identical in shape (`questionUuid`, `questionIndex`, `selections`, `freeText`) to the transcript-derived path.
4. After a successful submit, the question sheet is dismissed, the composer is unlocked, and the blocked session proceeds (server injects the corresponding keystrokes). The user completes the answer without ever switching to the tmux view.
5. The "⌨ Answer in tmux to continue" read-only fallback is no longer shown for pending questions whose options are available to render. If a genuinely un-answerable residual case remains (options cannot be derived at all), it is the explicitly-justified exception, not the default.
6. Multi-select questions and the "Other" free-text option round-trip correctly for pane-derived questions, exactly as they do for transcript-derived ones.
7. An automated test asserts that submitting from a pane-derived pending question produces the correct `answer` / `answer-batch` frame and that the sheet/composer state transitions correctly afterward. If the existing send path is broken for the pane-derived case, it is fixed and the test guards the fix.
8. No regression: existing transcript-derived `question` / plan-approval flows and their tests still pass.
9. CI gates pass: `:android:test` and `:android:lint`; and if any server code changes, `:server:test` and `:server:spotlessCheck`.

## Potential Pitfalls & Open Questions
- **Assumption** — Pane-derived `pending-question` frames have historically been delivered header-only for multi-question batches (no full option text), which is exactly why they were marked `answerable = false`. To answer in-app the full option set must be available to the client. Resolution for the dev-team to confirm: either the options are already present on the pane-derived frame and only the client gate (`answerable`/UI) needs changing, or the server (`PendingPrompt` / `ConversationEventMapper` / `SessionConversationHandler`) must populate the options before sending. This determines whether the change is Android-only or Android + server.
- **Risk** — Keystroke injection is version-pinned (`InputInjectionService.PINNED_CLAUDE_VERSION`, Claude Code 2.1.169). The answer path for pane-derived questions MUST reuse the same `deriveAnswerSpec` mechanism as the transcript-derived path; do not add a parallel, divergent injection path.
- **Edge case** — A pending question may resolve or disappear between delivery and the user's submit (e.g., the user answered in tmux anyway, or the session moved on). A stale submit must be handled gracefully — no crash; the sheet dismisses and the composer unlocks.
- **Edge case** — If the pane-derived signal genuinely cannot carry/derive options for a particular prompt kind, that single case may still need the tmux affordance; it must be narrowly scoped and clearly labeled, not the catch-all.

## Original Description
In the ai-sandbox Android client, when the running Claude Code session raises an interactive question (an AskUserQuestion prompt), the user is currently told to go answer it in the tmux view. Instead, the Android app should surface that question — including its options — directly in the same in-app popup/UI and let the user pick/answer it there, sending the answer back to the session. This is likely an Android-client-only change. Also make sure the responses are sent properly (verify the answer-send path and fix if not).
