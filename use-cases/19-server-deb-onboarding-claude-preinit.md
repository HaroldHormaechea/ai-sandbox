# Use Case 19: Server `.deb` onboarding — auto-run the wizard on a TTY and capture Claude's first-run state so spawned sessions start fully onboarded

## Summary
Installing `ai-sandbox-server` from the `.deb` should leave the operator with a server whose newly spawned session containers launch a Claude already past first-run setup. Two gaps break that today. **(1) Install does nothing visible:** `server/debian/postinst` only auto-runs onboarding when debconf captured `onboard=true` + git name + email; under `sudo dpkg -i` (which never runs the debconf `config` script) or the noninteractive frontend it falls through to a "run it yourself" message — experienced as "it didn't auto-trigger." **(2) Spawned Claude is un-onboarded:** the Claude pre-init snapshot meant to suppress the in-container first-run wizard (theme + completed-onboarding + signed-in account) is never captured — the dpkg path always passes `--no-claude-preinit`, and the interactive capture (`ClaudePreInitStep`) binds only `~/.claude/` while Claude writes that state to the *sibling* `~/.claude.json` (preserved for live sessions only via the `entrypoint.sh` symlink), so the template omits exactly the suppressing state. The desired end state: installing from a terminal (via either `dpkg -i` or `apt install ./*.deb`) leads the operator into the full interactive onboarding (including a one-time Claude device-flow login) and any session spawned afterward starts at Claude's normal prompt; a zero-touch `--claude-config-source` path covers headless provisioning; and when no terminal is available the install completes cleanly with one unambiguous next step rather than a silent no-op. The hard constraint stands: a one-time Claude OAuth login needs a TTY/browser and cannot happen unattended inside dpkg.

## Acceptance Criteria
1. After the supported install + onboarding sequence, attaching to a freshly spawned session's tmux shows Claude at its normal prompt — **no** theme/color-scheme prompt and **no** account/login prompt.
2. The pre-init capture includes the state Claude reads to skip first-run onboarding (theme, completed-onboarding flag, signed-in account/credentials — i.e. the relevant `~/.claude.json` content), and that state is seeded into each spawned session's `~/.claude/` **and** `~/.claude.json`. New coverage asserts `~/.claude.json` content is captured (not just that some non-empty file exists).
3. Installing from an interactive terminal triggers the full interactive onboarding (including Claude pre-init), and this works whether installed via `sudo apt install ./*.deb` **or** `sudo dpkg -i *.deb`.
4. When no interactive terminal is available (noninteractive frontend / piped fds / unattended), install never hangs and never silently no-ops: it completes and emits exactly one unambiguous, correct next-step instruction.
5. Both capture paths are supported and documented: (a) interactive device-flow login (default) and (b) zero-touch `--claude-config-source <pre-built ~/.claude/>` for headless provisioning; both yield a template satisfying AC2.
6. `aisandboxctl onboard` run interactively completes Claude pre-init or fails loudly with actionable guidance (no Docker / no TTY) — it must never report success while producing a template that still leaves spawned Claude prompting (the usability check must detect onboarding/theme state, not merely "≥1 non-empty file").
7. Install + onboarding is idempotent — no duplicate system user, no clobbered PKI, no spurious re-prompt; `--force` refreshes intentionally.
8. Pinning contract tests (`DebPostinstContractTest`, `OnboardCommandTest`, `ClaudePreInitStepTest`, and any others that assert the old behavior) are updated to the new intended behavior and pass; new tests cover the TTY auto-run trigger, both install commands, the `~/.claude.json`/theme capture, and the `--claude-config-source` path.
9. No regression to the deliberate security posture: empty-allowlist start is preserved (server starts, returns 401 until a client is minted/enrolled); the gh token is never persisted to the debconf database or the process table.

## Potential Pitfalls & Open Questions
- **Risk (key implementation question)** — TTY detection inside maintainer scripts differs by installer: `dpkg -i` from a terminal usually preserves terminal fds, but `apt install` typically pipes maintainer-script fds into its progress UI, so a naive `[ -t 1 ]` in `postinst` will not reliably fire under apt. The auto-run trigger probably can't be "launch OAuth mid-postinst"; the analyst should choose a robust mechanism (detect apt vs dpkg; offer a `Y/n` invite; or defer to the first interactive `aisandboxctl`/login).
- **Risk** — running a `docker run -it` device-flow inside a maintainer script is fragile (apt may deny a controlling TTY; Docker may be down at install time). A "you have a terminal — run `sudo aisandboxctl onboard` now? [Y/n]" invite may be safer than launching OAuth from within dpkg.
- **Assumption (analyst to confirm)** — the installed Claude version stores completed-onboarding/theme/account in `~/.claude.json` exactly as the `entrypoint.sh` comment (lines 25–28) states, and the capture gap is precisely that this sibling file lives outside the helper container's `~/.claude/` bind. Confirm the exact file(s)/keys for the current Claude release before designing the capture fix.
- **Risk** — Claude's first-run state format is upstream-owned and version-volatile; prefer whole-file capture over synthesizing keys, and harden `ClaudePreInitStep.scratchIsUsable` without pinning brittle keys.
- **Edge case** — isolated vs shared `claude-config` (`spawn.sh --isolated-claude-config`) and the `.seeded` first-start marker in `entrypoint.sh`: the template must seed every variant, and rotating the template requires respawning affected sessions.
- **Constraint (kept)** — Claude refuses `--dangerously-skip-permissions` at euid 0; the capture container already runs as uid 1000 — preserve this when changing the capture path.

## Clarifications
- Q: A Debian postinst can't reliably run an interactive multi-step wizard (no guaranteed TTY, Claude OAuth needs a browser, image build is slow + Docker-bound), and UC-17 deliberately made the dpkg path non-interactive. Given that, what should installing the `.deb` do about launching onboarding?
  A: Auto-run the full interactive wizard when a TTY is present, with a reliable, unambiguous next-step fallback message when no terminal is available.
- Q: How was the package installed when it failed to auto-trigger?
  A: Either `sudo dpkg -i ...deb` or `sudo apt install ./...deb` — both must be handled. (The `dpkg -i` path never runs the debconf `config` script, which fully explains the deferred message.)
- Q: Claude's account login is a device-flow that needs an interactive terminal + browser, so it can't be fully automated inside dpkg. What level of automation is needed for the in-container Claude account?
  A: Support both — interactive device-flow capture as the default, plus a documented zero-touch `--claude-config-source` path for headless/automated server provisioning.
- Q: Should UC-19 cover both symptoms (install auto-trigger gap + spawned Claude stuck on theme/account), or scope down to one?
  A: Both — they share a root flow: install → onboard → spawned Claude starts fully configured.
