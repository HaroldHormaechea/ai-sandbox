# Use Case 76: Notifications — drop the always-on "Watching for questions"/"Attached to…" noise; only alert on a new question, titled "Claude needs your input"

## Summary
Today the Android app posts persistent foreground-service (FGS) notifications the user doesn't want: **"Watching for questions"** (the `PendingQuestionService` watcher FGS, started unconditionally in `MainActivity.onCreate`, effectively always-on) and **"Attached to ai-sandbox-N · …"** (the `TerminalForegroundService` FGS, present while a terminal stream is attached). The user wants neither shown as standing notifications. They DO want a notification **only when a question arrives** (the existing UC-69 pending-question event notification), and that question notification should be **titled "Claude needs your input"** (currently the title is the conversation name / label / `ai-sandbox-<n>`), with its **body being the first question text — which already happens today** (`PendingQuestionNotifier.bodyFor`). The core Android constraint: both standing notifications belong to `dataSync` foreground services, and Android 8+ **requires** a non-dismissable notification while an FGS runs — they cannot simply be deleted without re-architecting the services. The chosen direction is to **minimize them to quiet/generic** (keep the FGS legal, channel at `IMPORTANCE_LOW`, drop the "watching for questions"/attached-details copy) so they recede, while the question event notification becomes the only attention-grabbing one, retitled to the fixed string.

## Acceptance Criteria
1. The question (event) notification is **titled exactly "Claude needs your input"** for every pending question (no longer the conversation name / label / session id). The title is sourced from a string resource.
2. The question notification **body remains the first question's text** (unchanged behaviour: `PendingQuestionNotifier.bodyFor`, including its truncation and blank-fallback), and it still fires as a HIGH-importance heads-up on the `pending-questions` channel, auto-cancelling when the question is answered/cleared.
3. The **"Watching for questions"** FGS notification no longer shows the "watching for questions"/"you'll be notified" copy: it is minimized to quiet, generic text (or app-name only) on its existing `IMPORTANCE_LOW` `question-watcher` channel, so it is not a standing "watching" message the user notices. The channel id is unchanged (so user settings are not orphaned), and the FGS remains legal.
4. The **"Attached to ai-sandbox-N · …"** FGS notification is likewise minimized to quiet/generic text on its existing `IMPORTANCE_LOW` `terminal-stream` channel while a terminal is attached (it is FGS-required while attached, so it is minimized rather than removed). Its lifecycle (appears on attach, clears when the stream detaches) is unchanged.
5. No FGS is broken: both `dataSync` services still post a (now-minimal) notification while running, so neither service crashes or is killed for missing its FGS notification on any supported Android version.
6. Existing tests that assert the old question-notification title (the title-fallback cases in `PendingQuestionNotifierTest.kt`, and any posted-title assertion in the instrumentation test) are updated to the new fixed title; the body/first-question assertions stay green.
7. QA verifies on the emulator: launching the app no longer surfaces a prominent "Watching for questions" notification; opening a terminal shows only a quiet/minimal attached notification; raising an AskUserQuestion fires a heads-up titled "Claude needs your input" with the first question as the body; answering clears it.

## Potential Pitfalls & Open Questions
- **Risk / Android constraint** — FGS notifications are mandatory while the `dataSync` services run; they cannot be removed outright without re-architecting (e.g. dropping the always-on `PendingQuestionService` in favour of FCM/push, which is out of scope and changes UC-69's background-delivery semantics). The fix is minimization, not deletion.
- **Edge case** — Notification **channel importance can't be lowered programmatically** after creation, but both watcher/terminal channels are already `IMPORTANCE_LOW`, so no change is needed there; do NOT change channel **ids** (that orphans user settings).
- **Risk** — Don't downgrade the `pending-questions` channel (`IMPORTANCE_HIGH`/`PRIORITY_HIGH`/`CATEGORY_MESSAGE`) — that is what makes the question alert a heads-up; lowering it would break the one notification the user explicitly wants.
- **Edge case** — `POST_NOTIFICATIONS` (Android 13+) is already declared and guarded (`areNotificationsEnabled()`); behaviour must still degrade gracefully when denied (in-app UC-49 indicators remain).
- **Scope** — The request names both "attached to…" and "watching for questions…". The watcher (B) is the truly always-on one; "attached" (A) only appears while a terminal stream is attached. Both are minimized here; the body-already-correct part of UC-69 (first-question text) is a no-op.
- **Key files** — `android/.../notifications/PendingQuestionNotifier.kt` (`titleFor` → fixed string; `bodyFor` unchanged), `android/.../notifications/PendingQuestionService.kt` (watcher FGS builder), `android/.../terminal/service/TerminalForegroundService.kt` (attached FGS builder), `android/src/main/res/values/strings.xml` (`question_watcher_title/_text`, `notification_title/_body`, new "Claude needs your input" string), `AiSandboxApplication.kt` (channels — ids/importance unchanged), and the two notifier test files.
